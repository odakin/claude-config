# Wiring lock の範囲: 未採用の設計案

**状態: 設計検討のみ。採用の裁定なし。** 本書は現行の規則・engine・配線を変更しない。実装は本人の具体的な裁定後、その範囲だけを対象とする。規範は [規則の所有権](../conventions/agent-rule-ownership.md)、原稿固有の制約は [原稿の所有権](../conventions/manuscript-claim-ownership.md) にある。

## <a id="current"></a>現在の判定と問題

現在の `authority_regions()` は [agent-rule-guard.py](../scripts/agent-rule-guard.py) が所有し、[manuscript dispatcher](../scripts/manuscript-claim-guard.py) が共通利用する。対象となる code / 設定の本文に engine 名が一度でも現れると、`authority:wiring` は全文になる。コメント・実行するコード・文字列を区別していない。

一方、明示 block、`authority:file`、manifest、正本参照は独立して保護を追加する。**現状では block を追加しても全文保護を上書きしない。** 特に、このリポジトリの `scripts/run-all-checks.sh` は [manifest](../.agent-rule-guard.json) にも列挙されているので、暗黙の wiring 検出だけを変えても全文保護は残る。個々の repo で、実際に発火した領域を区別する必要がある。

全文保護は、呼出行を残して周囲から無効化する変更を止めるために導入した。しかし、同じ file に普通の診断や表示を集めると、独立した修正にも候補の記録が必要になる。ここでいう負担は、承認記録の作成と候補 hash の更新である。既存の本人の依頼が具体的な修正を既に許可している場合まで、毎回新しい確認会話が必要だという意味ではない。

## <a id="options"></a>候補の比較

| 案 | 普通の編集 | 早期終了・差替えに対する性質 | 評価 |
|---|---|---|---|
| A: 明示 block だけを保護 | block 外を許可できる | 外側の `exit 0` / `return`、条件、関数定義、環境変更で停止できる | 単独採用を推奨しない。これらの穴を許容する裁定なしには進めない |
| B1: 言及行と前後の固定行数 | 近傍以外を許可できる | 範囲の外へ早期終了や関数定義を置くだけで回避できる | 推奨しない |
| B2: 構文木・依存関係で周囲を決める | 無関係と証明できた部分を許可できる可能性 | 到達条件・戻り値・変数・呼出元・読込先・実行環境も必要。未対応の構文を通すと穴になる | 対応言語と証明範囲を限定した別設計が必要。未知は全文保護または検査不能に戻す |
| C: 現状の全文保護 | 同じ file の編集には候補の記録が必要 | 同じ file 内の早期終了・条件・順序変更を止める。外部依存まで自動的に保護するものではない | 裁定までの現行動作。低い実装複雑性と編集負担の交換 |
| D: 小さな保護入口と、そこから分離した通常処理 | 通常処理の独立した変更を許可できる | 必須検査の選択・呼出し・結果判定を、変更自由な本体から切り離す。入口は全文保護のまま | 条件を満たす構造分離を推奨 |
| E: コメントだけの engine 名を暗黙の wiring 判定から除外 | 説明に言及しただけの file の誤検出を減らせる | コメントを設定として読む別の処理、引用・heredoc の誤分類に注意が要る | D と別の変更。今回は一律自動除外を推奨しない |

A を選ぶなら、scope を狭める対象は暗黙の `authority:wiring` だけとし、`authority:file`・manifest・正本参照を block が解除する優先規則にはしない。marker の追加だけで既存 lock が消える移行も不可。対象 file と範囲を明示した裁定・変更前後の比較が必要になる。重複 ID・閉じ忘れ・不正な入れ子を拒否しないまま、marker を唯一の境界にすることもできない。

## <a id="counterexamples"></a>block の外から開く穴

以下の `LOCK-BEGIN` / `LOCK-END` は説明用の表示であり、新しい marker 文法ではない。

```sh
exit 0                  # 外側だけを追加する
# LOCK-BEGIN
run required_canary
# LOCK-END
```

この例だけを `exit` の文字列検索で防いでも、同じ file の遠い場所で `run() { :; }` とすれば呼出しは空になる。`python3` の関数差替え、実行先を決める変数や `PATH` の変更、`source` / `eval` / 読込先の差替えも関係する。B の「周囲」は単なる見た目の近さでは決まらない。

実行の有無だけでなく、結果の伝わり方も対象になる。

```sh
{
    # LOCK-BEGIN
    run required_canary
    # LOCK-END
} || true               # 外側で失敗を消す
```

`set -e` がある場合も、条件付き実行の文脈で挙動が変わる。固定 block の存在、呼出しの存在、終了値の伝播は別々に検証する。

既存の述語は変更せず、合成 canary を使った Bash の使い捨て fixture で次を実行した。これらは設計上の反例の観測であり、範囲縮小した engine を実装・検証した結果ではない。

| 合成例 | block 本文 | canary | 全体の終了値 |
|---|---|---|---|
| 基準 / 後ろの通常表示だけを変更 | 同一 | 実行 | 0 |
| 手前の `exit 0` | 同一 | 未実行 | 0 |
| source される本体の手前の `return 0` | 同一 | 未実行 | 0 |
| 遠い `run()` の定義を空へ変更 | 同一 | 未実行 | 0 |
| 手前で interpreter 名を空の関数へ差替え | 同一 | 未実行 | 0 |
| 外側の `if false` | 同一 | 未実行 | 0 |
| 外側で block 全体を非実行の heredoc にする | 同一 | 未実行 | 0 |
| canary が失敗する基準 | 同一 | 実行・失敗 | 7 |
| 失敗する canary を外側の `|| true` で包む | 同一 | 実行・失敗 | 0 |

現行の `authority:wiring` は、通常表示の変更も含め、これらの file 差分を保護対象にした。つまり、穴を止める性質と今回の負担の両方を再現した。

## <a id="separation"></a>D の成立条件と残る穴

D は「block を別 file にして、大きな本体から呼ぶ」案ではない。それでは本体の手前の `exit 0` が残る。**外部から最初に呼ばれる入口**が、必須検査を所有する構造である。

1. 最初に現在の義務を列挙する。必須チェックを勝手に「任意の診断」へ降格しない。必須の一覧、実行条件、検査対象、参照先、失敗・欠落時の扱いは、保護された入口または宣言側が所有する。
2. 入口は小さく保ち、file 全体を保護する。起動元の設定、interpreter、helper、参照先、実行属性・symlink も必要な範囲で既存の保護対象にする。agent が入口の手前に別の任意処理を挿入できる配線へ移さない。
3. 変更自由な部分は子 process として実行し、入口へ `source` しない。通常部分の出力を `eval` したり、そこから必須チェックの省略・成功判定を受け取ったりしない。子の `exit 0` は親の必須処理を取り消さない。
4. 必須検査を入口が実際に実行し、失敗・未実行・検査不能を成功として報告しない。子の出力・終了値と必須検査の結果を区別し、最終的な結果は入口が決める。前後どこで何を検査するかは、実操作と診断の役割に合わせて固定する。
5. 別の入口から本体を直接起動したことを、全検査の完了と認めない。実際の編集・commit 等は既存の独立した操作 gate を通す。任意に起動する総合診断だけを唯一の安全境界にしない。

**残る穴:** 同じ OS 権限の子 process は、別 file の改変・親 process への干渉・環境依存の動作をし得る。子 process 化を権限分離とは呼ばない。外部依存・配線の保護、親の異常終了を成功にしない呼出側、実操作直前の独立 gate が要る。実行前の canary が成功しても、その後の設定変更を見ない限り継続的な有効性は証明できない。canary は合成例の診断であり、実操作の許可でも、その操作 gate の代替でもない。

大きな本体を丸ごと移しただけでは D の条件を満たさない。表示 label 等を独立したデータとして扱える場合は負担を減らせるが、実行対象・分岐・失敗の扱いと結び付いた変更は保護内に残る。全ての一文字修正を無審査にできる案ではない。

## <a id="comments"></a>コメントだけの言及の扱い

意味としては、純粋な説明に名前があるだけでは実行配線ではない。しかし **`#` 以降や `#` で始まる行を機械的に落とす案は採らない**。

- 合成例の unquoted heredoc の中では、`# $(python3 ... --canary)` という行でも command substitution が実行された。行頭の `#` だけではコメントと決められない。
- quoted heredoc でも、`sh` に入力したり、後で `source` / `eval` したりする文字列はコードになり得る。単に「文字列だから配線でない」ともしない。
- shebang、authority marker、生成器・外部プログラムが設定として読むコメントは制御情報になり得る。例として、コメントの `gate-path:` を script 自身が読み直して実行する構造では、名前がコメントにしか現れなくても配線を決めている。
- 既存の file lock・manifest・正本参照の保護は、コメント扱いの変更で解除しない。

**今回の推奨は E の一律導入を見送ること。** D の整理に伴い、実行にも生成にも使わない説明は、確認した上で通常の説明文書へ移せる。ただし、従来の全文 lock が消える file は移行対象として本人に示す。E を別途選ぶ場合は、対応言語・純コメントの識別方法・設定コメントの宣言・未対応構文の扱いと、既存 lock の移行範囲を裁定の対象にする。これを通常のコメント掃除に紛れ込ませない。

## <a id="decision"></a>裁定してほしい範囲

**推奨: D を条件付きで採用し、A / B による一般的な block 縮小と E の一律自動除外は行わない。** 小さな入口の全文 lock、既存の操作 gate、独立した他の lock は維持する。移行対象、必須検査の一覧、通常編集が可能になる部分を具体的な候補で示す。まだ採用された設計ではない。

比較の代案は C の継続。A / B / E を選ぶ場合は、上に挙げたどの穴を塞ぐか、どの範囲を未保証として許容するかを、実装前に明示する。設計検討の依頼や agent の推奨を、本人の裁定に置き換えない。

裁定後の検査には、通常部分の変更が通ること、保護内の変更が止まること、守ると決めた早期終了・差替え・失敗の隠蔽が止まることを含める。否定例は拒否理由まで見る。marker を使う案なら重複 ID・不正な入れ子・欠落、E なら引用・heredoc・制御コメント、D なら本体の直接起動・欠落・親の異常終了も対象とする。失う保護と正常例の両方を、変更前に対照を置いて検査し、対応する反例が変更前では赤くなることを確認する。

独立した別 context からも A〜D とコメントの扱いについて批評を受け、marker の曖昧性、保護の足し合わせ、子 process の限界、canary と操作 gate の区別を比較へ反映した。これは採用の裁定でも実装の検品完了でもない。
