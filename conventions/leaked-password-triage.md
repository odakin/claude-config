# 流出したパスワードの使い回しの点検

使っているサービスから「メールアドレスとパスワードを含む会員情報が流出した」 と知らされたときに、 **同じ組を使っている他の先を見つけて、 急ぐ順に変えてもらう** 手順。
パスワードを変えるのは本人の操作で、 agent はパスワードの値を扱わない (入力も、 書き出した file を読むことも)。 agent の仕事は、 調べられることを先に調べ、 順番と入口を渡し、 済んだものを記録すること。

## <a id="verify-notice"></a>1. 通知が本物かを先に確かめる

- 流出のお詫びは偽のメールにも使われる。 メールのリンクでなく、 自分で公式サイトを開いて同じ告知があるかを見る。 送り手のドメインがサービスの本体と違うことがある (実測)
- 通知が求めている操作を読み分ける: パスワードの再設定か、 不審な連絡への注意だけか。 注意だけでも、 使い回した先の点検と続報の確認は残る (次の行)
- 「あなたの情報の流出は確認されていません」 は調査の途中の言い方で、 流出していないという判定ではない。 公式の告知が「影響範囲を調査中」 と言っている間は、 対応不要として閉じない (実測: この一文を根拠に「やることは無い」 と記録した)。 残すもの:
  - 使い回した先の点検 (2 から)
  - 続報を見に行く日 (期限つきの TODO)。 流出した項目 (パスワード・カード・住所) と自分の分かどうかが出たら、 そこで次の手を決める
  - そのサービスで期限のある利用が止まったままなら、 期限より前に別の経路を決める
- 会社が全員のパスワードをリセットしたときは、 古いパスワードでのログインは通らない = ログイン画面からでなく「パスワードを忘れた方」 の手順から入る。 混雑で開かなければ時間を置く (古いパスワードはもう効かないので、 その先は急がない。 急ぐのは使い回した他の先)

## <a id="find-same-password"></a>2. 同じパスワードの先を見つける

- Apple の「パスワード」 アプリのセキュリティの勧告:
  - 赤「漏洩の危険があるパスワード」 = そのパスワードの文字列が既知の流出の一覧にある、 という判定 (サイトごとの判定ではない)
  - 灰「使い回しのパスワード」 = 他の先と同じだが、 流出の一覧には無い
  - 赤は 1 種類のパスワードではない = 弱いパスワードが何種類か混ざる
- **一覧の並び順から「同じパスワードの塊」 を推さない** — 並びが A→Z で切り替わる所を塊の境目と見る仮説は、 境目の前後の項目を本人が開いて見比べると外れた (実測)。 並びから推すなら、 先に境目の両側の数件を本人に確かめてもらう
- 確実な方法は本人の操作で:
  1. 「すべてのパスワードを書き出す」 で CSV を作る。 置き場所は同期されない所 (デスクトップ・書類・クラウドの同期フォルダは避ける)
  2. 表計算で開き、 パスワードの列で並べ替えるか、 その値で絞る
  3. 見終わったらすぐ消して、 ゴミ箱も空にする (全部のパスワードが平文で入っている)
- **agent は CSV を開かない・受け取らない**。 本人に貼ってもらうのは、 サイト名・URL・ユーザ名の列だけ
- ブラウザにだけ保存したパスワードは「パスワード」 アプリに出ない = 別に見る。 どこにも保存していない先は、 メールの登録・ログイン・パスワードの通知を差出人のドメインで束ねると候補が出る (漏れはある = 消したメール・別のアドレスで登録した先)

## <a id="priority"></a>3. 急ぐ順

1. メールの鍵 (メールの account・Apple ID・Microsoft など) — ここを取られると、 他の全部の「パスワードを忘れた」 が乗っ取られる
2. お金が直接動く先 (銀行・証券・カード・送金・決済)
3. カードや住所が載っている先 (通販・予約・配送・携帯の会社)
4. 仕事 (所属のシステム・学会・投稿の system)
5. 自分の名前で発信できる先 (SNS・ブログ) — 乗っ取られると人に迷惑がかかる
6. 残り (店・趣味・古い登録) — 次に使うときに変えるか、 退会する

- 二段階認証・パスキーが必須の先は、 パスワードだけでは入られにくい (それでも変える)。 パスキーにできる先は、 パスワードを消してパスキーだけにするのが一番強い
- 急ぐ順の一覧は、 本人が保存アプリで引く語 (多くは URL のドメインの一部) と一緒に渡す。 項目は銀行名やサービス名でなくアドレスで登録されていることが多く、 名前で検索すると出ない

## <a id="precheck-before-asking"></a>4. 開いてもらう前に agent が調べる

- 本人にサイトを開いてもらう前に、 agent が調べられることは先に調べて、 まとめて伝える (実測: 終わったサービスの入口を本人に探させた)。 調べるのは:
  - 保存の host の名前解決と応答 (`dig +short` / `curl -o /dev/null -w '%{http_code}'`)
  - その送り手から最後にメールが届いた日
  - これで「終わっている」「何年も使っていなさそう」「今も使っていそう」「メールでは分からない」 に分けて渡す。 最後のメールの日付は目安 (お知らせだけ届く先もある)
- 保存の項目には古いものが多い = パスワードがもう変わっている・退会している・サービスが終わっている (実測)。 **漏れたパスワードで入れなければ、 その先は済み** として印を付ける
- **使い回しの先が分かったら、 その送り手からの直近数週間のログイン・パスワードの通知を引く** (「新しいログイン」「サインイン」「ログインコード」「パスワードの変更」 の件名):
  - 心当たりの無いログインがあれば、 その先を最初に変える。 心当たりは時刻と場所を添えて本人に 1 問で確かめる (本人のログインかどうかを agent が推さない)
  - その先の前のパスワード変更の通知があれば、 保存の項目が古いだけ = 漏れたパスワードはその先ではもう使えない (実測)
- 開かない保存先の型 (先に言っておく):
  - `www.` の無いアドレス (本体が `www.` 付きの名前にしか無い)
  - スマホのアプリから保存した項目 (`com.…` / `jp.co.…` の形) = Web のアドレスではない → そのサービスの公式サイトのアカウント管理から入る
  - 名前の変わったサービス (アドレスは前のままのことがある)、 会員サイトが移ったカード (今の入口は、 その会社から届く請求の通知に書いてある)
  - 会社の紹介サイトは、 アカウントの入口ではない

## <a id="lockout-and-codes"></a>5. 止まる・漏れるのを防ぐ

- 古い項目の自動入力で何度も失敗すると、 銀行などはログインを一時的に止める (実測)。 失敗が続いたらそれ以上試さず、 時間を置いてから公式の再設定の手順へ。 古い項目は消す (次の自動入力の誤りの元)
- 二段階認証の復旧コード (バックアップコード) が chat や画面の写しに出たら、 作り直してもらう (前のコードは使えなくなる)。 新しいコードは本人が file に置き、 agent は中身を読まずに暗号化された置き場へ移して、 所在と作り直しの手順だけを書く ([`secret-handoff.md`](secret-handoff.md))
- 点検の記録はサービス名と状態だけにする (ユーザ名・口座の ID・パスワードを写さない)。 本人が「変えた」「入れない」 と言うたびに印を付け、 残りの段を言う
