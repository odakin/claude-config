# 航空券の候補調べ (内蔵 Browser pane)

**Load this when**: 出張の航空券の候補を調べて比べる表を作るとき。 予約・支払い・個人情報の入力は agent がしない
(本人が行う) 前提で、 **本人がすぐ予約できる候補**を用意するまでを扱う。

経路の選び方の一般則は [`machine-route-first.md`](machine-route-first.md)、 ブラウザ操作の癖は
[`web-tools.md#browser-pane-input-quirks`](web-tools.md#browser-pane-input-quirks)。 本 file は航空券という対象に固有の機構だけを持つ。

## <a id="url-driven-search"></a>入口 = URL だけで検索結果まで開けるサイト

- **Kayak** と **Expedia** は URL に出発地・到着地・日付を入れるだけで結果画面まで開ける (実測)。
  URL は [`scripts/flight-search-urls.py`](../scripts/flight-search-urls.py) が作る (往復・大人 1 名・エコノミー。 それ以外の書式は未実測なので作らない)。
  ```bash
  python3 scripts/flight-search-urls.py NRT CDG 2027-03-01 2027-03-08 --kayak-filter alliance=STAR_ALLIANCE
  ```
  - Kayak の `fs=` 絞り込みで効いたもの (実測) = `alliance=STAR_ALLIANCE` / `airlines=<2 字 code>`。 都市 code (`TYO` = 東京の全空港) も通る。
  - Expedia は結果画面左の「航空会社」 欄で絞る。
- **航空会社の公式サイト**は検索の前に bot 判定を置いていることが多い (実測: 長押しで人間確認 / Cloudflare の確認画面) = 入口にしない。
  比較サイトで候補を絞ってから、 本人が公式で予約するかを決める。
- 航空会社の国際線予約でも、 提携便を含む行き先は選べるのに検索がシステムエラーで返ることがある (実測)。 1 回の error で「組めない」 と結論しない。

## <a id="google-flights-form"></a>Google フライトの入口 = 英語の決まった形の URL か、 入力欄の操作

- **`?q=` に英語の決まった形を入れると結果画面まで開ける** (実測): `https://www.google.com/travel/flights?q=Flights%20to%20<着 code>%20from%20<発 code>%20on%20<YYYY-MM-DD>%20through%20<YYYY-MM-DD>&hl=ja&curr=JPY`。 発着は都市 code (`TYO`) でも空港 code でも通る。 URL は [`scripts/flight-search-urls.py`](../scripts/flight-search-urls.py) `--site google` が作る。
  日本語の文や、 航空会社名を末尾に足しただけの英文 (「… Turkish Airlines」) を入れると、 **条件は入らず初期画面になる** (実測)。
  **1 社に絞るなら、 決まった形の末尾に `%20on%20<航空会社の英語名>` を続ける** (実測: `… through <日> on Turkish Airlines` のように 3 社で試し、 どれもその会社を含む便だけの結果が開いた。 道具の `--google-airline`)。 決まった形で開けないときは、 入力欄を 1 つずつ操作する:
  1. 出発地の欄を click → 候補一覧から選ぶ (欄に文字が残っていると、 `cmd+a` では選択されず追記になる 〔実測〕)
  2. 目的地の欄に英語の都市名を type → 候補の空港を click
  3. 往路の日付欄に `YYYY/MM/DD` を type → Tab → 復路も同様 (カレンダーを click で送るより確実。 月送りの連打は画面の月と click 先がずれる 〔実測〕)
  4. カレンダー下の「完了」 → 「検索」
- 検索後の `location.href` は `tfs=` 付きの URL になり、 これは開き直せる。 Claude in Chrome の `javascript_tool` は query つきの URL を返さない (実測: 返り値が伏せられる) = 人に渡すのは `?q=` の URL と、 そこで選ぶ行 (時刻と経由地) にする。
- 一覧は上の数件しか出ない。 「他のフライトを見る」 を押してから、 `javascript_tool` で行を抜く (`[...document.querySelectorAll('li')].map(li => li.innerText.replace(/\n+/g, ' | ')).filter(t => /往復/.test(t))`)。 湾岸の会社など除きたい航空会社は、 抜いた後に名前で外す。
- 往路の行を click すると、 **その往路と組める復路の一覧**に進む (実測)。 合計の価格は復路の選び方で変わる = 往路の一覧の価格は「最安の復路と組んだ値」 と読む。
- 結果の頁は大きく、 `find` (自然文で要素を探す tool) は入力が長すぎて落ちる (実測)。 行は `javascript_tool` で `li` を文字で選び、 `scrollIntoView` の後の `getBoundingClientRect()` の中心に、 screenshot の座標の幅 ÷ `innerWidth` を掛けた点を click する。
  「他のフライトを見る」 は読み込みが落ち着いてから押す = 落ち着く前は行が動き、 click が便の行に当たって復路の一覧へ進んでしまう (実測)。
- **複数社を乗り継ぐ路線では結果が他サイトより極端に少ないことがある** (実測: 他サイトで数十件出る条件で 1 件)。
  アライアンスで絞って 0 件でも、 別サイトでは同じアライアンスの乗継便が出る = 1 サイトの 0 件で不在と結論しない。

## <a id="bot-checks"></a>CAPTCHA・人間確認は押さない

- 比較サイトも数回検索すると reCAPTCHA が出る (実測: Kayak で数回目)。 **押さず、 そのサイトはそこで止める**。
- 別サイトに移るのは突破ではないので続けてよい。 ただし比べる表の冒頭に **使えた経路 / 使えなかった経路 (何で止まったか)** を書く
  (= 読み手が「このサイトでは見ていない」 を知る。 Turnstile 等の一般則 = [`web-tools.md#browser-pane-input-quirks`](web-tools.md#browser-pane-input-quirks))。

## <a id="reading-results"></a>結果の読み方

- `get_page_text` は広告ブロックと重複した案内文で数倍に膨らむ。 **件数・価格・乗継だけ欲しいときは `javascript_tool` で本文から切り出す**。
- **便名・運航会社・運賃種別 (返金可否・変更手数料・預け荷物) は結果一覧に無く、 dialog の中にある** (Expedia で実測)。
  便を click して運賃種別の panel を開き、 「フライトの詳細」 button (aria-label が「…のフライトの詳細を表示します」) を押してから読む:
  ```js
  [...document.querySelectorAll('[role=dialog], [aria-modal=true]')]
    .map(d => d.innerText.split('\n').filter(s => s.trim()).join(' | '))
  ```
  往路の運賃種別の「選択」 は復路の一覧に進むだけで、 取り消しにくい操作ではない。
- **アライアンスは運航会社で判定する**。 A 社の便名でも「運航会社 : B 社」 のコードシェアがある (実測)。 一覧の「複数の航空会社」 は 1 枚の航空券で組んだ乗継。
- **乗継空港のターミナル移動**を見る。 乗継時間が同じでも、 ターミナルを移る乗継は短いと危うい。
- **出発地を都市 code で引くと、 国内線の区間を前後に付けた 1 枚の券 (国内の別の国際空港から出る便) も並ぶ**。 首都の空港から出る便より安く、 経由地での待ちも短いことがある (実測: 同じ航空会社の首都発より約 3 割安)。 帰りの国内線への乗り継ぎは、 最初に着いた国内の空港で入国と税関を通る。
- **同じ条件でもサイトごとに価格が数千円ずつ違う** (実測)。 2 サイト以上で突き合わせ、 **見た時刻 (現地時刻) を価格と一緒に**書く。
  価格は時間で変わるので、 表の値は「その時刻に画面で見た値」 以上の主張をしない。
- 同じ運賃種別の変更手数料が、 一覧の panel と旅程確認画面で違う額で出ることがある (実測)。 両方を書き、 どちらかに丸めない。

## <a id="stop-before-personal-info"></a>止まる所 = 個人情報を入れる直前

- Expedia の流れは「航空券 → 座席 → お支払い」 (実測)。 往路・復路の運賃種別を選ぶと **旅程を確認する画面** (合計料金・運賃種別の条件) に着く。
  ここが agent の止まる所。 次の段 (座席・旅行者情報・支払い) には進まない。
- 候補表には「どの画面まで確かめたか」 を書く (「支払い画面の手前まで」 / 「一覧の価格だけ」)。

## <a id="fare-breakdown"></a>運賃・燃油・税の内訳は確認画面に出ない

- 旅程確認画面は **税・手数料込みの合計だけ**で、 運賃・燃油サーチャージ・空港税の内訳は出ない (Expedia で実測)。
- 旅費補助が内訳の分かる書類を求める場合、 予約前にその書類がどこで出るか (確認メール / 航空会社の e チケット控え) を確かめる段取りを候補表に書く。
- 旅行サイト (Booking.com) では、 **サイトの「予約内容」 から落とす PDF に「運賃」 と「航空会社の税・手数料」 の 2 行の内訳が出た** (実測)。 燃油サーチャージと空港税は分かれず、 税・手数料の行にまとめて入る。 燃油を分けた内訳が要るなら航空会社の予約管理の e チケット控えを当たる (出るかは未実測)。 確定メール 2 通には合計だけで内訳は無かった (実測、 [#confirmation-documents](#confirmation-documents))。
- 補助によっては**見積では足りず、 確定金額が分かる書類 (予約確認・予約完了画面) を求める**。 その場合の予約の期限は補助の応募締切から逆算する。

## <a id="hold-before-payment"></a>支払い前に予約だけできるかを前提にしない

- 比較サイトの旅程確認画面までに「支払いせずに保留」 の選択肢は見えなかった (Expedia で実測。 支払い画面より先は見ていない)。
- 旅行サイトの支払い画面まで進んでも、 ボタンは「今すぐ支払う」 だけだった (Booking.com で実測)。
- 航空会社公式の保留機能は、 bot 判定で公式サイトを読めないと確かめられない。
- ∴ 「保留して書類だけ先に出す」 段取りは、 保留が画面で確かめられた経路でだけ組む。 確かめられなければ、 予約と支払いが同時の前提で払い戻し条件を並べる。

## <a id="itinerary-vs-travel-request"></a>出張の申請書に日付・経由地を書く前に便を引く

候補の便は、 申請書に先に書いた日付や経由地と次の形でずれうる:

- **0:05 発のような深夜便**は、 券面の出発日が申請書の日付と同じでも、 実際には前日の夜に家を出る。
  逆に「X 日の夜に出る」 つもりの便は、 券面では X+1 日発になる。
- 深夜発・早朝着の乗継で、 **到着日が申請書より 1 日早い / 遅い**便が最安になることがある。 到着が早まると宿泊が 1 泊増える。
- 同じアライアンスで組むと、 経由地域 (中東 / 東アジア / 欧州) が申請書に書いた地域と変わることがある。

∴ 申請書 (出張願・日程表) を書く前に、 候補の便を先に引いて日付と経由地域をそれに合わせる。
既に出した後で候補がずれるなら、 予約の前に事務へ「変わる可能性がある、 確定したら変更点を知らせる」 と伝え、
予約確認を出すときに変更点を書き添える。

## <a id="self-transfer"></a>「自己乗り継ぎ」 は別々の航空券 = 最安値に混ざる

- Google フライトは、 別々の航空券をつないだ組み合わせに **「自己乗り継ぎ」** と表示する (乗り継ぎ地で荷物を受け取り直し、 前の便が遅れても次の便は振り替えられない)。
- **「最安値」 タブの上位は自己乗り継ぎばかりになることがある** (実測: 上位が全部自己乗り継ぎ)。 結果画面の絞り込みで**自己乗り継ぎを非表示**にできる (実測) = 比べる価格は非表示にした後の値にする。
- **同じ便の組み合わせが、 自己乗り継ぎ版と 1 枚の航空券版の両方で出る**ことがある (実測: 価格差は 1% 未満)。 便名と時刻が同じでも表示を確かめる。 旅行サイトの一覧には自己乗り継ぎの表示が無いことがあるので、 Google フライトで表示を見てから旅行サイトで買う。
- **複数都市 (往路と復路で東京の空港を変える等) で検索すると、 往復検索では出る航空会社の組み合わせが 1 件も出ない**ことがある (実測)。 往復検索の結果と比べる。
- 日付グリッド・カレンダーの安値に自己乗り継ぎが含まれるかは未実測 = 安い日を見つけたら、 その日付で一覧を開いて表示を確かめる。

## <a id="booking-channel"></a>予約先 = 比較サイト経由と直接で値段が違う

- Google フライトの「予約オプション」 に**航空会社公式が出ない**ことがある (実測: 旅行サイト 3 社だけ)。 公式サイトで同じ便を直接検索すると、 比較サイトより安いことがある (実測: 別の空港の組み合わせで約 4% 安い)。 公式サイトは curl だと bot 判定で 403 になるが、 本人のブラウザでは普通に検索できる (実測)。
- **同じ旅行サイトでも、 Google フライトの予約オプションから入ると、 サイトを直接開いて検索するより安い**ことがある (実測: 約 2%)。 直接開いて高く出たら、 比較サイトの予約オプションから入り直す。
- 予約オプションに航空会社公式の行があると、 **運賃の種類ごとの値と条件 (変更・払い戻し・預け荷物) が並ぶ** (実測)。 補助の申請額のような上限があれば、 上限に収まる中で条件の良い種類を推し、 上限から逆算した境の値も書いておく = 同じ便の全種類が 30 分で一律に約 5% 動いた (実測)。 手数料の額はここに出ない (公式の購入画面の運賃規則で見る)。
- 旅行サイトの行の上に「受託手荷物は 1 個目から有料」 と出る運賃がある (実測) = 安さは荷物代を足して比べる。 航空会社公式の値が「価格は正しくない可能性があるため非表示」 になることもある (実測)。
- Booking.com の航空券は、 支払い画面の契約条項で**予約サービスの提供元が別の旅行会社 (Gotogate International AB)** と明示される (実測)。 変更・払い戻しの窓口はそちらになる。
- 旅行サイトは払う前に、 **有料の追加を段ごとに足していく** (実測: 日程変更できるチケット / 空港の優先レーン / 座席指定。 座席は区間ごとに有料で、 全区間を選ぶと航空券の 1 割近くになる)。 **支払い画面の「料金の詳細」 で追加の行を 1 行ずつ読む**。 本人が選んだつもりの無い追加が入っていることがある (実測)。 座席は後から航空会社の予約管理やオンラインチェックインでも選べる。
- 追加 (優先レーン等) は運賃・燃油・税ではないので、 旅費補助の対象外になりやすい (制度次第)。

## <a id="connection-not-sold-by-airline"></a>航空会社公式が組まない短い乗継を、 旅行サイトが売っていることがある

- 旅行サイトで売られていた「国内線 → 国際線、 同じ空港でターミナルを移る約 2 時間の乗継」 を、 **その国際線の航空会社の公式サイトは組まなかった** (実測)。 公式は同じ出発便から、 乗継地で夜を越して 1 日遅く着く組み合わせだけを出した。
- 公式が組まない乗継は、 乗継時間が航空会社の目安より短い可能性がある (推定)。 旅行サイト側が別々の航空券をつないでいるのかは、 買う前には画面で分からないことがある。
- **買った後の確かめ方** = 詳細メール (e チケット番号の出るもの) で、 **全区間の e チケット番号が 1 つ** (連番の枝番を含む) なら 1 枚の航空券 (実測)。 区間ごとに別の番号なら別々の航空券で、 乗り遅れの振り替えは保証されない。
- 買う前に分かるのは、 比較サイトの「自己乗り継ぎ」 表示 ([#self-transfer](#self-transfer)) と、 旅行サイトの便の詳細・支払い画面に「別々の航空券」「手荷物を受け取り直す」 の注意が無いか、 まで。

## <a id="route-over-conflict-areas"></a>紛争地域の上空を避けたいときは、 実際の航跡で確かめる

- 経由地の空港だけでなく、 **乗継の前後の区間の上空**も見る。 経由地を変えても、 その先の区間が避けたい地域を横切ることがある (地図の上では、 湾岸のハブから地中海側への区間は半島の上空を通る)。
- 航空会社や地図からの推測で決めない。 **FlightAware の track log** で、 同じ便名の最近の 1 便の実際の位置を読む (ログイン不要、 実測):
  1. `https://www.flightaware.com/live/flight/<ICAO の便名 = 航空会社の 3 字 code + 番号>` を開き、 `a[href*="/tracklog"]` の link を拾う
     (形 = `/live/flight/<便名>/history/<YYYYMMDD>/<HHMM>Z/<発 ICAO>/<着 ICAO>/tracklog`。 日付を 1 日ずらせば前日の便も読める)
     区間の便名が分からないときは `https://www.flightaware.com/live/findflight?origin=<発 ICAO>&destination=<着 ICAO>` を開き、 数秒待ってから表を読む (後から埋まる表、 実測)。
     history の一覧の最新の行はまだ飛んでいない便のことがある (点が 0 = 次の行を読む)
  2. track log の表の行 (時刻・緯度・経度) を `javascript_tool` で抜き、 避けたい国の経度の帯で緯度の範囲を見る。
     緯度・経度の cell は値が重なった文字を持つ = cell の最初の `span` を読む (cell の文字のままだと `35.744335` のように桁が重なる、 実測)。
     何便も読むときは flightaware.com の頁の上で `await fetch('/live/flight/…/tracklog').then(r => r.text())` を `DOMParser` に通すと、 頁を移らずに読める (実測)
  3. 受信の届かない海や砂漠の上は記録が途切れる = 途切れの前後の点から判断し、 途切れていることを書く
- 読めるのはその日の 1 便だけ = 「確かめたのは往路の 1 日分」 のように範囲を書く。 日や管制で経路は変わる。
- 実測の例 (経路の目安): 東アジア ⇄ トルコの便は中央アジア・カスピ海・コーカサスの上 (北緯 40〜44 度) を通り、 イランの上空は通らない。
  東アジア ⇄ 北アフリカの直行便と、 中国 ⇄ 北アフリカの便も、 カスピ海・コーカサスからトルコを南へ抜けて地中海に出る (直行便はシリア国境のすぐ北を通った)。
  東アジア → アフリカの角の便はインドからアラビア海に出て、 アデン湾の中ほど (両岸から約 180 km) を通る。 アフリカの角 → 北アフリカの便はエリトリアと内陸の国の上空を通る。
- 経路が分かったら、 外務省の危険情報 (国ごと・地域ごとのレベル) と、 航空当局の紛争地域の注意情報 (EASA の CZIB など) で、 通る国と海を当てる (読み方と道具 = [#route-risk-official-sources](#route-risk-official-sources))。

## <a id="route-risk-official-sources"></a>経由地・上空の危険を、 公式の情報と航空会社の運休で読む

- 外務省の海外安全ホームページは WebFetch を拒む (403、 実測)。 同じ中身は公開データの国ごとの XML にあり、 [`scripts/mofa-anzen-opendata.py`](../scripts/mofa-anzen-opendata.py) `<国番号>` が危険レベル・最終変更・領事メールと広域情報の一覧を 1 回で出す (国番号 = 電話の国番号を 0 で 4 桁に、 本文 = `--show <語>`、 根拠に使うなら `--save-dir` で保存)。
  - 段の値だけで決めない。 段が変わらないまま、 大使館・総領事館が在留邦人に在留状況の調査 (「万が一の事態に備え」) を回すことがある = 退避の段取りの前段 (実測)。 道具は ❗ を付ける。 調査が出ている国と出ていない国を並べると、 政府がどこを心配しているかが分かる。
  - 段は地域ごとに違う。 行き先の都市の段は、 危険情報の本文の「地域別情勢」 で確かめる (`--show 危険情報`)。
- EASA の紛争地域の注意情報 (CZIB) は、 一覧の頁 `https://www.easa.europa.eu/en/domains/air-operations/czibs` が WebFetch で読め、 有効なものと期限が並ぶ。 個々の頁の URL は bulletin ごとに書き方が違う (`czib-<年>-<番号>-r<版>` と `czib-<年>-<番号>r<版>` が混在、 推測した形は 404 = 実測) = 一覧の頁から link を拾う。
  - 期限 (valid until) は延長されることが多い。 出発の前に、 延長されたか・取り下げられたかを見直す。 一覧に無い国・海が安全だという意味にはならない (載っていないのは、 EASA がその空域に bulletin を出していないというだけ)。
  - 「その FIR の海の上は飛ばない、 FIR の中の空港の発着は可」 の形では、 経由地のハブへの発着は続けられ、 周りの海の上が避ける対象になる。 発着と上空を分けて読む。
- 航空会社の運休の延長・再開 (いつまで止めるか) はお金の動きで、 声明より重い。 同じハブに、 再開した会社と翌年まで止める会社が並ぶことがある = 1 社でなく一覧で見る (ハブの地元紙の「どの会社が飛んでいるか」 の記事が一覧を持つ)。
- 体に危害が及ぶ見込みと、 足止め (欠航・空港の閉鎖・帰りの便が成り立たない) の見込みを分けて書く。 前者が低くても後者が高いことがある (実測)。

## <a id="split-ticket-to-hub"></a>地方の空港までの通しの券は高いことがある = 首都までの往復 + 国内線

- 国内線の先の地方空港まで 1 枚で買うと、 首都の空港までの往復と国内線を別々に買うより大きく高いことがある (実測: 1.5 倍以上)。 比べるときは両方を引く。
- 別々に買うと**自己乗り継ぎ** ([#self-transfer](#self-transfer)) になる = 国際線が遅れて国内線に乗れなくても振り替えられない。 首都で半日以上あけるか、 首都で 1 泊する。
- 国内線は、 朝の便だけの安い会社と 1 日数便の会社がある。 国際線の着く時刻の後に飛ぶ便で値段を見る (朝の便だけが安い、 実測)。
- 決めた便の組みのまま 1 枚にできるかの確かめ方 = 次の節。

## <a id="through-ticket-check"></a>決めた便の組みを 1 枚の券 (通しの運賃) にできるかを確かめる

国際線の会社 (A 社) と国内線の会社 (B 社) の便を別々の券で組んだ後に、 同じ便の組みを 1 枚にできるかを見る手順。 見る先は A 社の公式・B 社の公式・ITA Matrix の 3 つ。

- **A 社の公式で、 行き先を国内線の先の空港にして往復を引く**。 通しの券に載る国内線の区間は、 **A 社の便名を付けた共同運航便だけ**のことがある (実測)。 B 社の便名の区間を含む組みはエコノミーが「満席」 でビジネスだけが出る一方、 B 社の自社サイトでは同じ便にエコノミーの値が出ていた = 便が満席なのでなく、 通しの券に載せるエコノミーの枠が閉じていると読める (運賃規則は見ていない)。 欲しい時刻の国内線に A 社の便名が付いていなければ、 A 社の公式では通しで買えない見込み (旅行サイトが同じ組みを 1 件で出していても、 別々の券をつないだものかは [#connection-not-sold-by-airline](#connection-not-sold-by-airline) の確かめ方で見る)。
- **航空会社公式の往復の一覧の値は片道ごとのことがある** (実測)。 往路・復路の行の値を足したものが合計で、 両方を選んだ後に画面下の合計欄に出る (旅行者情報の画面に進まなくても出る)。 Google フライトの往路の一覧の値は往復の値 ([#google-flights-form](#google-flights-form)) = 読み方が逆。 一覧の値を往復の値と読むと、 合計を半分に見誤る。
- **A 社の公式の複数都市の検索は、 国内線と国際線の間で一晩あける形を断ることがある** (実測: 「この日程では複数都市のフライトは利用できない」 の旨)。 往復の候補にも出ない。 乗り継ぎ時間の上限に掛かると見られる (推測)。
- **B 社の公式は、 B 社が飛ばない空港を出発地に選べず、 A 社の便を含む組みも出さないことがある** (実測)。 B 社の公式で 0 件でも、 通しの券が無いとまでは言えない = A 社の公式と Matrix も見る。
- **ITA Matrix** (`matrix.itasoftware.com`、 ログイン不要) で、 公開運賃で通しに組めるかを見る (売り場ではない):
  - Multi City で区間ごとに「Show Advanced Controls」 → Routing Codes に便名を空白区切りで書く (`AA123 BB456`) と、 その便の組みに絞れる。 航空会社の code だけ (`BB`) なら、 その会社の便を 1 本 (実測)。
  - 0 件なら「Only show flights and prices with available seats」 を外して引き直す。 外して出れば席が無い、 外しても 0 件なら公開運賃では組めない (実測)。 確かめに、 国際線の区間だけを同じ書き方で引く = 出れば書き方の誤りではない。
  - 便名で絞っても、 後の区間の日付は固定されない (翌日着の組みも並ぶ) = 着の日付を読んで、 決めた日付の行を拾う (実測)。
  - 手で組んだ `?search=` の URL は、 読み込みが終わらないことがある (実測)。 検索の画面の「Recent Searches」 の chip で前の条件を form に戻し、 欄を直して検索する。 Multi City の form は、 日付を入れた区間が日付順に並び替わることがある = 入れ終えたら `javascript_tool` で欄の値を読み直す (実測)。
  - Matrix の値は公開運賃で、 航空会社の Web の運賃より大きく高いことがある (実測: 同じ便で 1.5 倍以上)。 旅行会社に通しの見積もりを頼んでも、 公開運賃で組めば Web より高く出る見込み (旅行会社の独自の運賃は別)。 頼むなら、 営業日と返事までの日数の間に Web の値が動くことも比べる。

## <a id="ota-cancel-refund"></a>旅行サイトで買った券のキャンセル・変更は、 その旅行サイトの画面と窓口だけ

- Booking.com の航空券は、 予約ページの「キャンセルの選択肢を確認」 で **「今キャンセルすると〇〇円の返金」** が出る (実測)。 その画面の赤い「この予約をキャンセルする」 は押した時点で往復ともキャンセルになる = 返金額を読むだけで押さない。
- 返金額が出発の何日前までで変わるかの表は、 旅行サイトにも発券元にも公開されていなかった (実測) = 知りたければ窓口に聞く。 乗らずに出発を迎えると (no-show) 返金が大きく減るのが普通 (航空会社の運賃規則による、 個々の券で確かめる)。
- 航空会社の予約管理は予約番号と姓で開けるが、 旅行サイトで買った券は「オンラインでは変更できません。 旅行会社にお問い合わせください」 と出た (実測)。 開いたときに出る「Eメールアドレスを追加」 の dialog には入力しない (予約の連絡先が変わる)。 cookie の確認は「設定」 から必要なものだけを残して閉じる。
- 取消料 (支払額 − 返金額) をどの財源が持つかは、 取消の前に決める = [`research-email.md#split-by-expense-item`](research-email.md#split-by-expense-item) の「取消料」 の段。

## <a id="confirmation-documents"></a>旅費補助に出す書類 = 確定メール・詳細メール・予約内容 PDF・領収書

旅行サイト (Booking.com) の場合 (実測):

| 書類 | 届き方 | 中身 |
|---|---|---|
| 予約確定メール | 支払い直後 | 照会番号・**暗証番号**・便・合計金額。 内訳・e チケット番号・航空会社の予約番号は無い |
| 予約内容の詳細メール | 確定メールの約 10 分後 (「1 時間以内、 最大 72 時間」 と書かれている) | e チケット番号・航空会社の予約番号・荷物。 金額は無い |
| サイトの「予約内容」 PDF | 本人がサイトから落とす | 便・搭乗者・荷物・**運賃と税・手数料の 2 行の内訳**・合計・連絡先・**暗証番号** |

- 「詳細メールは来ていない」 と答える前に、 確定メールからの経過時間を見て検索し直す (確定直後に見て「未着」 と言うと、 数分後に届く)。
- **暗証番号 (PIN) は予約の変更に使える秘密** = 事務に出す写しでは塗る。 文字層から消えたかまで確かめる = [`scripts/pdf-redact-text.py`](../scripts/pdf-redact-text.py) (上に黒い四角を描くだけだと、 下の文字を抽出で読める)。 HTML メールを PDF にするときは保存 HTML を [`scripts/html-print-pdf.py`](../scripts/html-print-pdf.py) に通し、 暗証番号は PDF にする前の HTML で伏せてもよい。 本文を text で取ったメール (API で落とした本文・ヘッダつき) は [`scripts/mail-to-pdf.py`](../scripts/mail-to-pdf.py) `--redact '<正規表現>'` で、 伏せてから PDF にする (日本語可。 伏せた件数が出るので 0 なら書式違いを疑う)。
- <a id="quote-mail-as-document"></a>**「宿泊先と金額が分かるもの」 のような書類の指定は、 宿・旅行会社からの見積メールで足りることがある** (実測) = 正式な見積書・請求書を催促する前に、 **届いているメールをそのまま担当へ転送して「これで足りるか」 を聞く**。 足りなければそこで正式書類を頼む (= 催促の往復と待ちを 1 回省ける)。 宛名が申請者本人のメールであることが効く。
- **サイトを日本語表示にして落とした PDF は、 項目名 (運賃・税・手数料) が豆腐 (□) で読めなかった** (実測: 和文 font が埋め込まれていない)。 金額だけ並んで何の額か分からないので、 **サイトを英語表示に切り替えて落とし直す** (実測: 項目名が読める)。 出す前に PNG にして目で見る。
- 出す書類がそろったら、 暗証番号入りの原本 (ダウンロードフォルダ等) と塗った写しを取り違えない = 写しの file 名に塗ったことが分かる語を入れる。
- <a id="evidence-that-expires"></a>**後から取れなくなる証憑は、 交通手段が決まった時点で頼む** (自分の出張でも、 招いた講師の旅費でも)。 e チケットの控えは、 搭乗した後では出してもらえないと事務に言われた (実測。 航空会社・旅行サイトで違いうる) = 買ったときの確定メール・控えを印刷か PDF で保存してもらう。 搭乗証明書は逆に搭乗の後にしか取れない (帰りの便の分は帰着後) = 何をいつ取るかを分けて伝える。 当日の案内に「控えをお持ちください」 と書くだけでは、 搭乗の後に気づいても取れない。
- **日当は出発・帰着の時刻で額が変わる規程がある** (例 = 午後出発・午前帰着は半額)。 日程表の時刻を目安で書いて出したら、 便が決まった時点で本人に時刻を聞いて直す。
- <a id="payment-proof"></a>**領収書と、 支払った円の額の証明** (実測):
  - Booking.com の航空券の領収書は、 予約ページ下の「フライト・ヘルプセンター」 → 「支払い」 → ライブチャット (発券元の旅行会社が対応) で頼むと、 数分で「法人向け領収書」 (invoice) がメールで届く。 宛名・会社名・住所・VAT 番号は入れられるが、 **発行日と支払日は入らない** = 支払日はカードの利用明細で示す。
  - カードの利用明細は、 他の利用を見せずに 1 行だけ出せる形にする。 三井住友カードの Vpass は「印刷用ページ」 で行ごとに「非表示」 に✓を入れられる (隠した行と合計は「＊」 になる、 公式の機能) → 印刷を PDF に保存。 印刷用ページは popup なので、 内蔵 Browser pane では agent の click からは開かず (本人が押す)、 popup が開いている間は agent の script が止まる。
  - 送金サービス (Wise) で外貨を払った分は、 アカウントの送金から「送金証明書」 の PDF が取れる。 1 頁目に入金した円・手数料・換算レート・送った外貨が出る。 2 頁目以降 (受取人の口座・SWIFT 電文) は精算に要らない = 1 頁目だけ出す。
  - 事務に「〜を依頼していますので、 届き次第お送りします」 と書いて先にそろった書類を送るのは、 依頼を実際に出してからにする (出していない依頼を「しています」 と書かない)。

## <a id="window-side"></a>景色を見るなら日陰側の窓

- 夜の区間は窓の左右を気にしない。 昼の区間は、 進む方位と時刻から太陽の側を見て、 **反対 (日陰) 側**を選ぶと、 まぶしさがなく地上が順光で見える (北半球の冬の昼は太陽が南寄り = 東へ飛ぶなら左、 西へ飛ぶなら右。 午後に南へ飛ぶなら東側 = 左)。
- 実際の経路と着陸方向は風と管制で変わるので、 目安以上に言わない。
