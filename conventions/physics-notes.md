# 物理・数理ノート規約 (odakin 流)

> **位置づけ**: これは本リポ維持者 (odakin) が「自分の関わるノートでは常にこれで行く」と宣言している**個人の流儀**であり、共著者や他の利用者が従う義務はない。コラボごとに書き散らさず全プロジェクト横断で一貫させるために最上位 (公開層) に置いてある。Claude は odakin のノートを書く・改稿するときにこの規約を適用する。同様の流儀を採りたい人への参考としても公開しておく。

物理・数理の導出ノート (LaTeX/PDF/md、共同研究の note・解説・手検算 reference) を書く・改稿するときの規約。5 つのルールはいずれも「後から取り違える経路を構造的に塞ぐ」ためのもの。

## 1. 脚 (添字) は常に全部顕に書く

**ルール:** 数式で添字を省略しない。inline shorthand (`hG⁽¹⁾h`、`C⁽¹⁾C⁽¹⁾`、`êΓê`、`δ²S/δêδê` の類) を書かず、縮約と functional derivative は添字を全部書く:

- `h^{µν} G⁽¹⁾_{µν}`、`C⁽¹⁾_{µνρσ} C⁽¹⁾^{µνρσ}`、`ê_{bν} Γ⁽²⁾_{(bν)(cρ)} ê_{cρ}`、`δ²S/(δê_{bν} δê_{cρ})`
- worked example・boxed 主結果・付録も例外なし
- 表示数式 (display) を使う。inline に押し込むと省略する圧力が生まれる

**Why:** 省略した脚を後から「復活」させるときに、反対称化重み (1/3!、2!)・対称化の ½・mode の規格化・Taylor の ½ (Γ = δ²S) と field rescale の組合せを取り違えるのが定番事故。kernel-level と action-level の係数取り違えも省略簿記から生じる。読者 (共著者・未来の自分) の追計算の最大障壁も省略形の再構成コスト。

**How:**
- 数式を書いた直後に「省略された縮約・脚はないか」を 1 周 scan し、あれば display で書き下す
- 組合せ重み (1/k!、射影子ノルム、½) が絡む等式は、数値検証 (numpy 数行) を 1 本添えて regression 化する

**事例 (一般化):** 添字を省略した quadratic form から係数を読んだノートで、5 つの係数が単一の規約で読めない混在 (項により ×4 / ×2 のズレ) になっていた。全添字化にともなう機械検証で、「この mode は他の射影子に消される」と書いた前提が実は二次形式直交でしか成立しない箇所 (off-diagonal 射影子は operator としては消さない) も発見された。省略形のままでは両方とも見えない。

## 2. 規約表のセルは「宣言の引用」か「推定の明記」のどちらか

**ルール:** 他者・他文書の規約 (signature・Fourier・質量符号・規格化・括弧の重み等) を表やノートに記録するときは、各セル/各主張について:

- (a) 一次資料の**明示的な宣言** (式番号・節・ページ) を引用する、または
- (b) 式形からの**推定**なら「inferred from …」と明記して根拠を添える

のどちらかにする。推定セルを事実の顔で再利用・転載しない (再利用する前に一次資料の宣言を確認する)。文書が規約を宣言していない場合は「undeclared (inherits X)」のように継承元を辿って書く。

**Why:** 推定が一度セルに入ると、以後は表が「事実」として引用され、誤りが下流 (付録・回答・別ノート) へ伝播する。さらに対称化 kinetic 項のように**複数の規約選択が観測同値 (pair-agnostic) になる場合、式形からは規約を原理的に決定できない** — 決めるのは宣言だけ。実例: Fourier 規約の誤推定 ("taken to be" と書かれた推定セル) が表 → 付録 → 口頭回答へ 3 段伝播しかけ、読者の疑義 → 一次資料の記法宣言の確認で発覚した。

**How:** 表を書く・読むとき、各セルに「この値の出典は宣言か推定か」を 1 周問う。宣言が見つからないセルは隠さず「(undeclared; inferred from …)」と書く。宣言は孫引きせず、可能な限り宣言箇所そのもの (式番号) を確認する。

## 3. ノートは snapshot、歴史は repo 側 (md + git)

**ルール:** 配布物としてのノート (tex/PDF) には「その時点の最良の知見」だけを self-contained に書く。旧版の誤り・訂正経緯・version 史話 (「v1 ではこうだった」「旧 narrative を訂正」) はノート本文に入れない。履歴の home は repo 側の md (SESSION/DESIGN/RETRACTIONS 等) と git log。

これは CONVENTIONS.md §2 の **snapshot 原理** (dynamic docs は現状のみを記録し、履歴は git log に委ねる) の deliverable 文書への拡張。

**Why:**
- ノート内の史話は、読者に旧誤りを再 import させる毒餌になる (誤った係数や撤回済み narrative がノートから引用され続ける)
- self-contained 性が壊れる (史話は外部文脈を前提にする)
- 未配布の版に対する version 注記は読者にとって無意味な認知負荷

**How:**
- 改稿時に各段落へ「これは現在の最良知見か、経緯の説明か」を問い、経緯は md へ移してノートから削除する
- supersession marker・新旧換算表は md 側に置き、ノートからは参照しない (ノートは単体で完結)
- scripts や他の docs からノートを参照するときは、式番号・節番号でなく**安定な §名/topic 名**で参照する (ノートは進化して番号がズレる)
- ノートの `\date` (タイトルの日付) は **つねに snapshot 日付** (= 最後に現状へ更新した日) にする。起草日 (「March 2026」等) を残さない — snapshot は「いつ時点の最良知見か」を表すので日付も snapshot 時点であるべき。改稿で内容を現状化したら `\date` も同じ日に更新する
- 例外: 公開後 (arXiv 等) の正誤訂正は erratum の標準作法に従う (この規約は未公開の作業ノートが対象)

## <a id="verification-note-minimal"></a>4. 共著者向け検証 note は「問題・結論・手当」だけ (2026-08)

**ルール:** 争点 1 個の検証 note (= 共著者・共同研究者に送る 1 枚もの) は次だけで構成する。

- 第 1 文 = **なぜ気にするか** (問題)。第 2 文 = 結論 (成立する理由は駆動構造 1 個まで)。第 3 文 = どう手当てしたか (**現物を verbatim 引用**する — 「〜を追加した」 と言うだけでは読者が現物を探しに行く)。
- 式の引用は決定的な 1 個に絞る (= 相手は自分の原稿の式構成を知っている。列挙は検証の証明であって伝達ではない)。
- 導出・数値 check・傍論は note に書かず自 repo の解析記録に置き、聞かれたら出す。

**Why:** 2026-08 の実例で、2 ページの節立て note が user 指摘 4 巡 (「冗長すぎ、読んでもらえない」「そもそもなぜ気にしているかが伝わらない」) を経て 3 文 + 引用 1 block に縮んだ。最終形が伝達として最も強い。

## <a id="no-internal-shorthand-in-deliverables"></a>5. 配布物に内部記号を出さない (2026-08)

**ルール:** 共著者・共同研究者に渡す成果物 (note / 差分 PDF / 図の表紙 / メール本文) には、 **自分と作業 agent の間でしか通じない記号を書かない**。 具体的には: 編集回の符号 (「edit Y」「B 案」)、 commit hash、 「N 版」「N edit 版」 のような内部 version 名、 内部 file の path、 作業日を基準にした版指定 (「今朝の版」)。

**置換の型:** 内部記号 → **相手が知っている事実**で言い直す。

| 内部記号 | 配布物での書き方 |
|---|---|
| 「27 edit 版との差分」 | 「投稿版 (2026-05-16 に提出したもの) との差分」 |
| 「edit Y と Z」 | 「8/22 に直した 2 件」 + 中身を 1 行 |
| 「commit abc1234 を base に」 | (書かない。 base は相手が持っている版で指定する) |
| 「B-strong 案」 | 「(案の中身を表す語)」 |

**判別:** その語で相手が**自分の手元の何かを指させるか**。 指せないなら内部記号。 相手が持っているのは「自分が送った / 受け取った版」 と「日付」 だけで、 こちらの編集履歴は持っていない。

**式番号・節番号も版依存 (2026-08 追記):** `(55)` や `Sec. 5.1` は内部記号ではないが、**どの版の番号か**で指す先が変わる — numbered equation を 1 本増減した改訂版では以降の番号が全部ずれる (実例: 同じ式が投稿版 (55) / 作業版 (54))。配布物では**相手が持つ版**の番号で書き、その版の PDF 現物で照合してから送る (tex の行番号は最悪 — 版どころか手元の 2 版の間でもずれ、相手はそもそも行番号で指せない)。document class が変わった版では節の呼び方も変わる (revtex `Sec. 5A` ⇔ article `Sec. 5.1`)。

**Why:** 内部 ledger (= DESIGN / SESSION / 作業 log) では編集回の符号が正しい語彙で、 そのまま配布物に流れる。 2026-08 の実例では、 差分 PDF の表紙・note の変更履歴節・提案 doc の title の 3 箇所に同時に流出し、 user 指摘「私とクロードにしか通じないジャーゴン」 で発覚した。 **内部 ledger の語彙と配布物の語彙は別**と決めておく以外に防ぎ方がない (= 内部記録側で使うのをやめると、 今度は履歴が追えなくなる)。
