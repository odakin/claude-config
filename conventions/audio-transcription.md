# 録音の機械文字起こし

会議・インタビュー・収録を whisper 等でテキスト化して、それを議事録・引用・記録に使う場面。

YouTube の URL から元音声を取得する段階は [web-tools.md#youtube-audio-extraction](web-tools.md#youtube-audio-extraction) を参照。HTML と音源の区別、HLS での取得、M4A への格納と確認を同節で扱う。

出発点は姉妹 doc と同じ: **モデルが起こしたテキストは転記ではなく生成**である
(画像から起こす場合は
[`photographed-document-transcription.md#quotation-extraction`](photographed-document-transcription.md#quotation-extraction))。
音声はさらに条件が悪い。原本が「見れば分かる」形で残らないので、
**照合するには誰かが聞くしかない**。

## <a id="unclear-word-protocol"></a>確定できない語は推測で埋めず、切り出して人に聞く

聞き取れなかった語は「聞き取れませんでした」とは出力されず、**もっともらしい別の語**になる。
文脈から補える語ほど危ない (前後が自然に繋がるので目視では検知できない)。

まず機械側で 3 手だけ試す価値がある。どれも数分で終わる:

1. **beam search** (`-bs 5` / `-bs 8`) — 貪欲デコードとの差を見る
2. **0.75〜0.85 倍速化** (`atempo`) — 早口区間に効くことがある
3. **直前の確定テキストを prompt に注入** — 語彙と文脈を与える

**3 手とも候補が割れたら打ち止め**にする。粘っても当たらない。

⚠️ **多数決を採ってはいけない。** 実測: ある 1 語について再転写のほぼ全 pass が同じ候補を出したが、
正解は**どの pass にも一度も現れなかった語**だった (意味も通らなかったので気付けた)。
候補の一致は正しさの証拠ではなく、同じモデルが同じように外している証拠でしかない。
別の機械と一致しても同じ: 会議ツールの文字起こしと whisper が同じ語に聞き違え、 その区間だけを短く切って転写し直すと別の語が出た
(前後の文脈を持ち越して付いた語が落ちた) ことがある (実測)。 揃ったことは確かめにならない。 短く切った転写は、 候補を増やす手の 1 つになる。

打ち止めたら、**該当区間を切り出して原音を持つ人に聞いてもらう**:

    ffmpeg -ss <開始> -to <終了> -i <音源> -c:a aac -b:a 96k unclear/<番号>_<内容>.m4a

- **前後 5〜10 秒の文脈を必ず入れる。** 単語だけ切り出すと本人でも判別できない
- ファイル名に**時刻と「何を聞いてほしいか」**を書く。聞く側が 1 分で片付けられる形にする
- 聞く人がその機械の前にいないときは、 clip の file を送る (置いた path を伝えても聞けない)
- 確定するまでは対照表に**空欄で置く** (「未解決」の行として)。埋めた推測は後から見分けが付かない
- 確定したら、**機械が出した候補も残す**。「多数決が外れた」記録それ自体が次回の判断材料になる

**時刻の換算に注意。** `1:07.38` は 67.38 秒であって 106.8 秒ではない。
分秒表記と秒指定を行き来する場面なので、切り出した clip は**必ず中身を確認**してから渡す
(短い clip なら再転写して目的の語が入っているか見るだけでよい)。

## <a id="hallucination-runs"></a>無音・雑音区間のハルシネーションは区間ごと隔離する

無音や非音声の区間で、モデルは同じ音を延々と繰り返した出力を作ることがある
(「いろいろいろいろ…」「はいはいはい…」)。実発話ではない。

- 見つけたら**時刻区間を対照表に書いて隔離**する。本文からは消さない (消すと次に読む人が同じ判断をやり直す)
- 「引用しない」と明記する。長さがあるので、要約に混ざると実在しない発言を作る

## <a id="loop-runs-in-speech"></a>話している区間のループは、 その区間だけ文脈を切って転写し直す

長い録音を一括で転写すると、 **音のある区間でも**同じ 1 文が数分〜数十分続くことがある (実測)。
上の無音のハルシネーションと違い、 ここには本物の発話がある。 原因は前の出力を次の区間の文脈に
持ち越すことで、 whisper.cpp なら**その区間だけ `-mc 0` (文脈を持ち越さない) で転写し直す**と中身が戻る。

- 見分け方: 繰り返し区間の音量 (`ffmpeg … -af astats` の RMS level) が、 普通に転写できた区間と同じくらいある
  → 発話がある。 ノイズフロア並みなら無音 = 上の節どおり隔離する
- 全体を最初から `-mc 0` で回さない: 文脈が切れると区間の境目で語が崩れやすい。 ループした区間だけに使う
- 転写し直しても繰り返しが残る区間は、 無音か非音声として上の節どおり隔離する
- **ループでない別の崩れ**: 長い録音を一括で起こすと、 途中から区切りが 1 秒刻みに揃い、 各行の末尾に「…」 が付く出力に変わることがある (実測)。
  中身は発話のままで同じ文も続かない (= ループの検出にかからない) が、 **時刻が 2 秒ほどずれる**。 章立てには使えるが、 切る位置は音
  (`silencedetect` と音量の並び) で決め、 転写の時刻を切れ目にしない。 その区間を転写の見出しに書いておく
- 道具 = [`../scripts/whisper-transcribe.py`](../scripts/whisper-transcribe.py) (全体の転写 → ループ区間の検出 →
  `-mc 0` で転写し直して差し替え → 差し替えた区間と未解決の区間を見出しに書く、 を 1 コマンドで)

## <a id="word-onset-clipping"></a>語頭欠落は収録側の問題 — デコードでは戻らない

会議ツール (Zoom 等) のノイズ抑制は、**語頭の子音を削る**ことがある。
会話中は脳が補完するので気付かず、**文字起こしして初めて可視化される**。

- **デコード側の工夫は当たらない。**上の 3 手が全滅する典型がこれ。音が無いものは復元できない
- 直すのは**収録側**。次回の収録前に設定と環境を確認する
- ⚠️ **相手側は直せないことがある。**携帯アプリ版だとノイズ抑制の強弱を選ぶ設定自体が無い。
  相手に頼む前に、相手のクライアントで選べるのかを確かめる
- **定常ノイズ源を持ち込まない。**送風 (扇風機・エアコンの風が本体に当たる) のような
  途切れない音があると、抑制がそれを消しにかかり続ける

## <a id="verify-the-setting-took-effect"></a>「設定を変えた」と「効いた」は別 — ノイズフロアで測る

設定を変えた記憶を根拠に原因を確定しない。**録音そのものから確かめられる**:

    ffmpeg -hide_banner -nostats -ss <開始> -t <長さ> -i <音源> -af astats -f null - 2>&1 \
      | grep -E "Noise floor dB|RMS trough dB"

抑制が強いほど無音が深く潰れるので、**ノイズフロアが設定の効き方の代理指標**になる。
実測例: 抑制「強」の区間が -78 dB、「弱」に変えた後が -57 dB — 20 dB 開いていて、変更は効いていた。

これで**仮説を捨てられる**ことがある。上の例では「抑制が強すぎたせい」で片付けかけたが、
症状が出た時刻を照合すると**全部が変更後**だった。効いているのに症状が残るなら原因は別にある。
**症状の時刻と、設定を変えた時刻を必ず突き合わせる。**

## <a id="no-speaker-separation"></a>単一 mix track では話者分離できない — 1 コマンドで確かめる

会議ツールのローカル録音は全員を 1 本に混ぜたものが普通で、ステレオでも中身が同一のことが多い。
L−R が無音なら**機械的な話者分離はできない** (誰の発話かは内容から読むか、人に聞くしかない):

    ffmpeg -ss <開始> -t 20 -i <音源> \
      -af "channelsplit=channel_layout=stereo[l][r];[l][r]amerge=inputs=2,pan=mono|c0=c0-c1,astats" \
      -f null - 2>&1 | grep "RMS level dB"        # -inf なら L=R = 分離不能

「誰の発話か」は音質問題の切り分けで効いてくる (自分側の環境が原因か、相手側か)。
分離できないと分かった時点で、**人に聞く**を手順に組み込む。

**会議ツール自身の文字起こしが取れるなら、 先にそれを見る**: Zoom の文字起こし (VTT) は参加者ごとの表示名つきで、
内容から推すより確かな帰属の手がかりになる (取り方・時刻のずれ・語の取り違え = [`zoom-meetings.md#transcript-speaker-labels`](zoom-meetings.md#transcript-speaker-labels))。

- **内容から読んだ話者は推定にすぎない** — 問いと答えが続く短いやりとり (合成例: 「出して大丈夫？」「大丈夫でしょ」) は、
  内容からはどちらが聞いた側か決まらず、逆に読む (実測)。話者を記録に書くなら「推定」 と書き、
  **外に出す文面 (相手への確認・引用・紹介文) に誰の発言かを書くときは、その場に居た人に確かめてから**にする。
  会議ツールの AI 要約の話者の帰属も同じく推定として扱う

## <a id="paragraphing"></a>段落化は script にする

生の SRT はセグメントが 1〜10 秒刻みで、そのままでは読めない。
**無音 N 秒 or 約 M 字で段落を切り、行頭に時刻を置く**だけで読めるようになる。

これを手作業でやらない。収録が繰り返し発生するなら、整形は最初から script にする
(閾値を変えたくなったとき、変更点が 1 箇所で済む)。

## <a id="splitting-long-recordings"></a>長い録音の分割 — 音の切れ目と話の切れ目の両方を満たす

転写結果のいちばん実用的な使い道が**分割点探し**である。切れ目には 2 つの条件があり、
**片方だけでは失敗する**:

1. **音の切れ目** — 無音の中で切る。発話の途中で切ると聞けたものではない
2. **話の切れ目** — 話題が変わる所で切る。**音だけで選ぶと話題を途中で割る**

実測: 1 つ目の条件だけで選んだ切れ目は、綺麗な 2 秒の無音だったが、ひとつの話題
(ある材料の話) を前半と後半に割っていた。**転写の章立てを見て初めて分かった。**

    ffmpeg -hide_banner -nostats -ss <開始> -t <長さ> -i <音源> \
      -af "silencedetect=noise=-45dB:d=0.4" -f null - 2>&1 | grep silence_

候補の話題境界を転写から拾い、その近傍で `silencedetect` に無音を出させて、
**両方が重なる所**を切れ目にする。

- **各 part は「その話題の 1 文目」から始める。**単体で聞き始めても話が立ち上がる。
  話題の受け渡しの一文 (「さっきの話に戻りますけど」等) は**次の part の頭に入れる**。
  前の part の末尾に残すと、次が唐突に始まる
- **無劣化 copy で切る** (`-c copy`)。再エンコードしない。**尺の合計が元と一致するか**を
  毎回確かめる (= 欠落・重複の検査。これは 1 行で機械化できる)
  - 切り直すときは、**秒でなくフレーム数で切る** (`-frames:a N`。AAC は 1 フレーム 1024 サンプル)。
    `-c copy` に `-to` / `-t` を秒で渡すと、境目がフレームに丸められて **1 フレームはみ出す**ことがある
    (実測: 合計が 0.021 秒長く、隣の part との境目が 1 フレーム重なった)。合計の長さだけでなく、
    **隣の part と接する側の音を decode して旧版と sample 単位で比べる**と、どの境目が動いたかまで分かる
  - 道具 = [`scripts/audio-split-by-frames.py`](../scripts/audio-split-by-frames.py) (フレーム番号か秒で境目を渡すと、無劣化で切って
    各 part のパケットが元と同じか・合計が合うかまで確かめる)。**無劣化で切れたかの確認はパケットの一致で見る** — デコードした音の
    比較は、雑音の帯域を乱数で埋める符号化 (PNS) だと同じパケットでも一致しない (実測)。**先頭に符号化の遅れがある音声では
    フレーム番号と時刻が 1 フレームほどずれる** = 秒から境目を決めるならパケットの実際の時刻を使う (script がやる)
- **長さの決まり (下限・目安の範囲) があるときは、話の切れ目の候補を並べて、範囲に入るものを選ぶ。**長さに合わせて話題を割らない。
  本数は「長さ ÷ 下限」で上限が決まる (付け足す冒頭・締めの音の長さも入れて計算する)。候補ごとに「何の話を割るか」を書き出すと選べる
- **話し手自身が話をまとめ直す所は強い話の切れ目。**「何の話だったっけ」→ 要約 → 相づち、の直後で切ると、前の part はまとめで閉じ、
  次の part は新しい話から始まる。まとめ (前の話を閉じる言葉) は前の part の尾、次の話への受け渡しの一文は上の規則どおり次の part の頭 (実測: 明示の話題転換の合図がある 2 か所ではどちらも話題の塊が割れ、まとめ直しの直後では割れなかった)
- **全部の切れ目の両側を再転写して確認する。**「末尾 6 秒 / 冒頭 10 秒」で足りる (道具 = [`../scripts/audio-window-check.py`](../scripts/audio-window-check.py) `edges <part…>`。
  切る位置を決める前の、 候補の前後の音量の並び = 同じ道具の `envelope --at <秒>`、 候補の前後の転写 = `window --at <秒>`)
- **切り直しは安い。**無劣化 copy なら元から何度でも切り直せる。最初の案に固執しない

⚠️ **話題が何度も戻ってくる素材では、どこで切っても完全には揃わない。**
「一番マシ」であって完全解ではない、と正直に書く。揃ったふりをすると、
次に触る人が「なぜここで切ってあるのか」を読み違える。

⚠️ **落とさないと決めた区間を、要約の語彙でぼかさない。**
公開すると決めた後も、以前の懸念が自分の要約に別の語として残ることがある
(実測: 出すと決まった話題を、部分一覧では当たりのやわらかい語に言い換えていた)。
**中身の一覧と方針は同じ語で書く。**

## <a id="transcript-words-in-titles"></a>転写の語を題・見出し・引用に使う前に

機械の転写は**同音の漢字を一貫して取り違える** (合成例: 「〜権」 を 「〜券」)。多数決も効かない (どの pass も同じに出る = [#unclear-word-protocol](#unclear-word-protocol))。
転写の語を**そのまま外に出す** (題・見出し・紹介文・引用) ときは、その語だけは次で確かめる:

- 前後の言い直し・言い換え (「〜の権利」 のように話し手が同じことを別の語で言っていないか)
- 誤転写の対照表 (その録音で見つかった取り違えの一覧)。新しく見つけた取り違えは対照表に足す
- 確かめられなければ、その語を使わないか、持ち主に聞く

外に出した後で見つかると、ホスト・公式サイト・RSS・配信先の全部を直すことになる (実測)。
