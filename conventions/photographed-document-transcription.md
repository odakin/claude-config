# Photographed document transcription — 撮影写真の一括転記

## <a id="scope"></a>場面

紙の束を**スキャナでなくカメラで撮った**写真 (= 斜め照明・机の写り込み・紙の湾曲・薄い鉛筆) を、
モデルに読ませて構造化データにするとき。 典型例は手書きの提出物・手書きノート・受領した紙書類。

隣接する規約との分界:

- [`media-transcription-ledger.md`](media-transcription-ledger.md) = **定期的に届く画像 stream** を SoT 化する仕組み (transcript home + 読取 ledger + 未読 detector)。 「どの画像を読んだか」 の追跡が主題。 本 doc は **1 回の束を読み切る**ときの作り方が主題で、 継続 stream なら両方を使う。
- [`chalkboard-close-up-merge.md`](chalkboard-close-up-merge.md) = 板書写真の広域 + close-up を 1 page に合成する個別 recipe。
- [`exam-grading-return.md`](exam-grading-return.md) = 読み取った**解答用紙の採点と返却** (部分点の決まり・写真への赤入れ・一人ずつのメール・全体への統計)。 本 doc の転記の正本をそのまま採点の正本にする。
- [`audio-transcription.md`](audio-transcription.md) = **音声**の機械文字起こし。 §quotation-extraction の「転記でなく生成」 が同じ形で効くが、 原本が「見れば分かる」 形で残らないぶん照合が難しい (= 確定できない語は切り出して人に聞く)。

## <a id="annotation-overlay-scan"></a>他人の書き込みが載った文書を読む — まず「どこに在るか」を機械で列挙する

自分が出した文書に**第三者が手書きで朱を入れて返してきた** PDF (事務の差し戻し・共著者の朱・
紙の査読票・朱を入れて返された紙) は上の 5 段と別種の問題を持つ: 原本の版面は自分が持っているので転記は
要らず、**知りたいのは「どこに何が書かれたか」だけ**。ところがスキャン PDF は
`get_text()` が空 (画像 1 枚) で、全頁を目で追うと見落とす。

- **色領域で書き込み位置を機械列挙する**。頁を raster 化 → 彩度の高い画素 (朱・青ペン・
  付箋の黄) の mask → 連結成分をとって bbox を余白込みで crop → **crop を 1 枚ずつ読む**。
  頁全体を 1 枚で読ませるより、書き込みと下地の本文が同じ crop に入るぶん文脈が正しく付く。
- 🔴 **「書き込みは無い」を部分走査で断定しない**。頁ごとの色画素数の総量だけ見て
  「後半の表だけ朱が入っている」と報告し、実際は本文中に十数箇所あった実例がある
  (印刷の網点・図の色・スキャン時の色かぶりが底上げして、真の書き込みが相対的に埋もれた)。
  **全頁 × 全連結成分**を列挙し、閾値未満で捨てた成分の個数も残す。
  一般則 = 単一情報源の null を不在の証明にしない ([`debugging-discipline.md`](debugging-discipline.md))。
- **crop file 名に文書 tag を入れる**。複数文書の crop を同じ dir に吐くと、頁番号だけの
  命名では衝突して**片方が silent に上書きされる** (実例: 2 文書分の走査で tag 無しの
  命名が衝突し、両方が同じ file 名になった)。
- 読み終えたら **指摘と情報メモを分けて台帳化**する。事務の付箋には対応不要の運用連絡
  (審査の色運用・件数制限・担当者名) が混じり、指摘と同じ扱いで抱えると作業が膨らむ。
  対応不要と判断したものは**理由付きで残す** (次の窓で読み返したとき再検討しないで済む)。

## <a id="pipeline"></a>全体の 5 段

```
1. 取り込み    写真を撮影順で連番化し、原本を不変の形で保存
2. 帰属確定    どの写真が誰/どの案件のものか → 台帳 (以後 変更しない)
3. 前処理      紙の切り出し + 照明ムラ除去 + コントラスト伸張 + タイル分割
4. 分担転記    spec を書いて複数 session へ → part file に書かせる
5. 統合・導出  本体 file へ統合 → 分割 file 削除 → 数字は script で導出
```

⚠️ **3 を飛ばして生写真を直接読ませない。** 薄い鉛筆は生のままだと読み違える。 これは
「読めなかった」 と自己申告される失敗ではなく、 **もっともらしい別の文字列を返す**失敗
なので、 出力を見ても検知できない。

## <a id="preprocessing"></a>前処理 — 何をするか、どこで転ぶか

実装: [`scripts/enhance-scan.py`](../scripts/enhance-scan.py) (docstring が使い方の正本)。

### 3 つの処理

1. **照明ムラ除去 (shading correction)**: 低周波成分でわり算して紙面を平坦化。 斜め照明で
   片側が暗い写真でも、 全面で同じしきい値が使えるようになる。
2. **紙の切り出し**: 机を捨てて画素を紙に集中させる。 画面の 4 割が机、 という写真は普通にある。
3. **コントラスト伸張**: 紙の地を基準に、 筆跡を黒側へ寄せる。

### <a id="preprocessing-traps"></a>実装で踏む罠 3 つ

| 罠 | 症状 | 正しいやり方 |
|---|---|---|
| **背景除算後の画像で紙を検出しようとする** | 紙も机も 1.0 付近になり全面が「紙」 判定 | 紙/机の判別は**除算前の低周波成分**で行う (= 紙は明るく机は暗い、 という大局的な差はそこにしか残らない) |
| **連結成分 + Otsu で紙領域を取る** | 机の照明反射 (ハイライト) が紙と繋がり、 外接矩形が全面になる | **行・列の明度プロファイルの最長連続区間**で取る。 小さい反射斑は profile では埋もれる |
| **切り出しを攻めすぎる** | 紙の縁が影で暗く、 内側を切り落として**行頭の記号や番号が欠ける** | 中点しきい値で芯を見つけ、 低しきい値で外側へ広げ直す 2 段構え。 **余白は広い側に倒す** (机が少し写る損 < 文字が欠ける損) |

もう 1 つ、統計の取り方:

- **紙の地は「高い percentile」 では取れない。** 光の反射が外れ値として上に出るので、
  percentile 99 は紙でなくハイライトを指す。 紙は画素の大多数なので **中央値が地**。
- percentile は**切り出し矩形の内側だけ**で取る。 矩形の縁に残った机に引っ張られると伸張が効かない。

### <a id="tile-size"></a>タイル分割はモデルの入力上限に合わせる

**モデルの画像入力には長辺の上限がある** (実務上 ~1568 px)。 これを超えるサイズを渡しても
内部で縮小されるだけで、 **1 文字あたりの画素はかえって減る**。

したがって「大きく渡す」 のではなく「**上限に収まる大きさに分割して複数枚渡す**」 のが正解:

| 原稿の密度 | 分割 | 1 タイルあたり |
|---|---|---|
| ふつうの手書き (A4 縦) | 上下 2 分割 | 紙幅いっぱい × 高さ半分 |
| 書き込みが密 | 格子 4 行 × 2 列 程度 | さらに細かく |
| 極端に密 | 5x2 / 4x3 へ上げる | — |

- 隣接タイルは数 % 重ねる (= 境界にまたがる行を落とさない)。
- 紙が横向きに写っている写真は先に回転させてから分割する。
- 分割を増やすほど読めるが、 その分だけトークンを食う。 **薄い/密なものだけ細かく**する。

## <a id="attribution"></a>帰属の確定と独立検証

写真 → 対象 (人・案件) の対応付けは、 **確定したら以後変更しない台帳**に固定する
(以降の全工程がこの台帳を参照するので、 途中で動かすと全部ずれる)。

問題は **1 枚目にしか識別情報が無い**場合。 裏面・2 枚目には名前が書かれていないことが多く、
「撮影順で直前の表面と同じ対象」 という**隣接推論**に頼ることになる。 これは撮影運用への
依存なので、 必ず裏付けを取る:

- ✅ **2 つの独立な集合の一致**を見る。 同じ対象について**別々に撮った 2 系統**があるなら
  (例: 本体書類と付属書類)、 両者から得た対象集合が完全一致することを確認する。 撮影順が
  系統ごとに違えば、 片方で 2 人を 1 人に潰す誤りは他方と食い違って露見する。
- ✅ 台帳内の**構造検査**: 同一対象の連番が連続しているか、 1 枚目が表で 2 枚目が裏か、
  1 対象あたりの枚数が想定内か。
- ✅ 原本ファイルの **sha256 を台帳に持たせる** (= 後から「この写真は本当にこれか」 を照合できる)。

⚠️ 隣接推論に頼った箇所は、 台帳に**そう明記する** (「氏名の記載がある N 枚以外は隣接で帰属」)。
後で誰かが「全部読み取って確定した」 と誤解するのを防ぐ。

## <a id="fidelity"></a>転記の忠実性

- **verbatim は原本のまま。 誤記・誤植も直さない。** 転記が判断の根拠になる用途 (採点・監査・
  引用) では「本人が実際に書いたもの」 が要る。 直した瞬間に根拠として使えなくなる。
- **判読できない箇所は推測で埋めず marker を置く** (`[判読不能]` 等)。 撮影写真の読み取りは
  「読めない」 と「もっともらしい別の文字列」 の距離が近い。 **読めないことを正直に記録した
  方が、 埋めた推測より価値が高い**。
- 原本の**物理的配置と論理的順序が食い違う**場合 (= 書かれた順が項目順でない) は、
  **論理順に並べ替えて転記し、 物理配置は別フィールドに書く**。 両方を保つ。
- 所見・判断は verbatim と**別フィールド**にする。 混ぜると後から「どこまでが原本か」 が
  分からなくなる。

## <a id="screen-derived-values"></a>画面から読んだ「値」 と「状態」 は、 読み直しでは検証にならない

写真・screenshot から読み取ったものを、 同じ画像を読み直して確かめても、 **同じ誤りが同じように再生産される**
だけで検証にならない。 別経路で確かめる。 とくに次の 2 つは誤りが自己訂正されない。

### <a id="opaque-string"></a>不透明な文字列 (復旧キー / ライセンス / シリアル / 番号)

自然文と違い **意味の冗長性がゼロ**なので、 1 文字違っても文として破綻せず、 読み返しても違和感が出ない。
気づくのは使う瞬間 = 使えないと分かる瞬間だけ。

- 拡大して**字形の幅**で判定する: `O`/`0`、 `1`/`l`/`I`、 `5`/`S`、 `8`/`B`、 `2`/`Z`。
  多くの UI 書体で数字の `0` は大文字 `O` より**狭い楕円**になる (隣の丸い字と幅を比べる)
- 文字列全体に出現する字から **alphabet を推定**して補強する (例: 全体に `0` が 1 度も出ないなら、
  その体系は `0` を除いて `O` だけを使っている可能性が高い)。 ⚠️ これは補強であって根拠ではない
- **読みの正しさは checker で確かめる** — その値を検証するコマンド・API があるなら 1 回通す。
  無いなら「未照合」 と明示して記録し、 照合済みと書かない
- **再表示できる source があるなら、 それを ground truth にする** (= 写しではなく元を開き直す)

### <a id="control-state"></a>制御の状態 (toggle / checkbox / 選択)

**色で判断しない**。 modal (sheet / dialog) が前面にあると背面の window 全体が減光され、 有効色 (青等) が
灰色に落ちる。 「灰色だから無効」 は誤読の定番。

- **幾何で読む**: toggle はつまみの左右、 checkbox はチェック印の有無、 選択は枠・背景の位置
- 状態を問える CLI / API があるなら、 画面ではなくそちらを一次情報にする (画面は人への説明用)
- 本人の記憶と実測が食い違ったら、 **実測の出力をそのまま見せて**判断を渡す。
  記憶は証拠ではないが、 こちらの読み違いの可能性も同時に潰す (= 別経路で 2 度測る)

## <a id="printed-totals-checksum"></a>数字の表は、 紙に印字された合計で検算する

通知書・明細・請求書のような**数字の表**を写真から転記するとき、 読み直しでない別経路 ([#screen-derived-values](#screen-derived-values)) を**紙そのものが持っている**ことが多い = 小計・合計の欄。

1. **原本の file から原寸で切り出して読む**。 添付した画像はモデルには縮小されて見える ([#tile-size](#tile-size)) が、 手元の file は撮影した解像度のまま残っている。 表を欄のまとまりごとに切り出してから読む (macOS = `sips -c <高さ> <幅> --cropOffset <上> <左> in.jpg --out crop.jpg`、 座標は原本の画素 = 縮小された表示の上で測った座標には 原寸 ÷ 表示 の倍率を掛ける)。 **何枚もまとめて貼られたときは、 切り出す前に file と書類の対応を確かめる** — 並びを数え違えて別の書類を切り出した実測がある。 縦長・横長の並び (`sips -g pixelWidth -g pixelHeight`) を表示の並びと照らし、 切り出した結果が目当ての書類かを見てから読む
2. **内訳の和を印字の合計と突き合わせる**。 一致すれば 1 桁の読み違いは残らない。 残りうるのは打ち消し合う 2 か所の誤りだけ。 **合わなければ記録に書かない** = どこかを読み違えている。 合計の欄が無い書類は、 同じ束の別の書類に載る同じ金額と突き合わせる (例: 申請書の対象経費 = 領収書の内訳の 1 行 = 見積の機器費 + 工事費)
3. **照合の方法と結果を記録に残す** (どの合計で検算したか・一致したか)。 後で「写真から起こした値を確かめたか」 を問われたときの答えになる
4. **紙に QR があれば中身と機械で照合できる** ([`scripts/decode-qr.py`](../scripts/decode-qr.py))。 **高密度の QR は紙面全体の写真では 1 マスあたりの画素が足りず、 見つかっても復号できない** (実測。 切り出して拡大・二値化しても同じ)。 QR だけを寄りで撮り直す

## <a id="local-vision-ocr"></a>外に出せない表の写真を、 手元の Vision で読んで照合する

人の ID と値 (順位・点数) が並ぶ表の写真を、 別に持っている表と照らしたいが、 中身を AI (外の model) に渡せない場合の作り方。
macOS の Vision (`VNRecognizeTextRequest`) は手元で動き、 Swift の小さな道具から呼べる (Python の PyObjC が無くても `swiftc` で組める)。

**中身を渡さない形**:
- 読みと照合は手元の script が回し、 読んだ文字・表・氏名は手元の file にだけ書く。 端末には件数と合わない ID だけを出す。
- AI の session が「実物で動くか」 を確かめるときは、 数だけを出す口 (`--counts-only` のような) を作り、 その出力も ID の形の文字列を伏せる filter に通してから受け取る。 Python のエラーの全文 (traceback) にも値が混じるので、 数だけの口ではエラーの全文を file に書き、 端末にはエラーの型の名だけを出す。 写真を読まずに表だけを集計する道具の一般形 (群の端の値を出さない・出力をデータ自身の ID と氏名で照らして止める) = [`confidential-repo-boundary.md#counts-only-analysis`](confidential-repo-boundary.md#counts-only-analysis)。
- 開発の試験は合成データ (架空の ID・氏名・手書き風の字の画像) で行う。 架空の ID は実在しえない形 (まだ無い入学年など) にする = 実在の人の ID と偶然一致しない。

<a id="independent-of-reference"></a>**写真の読みは照らす相手から独立に作る** (読みを相手の値に寄せると検算にならない):
- 写真を読む段には、 照らす相手の表から ID の一覧 (人を結ぶため) と人数だけを渡し、 照らす値 (順位など) の列は写真の読みが全部決まってから読む。 作りで分けておくと、 寄せていないことを code で示せる。
- 読みが割れた行を、 照らす相手の値と同じ読みがあるからといって「一致」 にしない = 「写真で決まらない」 と出す。
- 読み方の改良の選択 (描き方・閾値・読み替え) は、 合成データでの正解率で決める。 実データは「読めたか・どこが読めないか」 を測るためだけに使う。 実データの正解率を見て選んだものは、 合成データで選び直して申告する (実測: 実データで選んだ描き方を合成データで比べ直すと、 選択は変わらなかった。 選び直すまでは検算の独立を主張できない)。
- 表を使わない検算を足す: 写真の値の全体 (照らす相手に無い人も含む) が 1〜N を抜けも重なりもなく埋めているか (同点があれば重なる)。

**Vision の罠 (実測)**:
- `minimumTextHeight` の既定 (画像の高さの 1/32) では、 1 枚に数十行ある表の字が落ちる = 0 にする。 言語補正 (`usesLanguageCorrection`) も切る (ID が単語に直される)。
- 返す枠 (`topLeft`〜`bottomRight`) は傾きを持たない = 写真の傾きは ID の列の左端が下へ行くほどずれる量から測る。
- 大きな写真の 1 枚の読みは、 小さな字の列を丸ごと落とすことがある (4 桁の番号の列の上半分など) = 横長の帯に分けて拡大した読み、 行ごとに欄を切り出して拡大した読みを足し、 多数決にする。 欄の切り出しは傾きを直した座標で行い、 高さは行の間隔の半分弱にする (隣の行の字を拾わない)。
- 1 字だけの数字は文字の行として検出されない。 欄の字をぴったり切り出し、 印字の「No.」 の直後に貼ると「No.5」 という語になって読める (欄の余白ごと貼ると「No.」 と字が別の語に分かれて効かない)。
- 版 3 (既定) は 1 字の数字の上下を取り違え、 6 と 9 を入れ替えて読む = 1 字を読む切り出しは版 2 (`revision = 2`、 英数字だけ) で読む。 同じ画像を版 2 と版 3 で読んだ 2 つは、 同じ値なら多数決で 1 票に数える (誤りが重なって 2 票になる)。
- 手書きの 2 桁は 1 字ずつ別の語に読まれる = 同じ行で隣り合う 1〜2 字の数字をつなぐ。 別の読みの一部でしかない読み (52 に対する 2) のうち、 それを含む長い読みが同じ数以上の票を持つものを、 字を落とした読みとして多数決の前に外す。 長い読みのほうが票の少ないときは外さない = 長い読みが余計な字を拾った読みのこともある (実測: 票の数を見ずに外すと、 1 票の長い読みが多数の短い読みを全部消し、 誤った値に決まった。 下の 2 つの読み手の突き合わせで見つかった)。
- 読み違えの型: 右上に小さく書いた 0 を「°」、 縦線の 1 を「(」「|」「l」 と読む。 罫線の無い切り出しの中だけで 1 に読み替える (1 字の「|」 は罫線のことが多い)。

**色のペンで書いた値** (印字の表に手書きの順位を足した写真): 彩度 (RGB の最大 − 最小) が紙の色かぶりより十分高い画素だけを抜くと、 罫線と印字が消えて手書きだけが残る (書き込みの位置の列挙と同じ道具立て = 上の [#annotation-overlay-scan](#annotation-overlay-scan))。 抜いた字は白黒の 2 値でなく、 彩度に応じた濃淡で描いて読ませる (合成データでも 2 値より正しく読める)。 長い氏名のすぐ右に書いた値も、 色で抜けば氏名から離れる。

**表が 2 つ並ぶ写真**: 値の列の位置 (ID から見た横のずれ) を ID の列ごとに決める (表ごとに間隔が違う)。 列の位置の多数決は、 行の中ほど (縦のずれが行の間隔の 3 割以内) の数字だけで数え、 隣り合う区画の合計で比べる = 半行ずれて並ぶ隣の表の数字を数えない (実測: 合成の写真で、 右の表の列に左の表の値の列を選んでいた)。

<a id="local-vision-llm"></a>**手元の画像の LLM を 2 つ目の読み手にする** (Ollama の画像を読める model など。 Vision と違う読み違いをするので、 突き合わせると片方の誤りが見える):
- **中身を外に出さない起動**: 道具が自分で server を 127.0.0.1 の空いた port に立て、 外の推論を止める設定 (Ollama は `OLLAMA_NO_CLOUD=1`) で起動し、 読み終えたら止める。 既に動いている server は使わない (設定を保証できない)。 外の model (名前に cloud を含む・`/api/show` が remote と答える) は断り、 model が手元に無ければ落とさずに止まる (落とすのは本人の許可)。 Ollama の server は起動のときに配布元から推奨の model の一覧を取りに行く (写真は送らない)。 Homebrew で Ollama を入れると、 依存の Python が素の `python3` を替えることがある ([`python-env.md#brew-dependency-relinks-python3`](python-env.md#brew-dependency-relinks-python3))。
- **帯に切って読む**: 写真を横長の帯に切り、 帯の上下に重なりをもたせる。 回ごとに帯の本数とずらしを変え、 境目を変える (境目で切れた行が、 別の回では帯の中に入る)。
- **問いの文** (実測): 例の ID を具体に書くと、 model がその ID を写して答えに混ぜる = 例は `K##M####` のような形だけにする。 「順位」 とだけ聞くと、 同じ行の印字の別の数 (小数の値) を答える = 印字の ID・印字の氏名・手書きの値を、 名前を付けた別の欄で答えさせる (氏名の欄も答えさせると行の取り違えが減る)。 答えの形 (JSON の schema) を指定し、 温度 0 で読む。
- **下 4 桁だけの表**: model は ID の前半を作って答える (値を前半に入れた形など、 実測) = 完全な形の ID が照らす相手の一覧に無ければ、 下 4 桁で結ぶ (前半だけの読み違いもこれで救える)。 結ぶのに使うのは ID の一覧だけで、 照らす値は渡さない (上の [#independent-of-reference](#independent-of-reference))。
- **主な読み違いは隣の行の値を答える 1 行ずれ** で、 帯ごと・回ごとにばらばらに起きる (表が 2 つ並ぶ写真で多い、 実測) = 2 回読んで割れた人がいれば、 帯の境目を変えて上限つきで読み足し、 多数決にする。 割れが残った人は「写真で決まらない」 と出す。

<a id="two-reader-cross-check"></a>**2 つの読み手の突き合わせ**: 2 つの読み手はどちらも照らす相手の値を見ずに読み、 読み終えた表を ID ごとに並べる。 区分は 4 つ = 2 つが同じ値で照らす相手と一致 (人に出さない) / 2 つが同じ値で照らす相手と違う (照らす相手の側の誤りの見込みが高い) / 2 つの値が違う / どちらかで決まらない (この 2 つ = 写真のその行を人が見る)。 片方の読み手しか動かない機械 (model が入っていない) では、 その旨を 1 行出して 1 つの読み手で判定する。 「2 つの値が違う」 場合の試験は、 本物の読み手では狙って起こせない = 読み手と同じ引数と出力の形で、 合成データの答えの一部をずらし一部を決まらないにして返す代役を作り、 区分ごとに拾えるかを試す。

<a id="hand-over-copy"></a>**作った道具を人に渡す写し** (実データを手元だけで扱う他の道具にも同じ点検を当てる):
- 実データの出力を見て読み方を直した後は、 code のコメント・docstring・端末に出る文の例に、 実データの値 (氏名の断片と値の組・特定の行の書かれ方) が入る。 渡す前に、 例の文字列が実データの file (読み起こし) に何件出るかを件数だけで数え (file は開かない)、 例は合成データの値に置き換える (実測: 実データで直した読みのコメントの例に、 実在の氏名の一部とその値が入っていた。 公開 repo の例・selftest に起きる同じ引力 = [`confidential-repo-boundary.md#session-carryover-gate`](confidential-repo-boundary.md#session-carryover-gate))。
- 作り方の来歴を言う文 (「作った人は実物を見ていない」「実データは測るためだけ」) は、 後で実データを見て直すと偽になる = 直す commit で、 同じ file と説明の文書の来歴の文も直す。 上の [#independent-of-reference](#independent-of-reference) の「実データで選んだものは選び直して申告」 と同じ申告を、 来歴の文にも当てる (実測: 冒頭の説明が、 同じ file の実測の記述と食い違っていた)。
- 写しは file だけで渡す = repo の clone・履歴つきにしない (履歴には実データ由来の file と、 コメントから消した値が残る)。 読み起こし・実データでの検算の結果・作る途中の記録は写しに入れない。 判断のつかない file は名前と行数だけで決め、 中身に実データがありうるなら外す側に入れる。
- 受け取る人のための入口を別に書く: 要るもの (Command Line Tools の `swiftc`・Python の画像の library・手元の LLM を使うならその道具とモデル)、 データの dir に置く file の名前、 まず合成データで動くかを確かめる順。 作業の記録の README (案件の id・会話の引用・データの置き場の ID) は写しに入れない。 「外へ送らない」「この機械の中だけ」 は回すときの性質として射程つきで書き、 手元の LLM の server の起動時の通信 (上の [#local-vision-llm](#local-vision-llm)) は入口の目立つ所に書いて、 通信を一切させない回し方 (LLM の読み手を回さない option) を示す。
- <a id="hand-over-copy-count-check"></a>**写しの点検は件数で、 照らす元の値を出さずに**: 照らす元 (実名の一覧・読み起こし) を読み、 写しの側の一致した file と行だけを出す script で数える。 氏名の一部 (先頭・末尾の 2 字) で照らすと、 仮名 2 字の並びが普通の文に当たる = 当たった断片を出さずに、 字の種類 (仮名か漢字か) と、 無関係な公開文書の中での出現の数で、 普通の語の並びかを分ける (実測: 当たりはどれも仮名 2 字で、 公開の規約文書の数十〜千数百行にも出た)。 学籍番号の形は自前の正規表現で探さず、 学生の識別子の検査器 ([`scripts/check-student-identifiers.py`](../scripts/check-student-identifiers.py) の `--tree`) を当てる (実測: 自前の形が年の桁で見落とした ID の形の文字列を、 検査器が拾った)。 `--tree` は git repo を読むので、 写しの file を使い捨ての git に入れて当てる (`git init <dir>` → `git -C <dir> add -A` → `GIT_DIR=<dir>/.git GIT_WORK_TREE=<dir> git commit`。 作ったばかりの repo には hook が無いので、 そのまま commit する)。
- **仕様に挙がった直しの形を、 写しの全 file で探す**: 直しの仕様は、 それを書いた点検が読んだ範囲の中でしか形を挙げない = 「1 つの group だけを数える直書き」 のような形は、 仕様が名指した file に限らず写しの全 file を grep する (実測: 仕様が名指さなかった file に同じ直書きがあった)。 合成データの生成器が、 消した直書きを満たすために実在の名前を持っていることがある = 直書きを消したら、 生成器の名前も合成の名に替える。
- <a id="hand-over-copy-no-history"></a>**写しが作り方の経緯を言わない形にすると決めたら、 日付の語だけでなく、 作った順と試し方が読める形も探す**: 日付・「今日」「新しく」・前の版との比べの語のほかに、 (1) 1 つの道具を別の道具を基準に言う文 (「X の姉妹」「X の読み手を変えた版」「X と同じ照合を別の読み手で」、 「Y でも読む」「Y も回す」 の「も」「でも」) = X が先にあった・Y は足しと読める。 並べて言うなら両方を同じ重さで名指す (「2 つの読み (A と B) の突き合わせ」)。 文でない手がかりも同じ向きに読める = 片方の名前に接尾語を付けた file 名 (`X_llm.py`)、 2 つを並べる見出し・表の列がいつも同じ順、 片方の道具が他方の結果を読む作り。 手がかりが部品 (2 つの道具) の中にあるか、 部品を包む入口の中にあるかを分けて読む: 部品の中の非対称 (片方だけが他方の出力の形を知る) は部品どうしの作った順として読める = 突き合わせを入口に移し、 部品からは外す。 入口の作り (片方の部品を入れていない機械では回さない・回す順・結果の表の列の順) は入口の設計として読め、 部品どうしの作った順は言わない (実測: 直した後に入口にだけ残ったこの形を、 部品の順を推し量らせると読んだのは読み過ぎだった) (2) 試し方を言う文 (docstring の「試験は合成データで行う」) = 入口の文書が自己試験を説明していれば要らず、 「合成データだけで試した」 とも読める (3) 作った人の過去の行い (「…の機械で測った値」) (4) 来歴の語を消して限定が外れた言い切り (「実データでいちばん確かな読み」 → 「いちばん確かな読み」) = 消した後に、 その文が今も正しいかを読む。 逆向き (事実と違う経緯を足していないか) も同じ回で読む。 点検する側は (1) (2) を「読みようによっては」 と軽く扱わない (実測: 語で探す点検がこの 2 つを「問いを招く程度」 に分け、 読み直すと作った順と試し方がそのまま読めた)。
- **上げたら読み戻し、 作り直せるようにする**: 共有なしで置き場に上げた file は、 置き場の API で共有の状態・権限・checksum を読み戻して手元の file と照らす (上げる道具の「共有なし」 の 1 行だけで済ませない)。 写しを作る手順 (直しの組を当てる script・zip を作る script) を記録の隣に置き、 元の道具の README から写しと作り直し方を指す = 元の道具を直すと、 写しは黙って古くなる。 写しを何回かに分けて直したら、 回ごとの script を当て済みの組を飛ばす形で積み、 最初の写しから全部を順に当て直した結果が今の写しと 1 字も違わないことを確かめる (一括置換の側の形 = [`batch-text-edits.md#global-replace-expected-count`](batch-text-edits.md#global-replace-expected-count))。

## <a id="quotation-extraction"></a>引用の抽出は「転記」ではなく「生成」

手書きの束ではなく、 **印刷された本・資料を撮って、 そこから引用を起こす**場合。 活字なので
「読めているはず」 という油断が入るが、 **モデルが画像から起こした引用は転記ではなく生成**で、
実測された逸脱は軽い順に:

| 逸脱 | 実例 |
|---|---|
| 語の置換 | 一語だけ別の語に (「学科」 → 「学業」)、 送り仮名・句読点の増減 |
| 文体の平準化 | 原文の古い言い回しを自然な現代語に直す (「〜やうです」 → 「〜やうだ」) |
| 圧縮・要約 | 原文の一段落を要点に縮めたものを引用ブロックに置く |
| **引用の創作** | **原文に存在しない鉤括弧つきの一文を作る** (= 地の文の趣旨を、 誰かの「批判の声」 として括弧に入れる等) |
| **典拠の創作** | 表の年・ページ番号を原文と違う値で書く |

どれも「読めませんでした」 とは申告されず**もっともらしい形で出力される**ので、 出力を眺めても
検知できない (= §pipeline の警告と同じ構造)。

### 規律

1. **load-bearing に使う前に 1 対 1 照合する。** 引用が主張の根拠になる文書 (記事・論文・報告)
   では、 全引用を原本と突き合わせるまで「引用済み」 と見なさない。
2. **照合した範囲を表で残す。** どの引用をどの頁で照合し、 未照合はどれか。 「全部見た」 という
   記憶は当てにならない。
3. **解像度は 1 コマ 1 頁 + 寄り。** 見開き 1 枚では、 散文は読めても**仮名 1 文字・数字 1 桁の
   判別には足りない** (実測: 見開き 1 枚で表の「15」 を「18」 と読み違え、 拡大して撤回)。 逐語
   照合には撮り直す。 低解像度の画像から読んだ主張は、 そう明記して出す。
4. **主張の土台が引用なら、 引用の逸脱はそのまま主張の逸脱。** 「創設当初から」 の根拠が表の年
   だったなら、 年を 1 つ創作した時点で主張が崩れる。 引用の照合は文体の問題ではなく主張の検査。

### <a id="correction-baseline"></a>原典を持つ人が直してきたら、まず自分の生成物を疑う

**差分の基準点を「直前の版」 に置くと、 他人の訂正が「改変」 に見える。** その版が未検証の生成物
なら、 基準点そのものが汚染されている。

実測: 生成した下書きを、 原本を持つ相手が原文どおりに直して返してきたのを、 「引用を勝手に
書き換えている」 と読んで指摘リストの最上位に置いた。 **原本の写真は手元にあり、 開けば 1 回で
分かった** (§規律 1 の安価な検証を回していなかった)。

- 訂正が来たら **まず自分の出力を疑う**。 相手が一次資料を持っているなら、 なおさら。
- **安価な検証を先に回す。** 手元に原本 (写真・PDF・スキャン) があるなら、 指摘を書く前に開く。
- それでも食い違って見えるときは **断定せず「こちらの読みではこう、 現物ではどうか」** で出す。
  低解像度の画像を根拠にした断定は、 相手の一次資料に対して弱い。

## <a id="parallel-transcription"></a>大量転記の分担

数十枚を超えると 1 session では持たない。 分担の型:

1. **spec を書く** — 対象・前処理コマンド・出力スキーマ・検算スクリプト・担当割り・
   「やらないこと」 を 1 file に。 **判断が要らない粒度まで落とす** (= 基準がぶれると
   統合時に揃わない)。 先行して 1 単位を自分で完成させ、 それを「書式の基準」 として
   spec から参照させると揃いやすい。
2. **part file に書かせる** — 同一 file を複数 session が触ると衝突する。
   `<name>-part{N}` に分け、 統合は起票元が行う。
3. **統合後に part file を削除** — 残すと同じ内容が 2 箇所にある状態 (= SoT 重複) になる。
4. **出力量の上限に注意** — 1 応答の出力上限を超えると worker が沈黙して死ぬ。 spec に
   「1 応答で N 単位を書き切ろうとせず追記していく」 と明記する
   ([`output-cap-death-loop.md`](output-cap-death-loop.md))。
5. **統合前に機械検査** — スキーマ・値域・重複・取りこぼし・対象集合との突合を script で。
   目視で揃っているかを確かめない。

## <a id="three-layer-sot"></a>データ / 導出 / 判断 の 3 層に分ける

転記が終わると、 成果物が混ざりやすい。 3 層に分けて **数字を 2 箇所に書かない**:

| 層 | 中身 | 規律 |
|---|---|---|
| **データ** | 台帳 + 転記本体 (verbatim + 個別の値) | ここだけが一次情報。 直すならここ |
| **導出** | 集計・突合・分析の **script** | **状態を持たない** (何も書かない)。 数字の正本はこの再実行結果 |
| **判断** | 所見・申し送り・次にどうするか | 散文の home。 **数字を書き写さず script を参照**する |

- 集計値を判断層に手書き転記すると、 データを直した瞬間に stale になる。 **再現コマンドを
  書いておく**方が寿命が長い。
- 導出 script の docstring に **方法上の限界**を書く (= 何を観測していないか、 n は足りるか)。
  判断層がそれを引けるようにしておくと、 後から読む人が過剰な結論を引き出さずに済む。

## <a id="reuse"></a>次回のための保存

spec は使い捨てにせず、 完了 banner (「今回分は完遂・次回は §X と §Y を更新すれば再利用可」)
を付けて残す。 次回に更新が要るのは**対象一覧と担当割りだけ**で、 前処理・書式・検算・規律は
そのまま効く。
