# Photographed document transcription — 撮影写真の一括転記

## <a id="scope"></a>場面

紙の束を**スキャナでなくカメラで撮った**写真 (= 斜め照明・机の写り込み・紙の湾曲・薄い鉛筆) を、
モデルに読ませて構造化データにするとき。 典型例は手書きの試験答案・手書きノート・受領した紙書類。

隣接する規約との分界:

- [`media-transcription-ledger.md`](media-transcription-ledger.md) = **定期的に届く画像 stream** を SoT 化する仕組み (transcript home + 読取 ledger + 未読 detector)。 「どの画像を読んだか」 の追跡が主題。 本 doc は **1 回の束を読み切る**ときの作り方が主題で、 継続 stream なら両方を使う。
- [`chalkboard-close-up-merge.md`](chalkboard-close-up-merge.md) = 板書写真の広域 + close-up を 1 page に合成する個別 recipe。
- [`audio-transcription.md`](audio-transcription.md) = **音声**の機械文字起こし。 §quotation-extraction の「転記でなく生成」 が同じ形で効くが、 原本が「見れば分かる」 形で残らないぶん照合が難しい (= 確定できない語は切り出して人に聞く)。

## <a id="pipeline"></a>全体の 5 段

```
1. 取り込み    写真を撮影順で連番化し、原本を不変の形で保存
2. 帰属確定    どの写真が誰/どの案件のものか → 台帳 (以後 変更しない)
3. 前処理      紙の切り出し + 照明ムラ除去 + コントラスト伸張 + タイル分割
4. 分担転記    spec を書いて複数 session へ → part file に書かせる
5. 統合・導出  本体 file へ統合 → 分割 file 削除 → 数字は script で導出
```

⚠️ **3 を飛ばして生写真を直接読ませない。** 薄い鉛筆は生のままだと読み違える。 これは
「読めなかった」 と自己申告される失敗ではなく、 **もっともらしい別の文字列を返す**失敗
なので、 出力を見ても検知できない。

## <a id="preprocessing"></a>前処理 — 何をするか、どこで転ぶか

実装: [`scripts/enhance-scan.py`](../scripts/enhance-scan.py) (docstring が使い方の正本)。

### 3 つの処理

1. **照明ムラ除去 (shading correction)**: 低周波成分でわり算して紙面を平坦化。 斜め照明で
   片側が暗い写真でも、 全面で同じしきい値が使えるようになる。
2. **紙の切り出し**: 机を捨てて画素を紙に集中させる。 画面の 4 割が机、 という写真は普通にある。
3. **コントラスト伸張**: 紙の地を基準に、 筆跡を黒側へ寄せる。

### <a id="preprocessing-traps"></a>実装で踏む罠 3 つ

| 罠 | 症状 | 正しいやり方 |
|---|---|---|
| **背景除算後の画像で紙を検出しようとする** | 紙も机も 1.0 付近になり全面が「紙」 判定 | 紙/机の判別は**除算前の低周波成分**で行う (= 紙は明るく机は暗い、 という大局的な差はそこにしか残らない) |
| **連結成分 + Otsu で紙領域を取る** | 机の照明反射 (ハイライト) が紙と繋がり、 外接矩形が全面になる | **行・列の明度プロファイルの最長連続区間**で取る。 小さい反射斑は profile では埋もれる |
| **切り出しを攻めすぎる** | 紙の縁が影で暗く、 内側を切り落として**行頭の記号や番号が欠ける** | 中点しきい値で芯を見つけ、 低しきい値で外側へ広げ直す 2 段構え。 **余白は広い側に倒す** (机が少し写る損 < 文字が欠ける損) |

もう 1 つ、統計の取り方:

- **紙の地は「高い percentile」 では取れない。** 光の反射が外れ値として上に出るので、
  percentile 99 は紙でなくハイライトを指す。 紙は画素の大多数なので **中央値が地**。
- percentile は**切り出し矩形の内側だけ**で取る。 矩形の縁に残った机に引っ張られると伸張が効かない。

### <a id="tile-size"></a>タイル分割はモデルの入力上限に合わせる

**モデルの画像入力には長辺の上限がある** (実務上 ~1568 px)。 これを超えるサイズを渡しても
内部で縮小されるだけで、 **1 文字あたりの画素はかえって減る**。

したがって「大きく渡す」 のではなく「**上限に収まる大きさに分割して複数枚渡す**」 のが正解:

| 原稿の密度 | 分割 | 1 タイルあたり |
|---|---|---|
| ふつうの手書き (A4 縦) | 上下 2 分割 | 紙幅いっぱい × 高さ半分 |
| 書き込みが密 | 格子 4 行 × 2 列 程度 | さらに細かく |
| 極端に密 | 5x2 / 4x3 へ上げる | — |

- 隣接タイルは数 % 重ねる (= 境界にまたがる行を落とさない)。
- 紙が横向きに写っている写真は先に回転させてから分割する。
- 分割を増やすほど読めるが、 その分だけトークンを食う。 **薄い/密なものだけ細かく**する。

## <a id="attribution"></a>帰属の確定と独立検証

写真 → 対象 (人・案件) の対応付けは、 **確定したら以後変更しない台帳**に固定する
(以降の全工程がこの台帳を参照するので、 途中で動かすと全部ずれる)。

問題は **1 枚目にしか識別情報が無い**場合。 裏面・2 枚目には名前が書かれていないことが多く、
「撮影順で直前の表面と同じ対象」 という**隣接推論**に頼ることになる。 これは撮影運用への
依存なので、 必ず裏付けを取る:

- ✅ **2 つの独立な集合の一致**を見る。 同じ対象について**別々に撮った 2 系統**があるなら
  (例: 本体書類と付属書類)、 両者から得た対象集合が完全一致することを確認する。 撮影順が
  系統ごとに違えば、 片方で 2 人を 1 人に潰す誤りは他方と食い違って露見する。
- ✅ 台帳内の**構造検査**: 同一対象の連番が連続しているか、 1 枚目が表で 2 枚目が裏か、
  1 対象あたりの枚数が想定内か。
- ✅ 原本ファイルの **sha256 を台帳に持たせる** (= 後から「この写真は本当にこれか」 を照合できる)。

⚠️ 隣接推論に頼った箇所は、 台帳に**そう明記する** (「氏名の記載がある N 枚以外は隣接で帰属」)。
後で誰かが「全部読み取って確定した」 と誤解するのを防ぐ。

## <a id="fidelity"></a>転記の忠実性

- **verbatim は原本のまま。 誤記・誤植も直さない。** 転記が判断の根拠になる用途 (採点・監査・
  引用) では「本人が実際に書いたもの」 が要る。 直した瞬間に根拠として使えなくなる。
- **判読できない箇所は推測で埋めず marker を置く** (`[判読不能]` 等)。 撮影写真の読み取りは
  「読めない」 と「もっともらしい別の文字列」 の距離が近い。 **読めないことを正直に記録した
  方が、 埋めた推測より価値が高い**。
- 原本の**物理的配置と論理的順序が食い違う**場合 (= 書かれた順が項目順でない) は、
  **論理順に並べ替えて転記し、 物理配置は別フィールドに書く**。 両方を保つ。
- 所見・判断は verbatim と**別フィールド**にする。 混ぜると後から「どこまでが原本か」 が
  分からなくなる。

## <a id="quotation-extraction"></a>引用の抽出は「転記」ではなく「生成」

手書きの束ではなく、 **印刷された本・資料を撮って、 そこから引用を起こす**場合。 活字なので
「読めているはず」 という油断が入るが、 **モデルが画像から起こした引用は転記ではなく生成**で、
実測された逸脱は軽い順に:

| 逸脱 | 実例 |
|---|---|
| 語の置換 | 一語だけ別の語に (「学科」 → 「学業」)、 送り仮名・句読点の増減 |
| 文体の平準化 | 原文の古い言い回しを自然な現代語に直す (「〜やうです」 → 「〜やうだ」) |
| 圧縮・要約 | 原文の一段落を要点に縮めたものを引用ブロックに置く |
| **引用の創作** | **原文に存在しない鉤括弧つきの一文を作る** (= 地の文の趣旨を、 誰かの「批判の声」 として括弧に入れる等) |
| **典拠の創作** | 表の年・ページ番号を原文と違う値で書く |

どれも「読めませんでした」 とは申告されず**もっともらしい形で出力される**ので、 出力を眺めても
検知できない (= §pipeline の警告と同じ構造)。

### 規律

1. **load-bearing に使う前に 1 対 1 照合する。** 引用が主張の根拠になる文書 (記事・論文・報告)
   では、 全引用を原本と突き合わせるまで「引用済み」 と見なさない。
2. **照合した範囲を表で残す。** どの引用をどの頁で照合し、 未照合はどれか。 「全部見た」 という
   記憶は当てにならない。
3. **解像度は 1 コマ 1 頁 + 寄り。** 見開き 1 枚では、 散文は読めても**仮名 1 文字・数字 1 桁の
   判別には足りない** (実測: 見開き 1 枚で表の「15」 を「18」 と読み違え、 拡大して撤回)。 逐語
   照合には撮り直す。 低解像度の画像から読んだ主張は、 そう明記して出す。
4. **主張の土台が引用なら、 引用の逸脱はそのまま主張の逸脱。** 「創設当初から」 の根拠が表の年
   だったなら、 年を 1 つ創作した時点で主張が崩れる。 引用の照合は文体の問題ではなく主張の検査。

### <a id="correction-baseline"></a>原典を持つ人が直してきたら、まず自分の生成物を疑う

**差分の基準点を「直前の版」 に置くと、 他人の訂正が「改変」 に見える。** その版が未検証の生成物
なら、 基準点そのものが汚染されている。

実測: 生成した下書きを、 原本を持つ相手が原文どおりに直して返してきたのを、 「引用を勝手に
書き換えている」 と読んで指摘リストの最上位に置いた。 **原本の写真は手元にあり、 開けば 1 回で
分かった** (§規律 1 の安価な検証を回していなかった)。

- 訂正が来たら **まず自分の出力を疑う**。 相手が一次資料を持っているなら、 なおさら。
- **安価な検証を先に回す。** 手元に原本 (写真・PDF・スキャン) があるなら、 指摘を書く前に開く。
- それでも食い違って見えるときは **断定せず「こちらの読みではこう、 現物ではどうか」** で出す。
  低解像度の画像を根拠にした断定は、 相手の一次資料に対して弱い。

## <a id="parallel-transcription"></a>大量転記の分担

数十枚を超えると 1 session では持たない。 分担の型:

1. **spec を書く** — 対象・前処理コマンド・出力スキーマ・検算スクリプト・担当割り・
   「やらないこと」 を 1 file に。 **判断が要らない粒度まで落とす** (= 基準がぶれると
   統合時に揃わない)。 先行して 1 単位を自分で完成させ、 それを「書式の基準」 として
   spec から参照させると揃いやすい。
2. **part file に書かせる** — 同一 file を複数 session が触ると衝突する。
   `<name>-part{N}` に分け、 統合は起票元が行う。
3. **統合後に part file を削除** — 残すと同じ内容が 2 箇所にある状態 (= SoT 重複) になる。
4. **出力量の上限に注意** — 1 応答の出力上限を超えると worker が沈黙して死ぬ。 spec に
   「1 応答で N 単位を書き切ろうとせず追記していく」 と明記する
   ([`output-cap-death-loop.md`](output-cap-death-loop.md))。
5. **統合前に機械検査** — スキーマ・値域・重複・取りこぼし・対象集合との突合を script で。
   目視で揃っているかを確かめない。

## <a id="three-layer-sot"></a>データ / 導出 / 判断 の 3 層に分ける

転記が終わると、 成果物が混ざりやすい。 3 層に分けて **数字を 2 箇所に書かない**:

| 層 | 中身 | 規律 |
|---|---|---|
| **データ** | 台帳 + 転記本体 (verbatim + 個別の値) | ここだけが一次情報。 直すならここ |
| **導出** | 集計・突合・分析の **script** | **状態を持たない** (何も書かない)。 数字の正本はこの再実行結果 |
| **判断** | 所見・申し送り・次にどうするか | 散文の home。 **数字を書き写さず script を参照**する |

- 集計値を判断層に手書き転記すると、 データを直した瞬間に stale になる。 **再現コマンドを
  書いておく**方が寿命が長い。
- 導出 script の docstring に **方法上の限界**を書く (= 何を観測していないか、 n は足りるか)。
  判断層がそれを引けるようにしておくと、 後から読む人が過剰な結論を引き出さずに済む。

## <a id="reuse"></a>次回のための保存

spec は使い捨てにせず、 完了 banner (「今回分は完遂・次回は §X と §Y を更新すれば再利用可」)
を付けて残す。 次回に更新が要るのは**対象一覧と担当割りだけ**で、 前処理・書式・検算・規律は
そのまま効く。
