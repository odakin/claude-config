# ポッドキャストの仕上げ（ジングル・音量・書き出し）

分割済みの本編 1 本に、ジングルを頭と尾に付け、音量を揃えて配信用ファイルに書き出す場面。
機械化 = [`scripts/audio-finish-episode.py`](../scripts/audio-finish-episode.py)。番組ごとの値
（ジングル、タグ、冒頭ジングルを切る位置、本編ごとの頭の削り）は、呼び出し側の薄い入口で渡す。

前段（文字起こし・分割）は [`audio-transcription.md`](audio-transcription.md)。

## <a id="loudness-target"></a>音量の目標: -16 LUFS ±1、true peak -1 dBTP 以下

- [Apple Podcasts の公式要件](https://podcasters.apple.com/support/893-audio-requirements) は
  **-16 LKFS ±1 dB、true peak ≤ -1 dBFS**（ITU-R BS.1770 で測る）。ほかの配信先は再生時に音量を揃えるので、
  ピーク側の条件が厳しいこの値に合わせておけば困らない。Spotify を -14 LUFS とする記事もあるが、公式ページでは未確認
- **ジングルも本編も同じ値に揃える**。LUFS は聴感の大きさを測る尺度なので、まず同じにしてから聞いて調整する
  （音楽のジングルは話し声より 5〜7 dB 大きいのが普通、実測）。調整するなら「ジングルを何 LU 下げるか」で持つ
- 本編ごとに大きさが違う（同じ番組でも 2 dB ほど、実測）ので、ジングルだけを本編に合わせるやり方だと回ごとに音量が揃わない

## <a id="limiter-oversampled"></a>ピークは 192 kHz で掛けたリミッターで抑える

本編を目標まで上げると、元の山が上限を越える。削る必要がある。

- 48 kHz のまま削ると、サンプルとサンプルの間に立つ山（true peak）が残る。**192 kHz に上げてから削り、戻す**
- 上限は -1.0 でなく **-1.5 dBFS** にする。MP3 にすると山が少し伸びる（実測で 0.4 dB 前後）
- **ffmpeg の `alimiter` の罠 2 つ**:
  - `level` は既定で有効で、出力を上限まで**自動で持ち上げる**（音量が勝手に変わる）→ `level=0`
  - 先読みの遅延を補正しない（頭がずれて尾が欠ける）→ `latency=1`
- **`loudnorm` だけで済ませない**: 目標の音量とピークを同時に満たせないとき、数秒単位で音量を自動で上げ下げする
  モードに**黙って切り替わる**。話の間や声の大小が平らになる
- 削った量（削る前のピーク − 上限）を記録する。6 dB を超えたら、大きな笑い声などの箇所を聞いて歪みを確かめる

## <a id="measure-rerender-loop"></a>書き出したら測り直す（1 回で合うと思わない）

リミッターで山を削ると本編の積分音量が少し下がり、MP3 にすると山が少し伸びる。どちらも書き出してみないと量が分からない。

1. 入力を測る → 利得を決める → 連結・リミッター・**符号化は最後に 1 回だけ**（圧縮音声は符号化のたびに劣化する）
2. 出力を測る: 全体・本編区間・冒頭ジングル区間の積分音量、true peak
3. 本編区間が目標から外れた分を利得に足し、true peak が上限を越えた分だけリミッターの上限を下げて作り直す（数回で収まる）
4. 検査: 全体 ±1 LU / true peak / 本編区間 ±0.5 LU / ジングル区間 / **長さ = 冒頭ジングル + 本編 + 締めジングル**
   （MP3 の前後の詰め物ぶん ±0.15 秒）/ **入力のメタデータが残っていない**（作者欄などが配信ファイルに持ち越されるため、
   タグは付け直す）
5. 検査に落ちた出力は名前を変えて残し（配信用と取り違えない）、試した利得・上限・測定値を JSON に残す

検査が飾りでないことも確かめる: 無理な目標（例: -6 LUFS）では落ちること。

## <a id="edge-fades"></a>本編の頭と尾: 短くフェードし、切れた断片は聞いて削る

- ジングルの余韻が**完全な無音**まで落ちた直後に、本編が 10 ミリ秒で -18 dB まで立ち上がると、
  **プツッという雑音に聞こえる**（実測）。録音開始の本編は話の途中から始まることが多い
- 対処 1: **本編の頭 0.03 秒・尾 0.05 秒を必ずフェードする**（尾は、話の途中で切れた本編からジングルへつなぐため）
- 対処 2: 頭に**切れた語の断片**や「うん」「ろ」のような意味の無い音があれば、最初の文の立ち上がりの少し手前
  （部屋の静かな音だけの所、例: 0.08 秒前）から始める
- **削るかどうか・どこまで削るかは聞いて決める**: 断片に見える音が語の頭そのものの場合がある。短い区間だけを
  機械で文字起こしすると、長い区間とは別の語が出る（実測: 同じ冒頭が短い窓では「うん、ろ」、長い窓では語の一部として吸収された）
- 聞き比べの候補ファイルは、**名前の先頭で区別が付くようにする**。共通の接頭辞に A/B/C を付けただけの名前は、
  プレーヤーの窓の題名が途中で切れて区別できない（実測）。中身を名前にする（例: `よしから始める版.mp3`）
- 削った秒数は、書き出しの記録（JSON）と素材の目録に書く（作り直すときに同じ値を使う）

## <a id="intro-jingle-silence"></a>冒頭ジングルの後ろの長い無音は切る

ジングルのファイルは、音が消えた後に数秒の無音を持っていることがある。冒頭にそのまま置くと、話し始めまでが空きすぎる
（実測: 3 秒強の空白は長すぎる）。

- ジングルの音が **-60 dB を最後に越える時刻**を測り、その少し後（0.5 秒前後）で切る。切り口は 0.2 秒ほどでフェードする
- 締めのジングルは切らない（回の終わりは余韻のまま終わってよい）
- 切る位置はジングルごとの値なので、番組側の入口に持つ

## <a id="measure-from-file-head"></a>区間の長さはファイルの頭から測る

MP3 を途中の時刻から切り出して（`-ss` で頭出しして）測ると、**先頭の数十ミリ秒が無音に見える**ことがある。
その区間を「無音の始まり」と拾い、空白の長さを実際より長く出してしまう（実測: 0.7 秒の空白が 1.5 秒と出た）。
区間の境目や空白の長さは、ファイルの頭から読み込んで時刻で数える。

## <a id="listen-checklist"></a>機械では確かめられない所（人が聞く）

1. 頭: ジングル → 本編の最初の一言
2. ジングルの大きさ: 声と比べて大きすぎ／小さすぎないか
3. 尾: 本編の最後 → ジングル
4. リミッターの削り量が大きかった本編の、大きな笑い声などの箇所

## <a id="when-a-check-fails"></a>検査に落ちたとき

| 落ちた検査 | よくある原因 | 対処 |
|---|---|---|
| true peak | 削る量が大きく、MP3 化で山が伸び続けた | 作り直しの回数を増やす前に、本編に大きな雑音や機材トラブルが無いか疑う |
| 本編区間の音量 | 本編が極端に小さく、リミッターが効きっぱなし | 削り量が 10 dB を超えるなら収録の問題。目標を下げて出すか相談する |
| ジングル区間の音量 | ジングルが極端に短い・無音が長い | ジングル単体を測る。無音が長いと区間の測定が不安定になる |
| 長さ | 入力の音声が途中で切れている・先頭に空白がある | 本編の長さと開始時刻を確かめる。頭尾を削ったなら、削った後の長さで勘定しているか |
| タグ | ffmpeg の版で付くタグが変わった | 余分なタグ名を見て、無害なもの（エンコーダ名の類）なら除外に足す |
