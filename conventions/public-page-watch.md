# 公開ページの告知を見張る

「受付を再開したらすぐ出す」「日程が動いたら直す」 のように、 **いつ変わるか分からないが、 変わったら
すぐ動く**告知を待つ場面の規約。 人が「その頃に見る」 と覚えておく形は、 見に行く日がずれた・その日に
手が塞がっていた、 のどちらでも黙って遅れる ([`convention-design-principles.md#human-memory-not-a-carrier`](../docs/convention-design-principles.md#human-memory-not-a-carrier))。
先着順や予算の範囲で締め切られる告知では、 遅れはそのまま取りこぼしになる。

道具 = [`scripts/web-page-watch.py`](../scripts/web-page-watch.py) (台帳 + 目印 + state + 通知、 `--selftest`) と
[`scripts/headless-push-notification.sh`](../scripts/headless-push-notification.sh) (スマホ push、 `--probe`)。
定期実行の登録は [`scheduled-tasks.md`](scheduled-tasks.md) (local 通知は受け手の Mac ごと = `#per-recipient-notification-locus`)。

## <a id="announcement-sot-layers"></a>1. 告知の正本は層になっている — 記録には読んだ版を書く

行政・学会・大学などの告知は、 1 枚のページが全部を決めているわけではない。 よくある層:

| 何を知りたいか | 正本 | 例 |
|---|---|---|
| 今受け付けているか・いつ再開するか | その告知のページ (「本ページでお知らせします」 と書かれていることが多い) | 受付中止・再開・予算の残り |
| 要件・金額・期間・提出書類 | 要綱・規程・募集要項 (制定と改正の日付を持つ) | 対象期間・必要書類の一覧 |
| 要綱に書いていない運用 | 案内・パンフレット・FAQ | 受付の順序・書類の細かい形式・代わりに認める書類 |

- 記録 (台帳・TODO) には**どれを正本にしたか**と、 **読んだ版** (ページの更新日・要綱の最後の改正日) を書く。
  手元の要点は写しと明記する
- **動く直前に版を見比べる**。 受付の再開や年度替わりは、 要綱・様式の改正と同時に来ることがある
- 案内 (パンフレット) と要綱が食い違う・案内にしか書いていない決まりがあるときは、 両方を出典つきで記録する

## <a id="marker-extraction"></a>2. 見張る範囲は目印で切る

ページ全体の hash を比べると、 ナビ・関連リンク・フッタ・アクセス数の変化で毎日鳴り、 すぐ誰も見なくなる。

- 台帳の各ページに**本文の始まりと終わりの目印** (`start` / `end`) を持たせ、 その間の本文だけを比べる。
  多くの CMS では「更新日」 の行から「お問い合わせ」 の手前が本文
- 目印は**実ページで 1 回切り出して確かめてから**台帳に入れる (本文の途中で切れると、 肝心の告知が範囲外になる)
- 目印が見つからない = ページの作りが変わった。 これは 1 回目から知らせる (黙って比べられなくなるのが最悪)
- HTML を行にするときは block 要素の**開きタグでも**改行する (閉じタグの無い文と次の段落が 1 行に繋がり、
  終わりの目印を含む行ごと範囲から落ちる = 実測)
- 見張りには**期限** (`until`) を付ける。 理由が消えた見張りを台帳に残し忘れない

## <a id="action-first-message"></a>3. 知らせる文は「今すぐ何をするか」 まで書く

「ページが変わった」 だけの通知では人は動かない。 開いて差分を読み、 何をすべきか思い出す手間が、
その場で後回しにさせる。 知らせる文は 1 行で:

> <何が> 変わった (<決め手>) → 今すぐ: <やること> [<案件の記録の場所>]

- **決め手** = 変化を判定する文言。 「受付を中止しています」 が**消えた**、 「日程を変更しました」 が**出た**、 のように、
  確認済みの本文と最新の本文を比べて文言の消失・出現を添える (台帳の `signals`)。 外れても本文が変われば知らせる
- **やること**は、 その場で手を動かせる粒度で書く (送り先・持っていくもの・締切の性質まで)。
  後で探す前提にしない
- 同じ文を、 dashboard の行・通知・ダイアログ・スマホ push のすべてに使う (面ごとに書き分けると、 短い方が勝つ)

## <a id="layered-notification"></a>4. 知らせる面を重ねる — バナーは単独で頼らない

macOS のバナー通知は数秒で消え、 通知センターは開かない限り見えない。 画面の前に居ても見落とす。

| 面 | 性質 | 使いどころ |
|---|---|---|
| dashboard の**最上段** | 確認 (`--ack`) するまで出続ける。 期限超過の一覧より上 | すべての変化 |
| session 開始時の注入 | 同上。 注入を 1 ブロックに畳む仕組みがあっても畳まない (出るのは行動に直結するときだけ) | すべての変化 |
| 押すまで消えないダイアログ | 画面の前に居れば見落とさない。 定期実行を止めないよう切り離して起動 | 急ぐもの (`urgent`) |
| スマホへの push | 画面の前に居ないとき。 ⚠️ キーボード操作中は送られない仕様がある = そのときはダイアログが受け持つ | 急ぐもの |
| バナー | 補助 | すべて |

- **急ぐもの**だけに大きい面 (ダイアログ・push) を使う。 全部に使うと、 急ぐものが来たときに押し慣れて閉じる
- 確認の記録 (`--ack`) はマシンごと。 複数のマシンで見張るなら、 どちらでも出る前提で文を書く

## <a id="surface-reads-state-only"></a>5. dashboard と session hook は state を読むだけ

巡回 (network に出て比べる) は定期実行の 1 か所だけにし、 dashboard や session 開始時の hook は
**巡回が残した state を読むだけ** (`--surface`) にする。

- 表示側で巡回すると、 そこで「新しい本文を見た」 と記録され、 **定期実行の側が通知しなくなる** (= 大きい面に届かない)
- 表示側には、 巡回が止まっている (最後の巡回からの時間) も出す。 定期実行が死ぬと、 見張りは黙って空になる

## <a id="probe-each-run"></a>6. 追加の経路は巡回ごとに健康診断する

スマホ push のような追加の経路は、 **実際に変化が起きたときに初めて使われる**。 その時点で壊れていると分かっても遅い。

- 巡回ごとに、 token を使わない軽い検査 (`--probe` = CLI が見つかるか・ログイン済みか) を回し、
  失敗している間は dashboard / session 開始時に ⚠️ を出す
- 実際に送って失敗したときも、 log だけでなく state に残し、 次に成功するまで出し続ける
- 検査は**本物の定期実行の環境で**回す。 対話 shell では通っても、 launchd の PATH には CLI が無かった (実測、
  この検査が見つけた)。 逆に `env -i` で環境を空にした試験は厳しすぎ、 USER 等が無いと keychain の
  認証が読めず「未ログイン」 と誤判定した (実測) = launchd の job を手で起動して確かめる

## <a id="sealed-headless-push"></a>7. headless `claude -p` を通知の送信だけに使うときは閉じる

PushNotification は headless `claude -p` からも呼べる (`scheduled-tasks.md`)。 ただし普段の設定のまま起動すると、
**通知を送らずに別の仕事を始める** (実測: config dir の Stop hook が求める処理に引っ張られ、 手元の MCP で
メールを読み始めた)。 送信だけの run に閉じる:

- **hook を止める** = `--settings '{"disableAllHooks":true,"remoteControlAtStartup":false}'`
- **MCP を外す** = `--strict-mcp-config` を `--mcp-config` なしで付ける (`--tools` で絞っても MCP の tool は残った)
- **project の外で起動する** = CLAUDE.md の自動読込を避ける
- **prompt は stdin で渡す** = `--tools <tools...>` は可変長で、 後ろに置いた位置引数の prompt まで tool 名として
  飲み込み「Input must be provided」 で落ちる (実測)
- **使う config dir を明示する** = 既定の `~/.claude` は account の切替で変わり、 未ログインのマシンもあった (実測)。
  届けたい account に pin した dir を使う
- **成否は出力の印で判定する** = prompt で `PUSH_RESULT <tool の結果>` を 1 行出させ、 無ければ失敗
- `--bare` は hook を止めるが OAuth を使えなくなる (API key 前提) ので、 この用途には使えない
- launchd は LANG 空なので prompt は ASCII にし、 多バイトの本文は file に書いて Read させる

道具 = [`scripts/headless-push-notification.sh`](../scripts/headless-push-notification.sh) (env `CLAUDE_PUSH_CONFIG_DIR` / `CLAUDE_PUSH_TITLE`、 `--probe`)。

## 手順 (新しい告知を見張る)

1. §1 で正本を決め、 読んだ版を案件の記録に書く
2. 台帳に 1 entry: `id` / `url` / `label` / `start`・`end` (§2、 実ページで切り出しを確認) / `until` / `action` (§3) /
   急ぐなら `urgent: true` と `signals` / `note` に案件の記録の場所
3. 1 回巡回して基準を作る (初回は基準にするだけで知らせない)
4. 定期実行に `--notify --alert --on-change <push> --probe "<push> --probe"` を、 表示側に `--surface` を配線 (§4〜§6)
5. 合成の変化 (state の基準を 1 行ずらす) で、 dashboard・ダイアログ・push の文面を 1 回ずつ確かめてから戻す
