# 科研費 研究計画調書 — 審査基準への正対と紙面設計

公募要領・様式の年度個別値はその年の公募要領が正本。本 doc は**年度をまたいで効く機構知見**のみ
(2026-08 の挑戦的研究(萌芽) 調書作成の実測から)。sibling: e-Rad フォーム機構 =
[erad-submission.md](erad-submission.md) / JPS 講演申込 = [jps-talk-submission.md](jps-talk-submission.md) /
LaTeX 紙面の罠 = [latex.md](latex.md) / 図の機械 QA = [matplotlib-figure-qa.md](matplotlib-figure-qa.md)。

## <a id="review-criteria-alignment"></a>審査基準 (評定要素) を取得して欄構成を正対させる

JSPS は種目別の**書面審査における評定基準等** (審査委員に渡る評定要素の全文) を公開している
(jsps.go.jp の審査関係規程ページ)。調書を書く前・仕上げる前に**必ず現物を取得**し、
評定要素の各項目に「調書のどの段落が答えるか」をマップする。実測での効き方:

- **評定要素にあるのに調書に対応段落が無い項目が炙り出せる**。挑戦的研究の評定要素は
  (1) 挑戦的研究としての妥当性 (2) 研究目的・計画の妥当性 (3) 研究遂行能力 (4) **研究課題の
  波及効果** (学術・科学技術・産業・文化など幅広い社会へのインパクト) の 4 つで、
  (4) は書き手が自然には書かない = 明示的な段落を与えないと審査員に材料が渡らない。
- **評定要素の literal キーワードを見出しに掲げる**と審査員の checklist 照合が速い。
  例: 萌芽は「**探索的性質の強い、あるいは芽生え期**の研究計画の場合には可能性を有するか」が
  評定要素の文言 → 「探索的性質と芽生え期の可能性——なぜ萌芽か」のような見出しで正対する。
- 審査 process の機構も同文書にある。挑戦的研究は応募多数だと**事前の選考** (プレスクリーニング)
  があり、評点分布は 4=10% / 3=10% / 2=10% / **1=70%** の相対評価 — 事前選考が参照する様式
  (概要版) が生死を握る。概要版と本審査様式が独立に読まれる種目では両方を自己完結に書く。
- 「答えがどちらであっても成果になる」型の主張 (either-way wins) は、挑戦性と実現可能性の
  両評定要素に同時に効く — 高 risk の問いには入れる価値が高い。

## <a id="layout-pendulum"></a>紙面設計 — 詰めすぎ⇄空きすぎの振り子を頁数制限の中で

頁数上限との攻防で紙面は「隙間が空きすぎ (書けるのに書いていない)」と「ぎっしりで読む気が
しない」の間を振り子する。実測で収束した型:

- **見出しは run-in (段落頭の太字) でなく独立行 + 前後空き**。壁が節に割れ、斜め読みで骨格が
  拾える。`\newcommand{\gh}[1]{\par\vspace{.5em}\noindent\textbf{#1}\par\vspace{.1em}\noindent}` 程度。
- 空白を「詰める」のは頁が本当に溢れる時だけ。**頁下端に余裕があるのに float 間隔や
  caption 下を負の `\vspace` で詰めない** (過去の圧縮の残骸が読みづらさとして残りやすい —
  溢れが解消したら詰め物も戻す)。
- 収める順序: 図中と caption の重複説明を削る → 文単位のトリム (文字数トリムは折り返しに
  吸収されて行数が減らないことが多い) → 文献リストの `\small` 化 → 最後に間隔。
- **図の canvas 高さは本文行の回収源**: 実寸フォント設計 (文字 pt を canvas サイズと独立に固定) で
  作った matplotlib 図なら、figsize の高さだけ削っても文字は小さくならない — 0.1 in ≈ 0.6 行を
  可読性を落とさず回収できる (2026-09 実測: 3.8→2.9 in で約 5 行、ラベル衝突なし)。
- 引用の絞り方・業績統計は [#track-record-section](#track-record-section) 参照 (欄 2 側の紙面にも効く)。
- **審査はモノクロ印刷**の種目が多い (公募要領に明記)。図は白黒設計 + グレースケール検版
  PDF を毎ビルド生成して確認する。
- キャプション・行内数式の行かぶり検査と wrapfigure の罠は [latex.md](latex.md) の各 anchor
  (`#pdf-line-collision-detection` / `#wrapfig-caption-page-overflow-loss` 等) を参照。

## <a id="web-submission-system"></a>科研費電子申請システムの機構

- **毎日早朝 5:00 にシステム再起動**があり、またいだ編集は保存されない (トップページに明記)。
  長い入力セッションはこまめに「一時保存」。
- **応募情報は審査終了後の所定日に削除される** (毎年トップページで告知)。翌年度の再応募で
  流用するなら削除前に各自保存が必要 — 調書 source を手元リポで管理していれば実害はないが、
  Web 入力欄 (応募情報) の値は別途控える。
- 添付ファイル項目 (PDF) の登録後は、システム生成の**提出確認用 PDF を白黒で検品**する
  (崩れ・文字化け確認は公募要領上の義務)。
- ログイン ID/パスワードは e-Rad と共通 (e-Rad 側で変更すると反映に 30 分〜1 時間)。

### <a id="keihi-csv-import"></a>経費明細の CSV 一括取込 (2026-08 実測)

「研究経費とその必要性」画面の明細 (費目×年度×事項×金額の行群) は CSV 取込で一括投入できる。
手入力 30–50 行が 1 操作になるので、行数が多ければ迷わず CSV。仕様は画面の「フォーマットを
ダウンロード」で得られるヘッダ行から読み取れるが、罠が 2 つ:

- **エンコーディング = Shift-JIS (CP932) + CRLF**。UTF-8 は文字化けする。
- **費目区分は「A」〜「F」の記号指定** (画面の費目表示順: A=設備備品費 / B=消耗品費 /
  C=国内旅費 / D=外国旅費 / E=人件費・謝金 / F=その他)。日本語の費目名を書くと
  全行「費目項目が「A」〜「F」ではありません」で弾かれる。年度は西暦 4 桁。
- 8 列 = 費目区分 / 年度 / 品名・仕様 (設備のみ) / 設置機関 (設備のみ) / 事項 (設備以外) /
  数量 (設備のみ) / 単価 (設備のみ) / 金額。
- script で生成するなら、**年度別合計・費目別合計を予算表と assert で突合してから**書き出す
  (取込後の画面の「再計算」値と予算表の一致が最終確認)。

### <a id="keihi-meisai-granularity"></a>経費明細の粒度 — 事務チェックが必ず突く 3 点

金額の合計が合っていても、**行の書き方**で差し戻される。2026-09 に 4 種目同時で同じ 3 点を
指摘された (= 種目非依存の定型チェック項目とみなしてよい):

1. **設備備品費は「品名・型番」まで書く**。「数値計算用計算機」だけでは通らず、
   「〜用計算機（用途）・〈製品名 / メモリ等の仕様〉相当」まで要る。"相当" を付ければ
   特定ベンダーへの拘束にはならない。
2. **1 行に複数事項を詰めない**。「論文投稿・掲載料、クラウド計算資源利用料」は 2 行に割る
   (事務の指示は「別項目となるため行を分けて計上してください」)。**費目内の内訳が見えることが
   目的**なので、同種のものを 1 行にまとめるのは可。
3. **旅費は 事項欄に「場所・日数・人数」**。「国際会議での成果発表」→「国際会議での成果発表
   （欧州または米国、年 1 回、7 日間、1 名）」。行き先未定なら「〈地域〉または〈地域〉」で可。
   国内も「（年 2 回、各 1 泊 2 日、1 名）」まで。同じ内訳を**必要性テキスト側にも反映**する
   (明細と必要性で内訳が食い違うと再差し戻し)。

派生規律: 明細を script 生成するなら、必要性テキストも**同じ data から**書き出すか、
少なくとも同じ file に隣接させて置く (= 明細だけ直して必要性が旧内訳のまま残る drift の防止)。

### <a id="keihi-meisai-field-limits"></a>明細の各欄にはバイト上限がある — 「場所・日数・人数」を足すと踏む

上の 3 点 (特に旅費の「場所・日数・人数」) を素直に書くと、**「事項」欄の上限 72 バイト
(全角 1 文字 = 2 バイト、半角 = 1 バイト → 全角 36 字) を超える**。超過は CSV 取込時ではなく
**一時保存時に行番号つきの error** で返り、error が 1 つでも残ると画面の入力全部が保存されない
(2026-09-08 実測: 「国内旅費：事項 - 1行目は72バイト以内で入力してください」。CSV 取込自体は
通ってしまうので、必要性テキストまで貼ってから発覚し、4 種目分の CSV を作り直す羽目になった)。
実測で分かっている上限 (他の欄は未計測、超えたら error 文が上限を教えてくれる):

| 欄 | 上限 | 備考 |
|---|---|---|
| 各費目の「事項」 (消耗品費 / 国内旅費 / 外国旅費 / 人件費・謝金 / その他) | **72 バイト** | 全角 36 字 |
| 設備備品費の「品名・仕様」 | 72 より大 (77 バイトが通った) | 正確な上限は未計測 |
| 必要性テキスト (2 欄) | 500 字 / 改行 3 回 (画面に明記) | 改行は 1 回 = 全角 1 字換算 |

規律: **明細を生成する script は「事項」を書く時点で 72 バイトを assert する** (取込前に落とす)。
書き方の型 = 「〈用件〉（〈場所〉、年 N 回、各 M 泊、K 名）」で 36 字に収まるよう、用件側を削る
(「〜への参加と〜との研究打合せ」→「〜・〜との打合せ」、「対面研究打合せ」→「研究打合せ」)。
「場所・日数・人数」は落とさない (= 粒度の指摘の方が再差し戻しに直結する)。

### <a id="confirmation-pdf-detail-rows"></a>提出確認用 PDF に経費明細の行が印字されるかは種目で違う

基盤研究・挑戦的研究の提出確認用 PDF には「各経費の明細」の全行 (事項・金額) が印字されるが、
**学術変革領域研究(A) 公募研究 (S-74) の確認用 PDF には費目ごとの年度合計 (設備 / 消耗品 / 旅費 /
人件費・謝金 / その他) しか出ない** (2026-09-08 実測、2 件とも)。入力後の機械突合を「明細の各行が
PDF に在るか」で組むと、公募研究では全行 ✗ になって verifier が壊れる。突合は種目に応じて
(a) 明細行の literal (印字される種目) / (b) 費目 × 年度の合計 (印字されない種目) の 2 段で書く。
「研究費の応募・受入等の状況」は全種目とも確認用 PDF に含まれないので別途 (画面印刷 or 確認画面の
全行照合) — [#submission-artifact-staging](#submission-artifact-staging) 3 参照。

### <a id="textfield-wavedash-entity"></a>テキスト欄の波ダッシュは PDF に「&amp;#12316;」と焼かれる

Web 入力のテキスト欄 (経費の必要性等) に**波ダッシュ「〜」(U+301C) を貼ると、システム生成の
提出確認用 PDF に HTML 実体参照の文字列 `&#12316;` がそのまま印字される** (2026-08 実測。
入力・確認画面では正常に見えるため気づきにくい)。対策:

- テキスト欄では「〜」を使わない (「から」「1、2名」等に言い換える。全角チルダ「～」も
  同系の変換系を通るため避けるのが安全)。
- **検品を機械化する**: 提出確認用 PDF を PyMuPDF 等でテキスト抽出し、正規表現
  `&#\d+;|&[a-z]+;` の全頁掃引で実体参照の残置ゼロを確認する。あわせて図の入る頁を
  グレースケールで render して CJK ラベルの化け・キャプション切断を目視する
  (審査はモノクロ印刷。図の作り側の gate は `matplotlib-figure-qa.md`)。
- 添付様式が複数ある種目 (挑戦的研究の概要版+本文等) では提出確認用が **ZIP** で来る
  (中に本文 PDF と `GAIYO_` 概要 PDF)。

### <a id="oubo-jokyo-form"></a>「研究費の応募・受入等の状況」画面の落とし穴

- **「e-Rad登録情報を参照」は応募年度に研究期間が掛かる課題しか出さない**模様 (応募年度前に
  終了する応募中課題は一覧に現れない)。さらに**他人が代表の応募中課題 (自分は分担者として
  承諾済み) も自動では出ない** — 分担承諾した応募中課題は記憶と記録から能動的に洗い出して
  手入力しないと欠落する (実例あり。承諾操作をした課題は必ずここに載る、を checklist に)。
- 行の「1. 資金制度・研究費名」は**「役割」を選択して初めて活性化するプルダウン**。
  未選択のまま保存すると「必須項目です」で全行エラーになる。科研費以外は「その他」+ 自由記入。
- 金額欄の使い分け: 表の金額欄 = **応募年度の経費**、括弧欄 = 期間全体額、「総額」欄 =
  **科研費の研究代表者のみ**記入。⚠️ **上段・括弧欄はどちらも「本人が使用する額」** — 自分が
  代表で分担者に配分する課題では、**分担金を差し引いた額**を書く (総額は総額欄が別に受け持つ)。
  「代表だから総額を書く」と思い込むと括弧欄が総額と同値になり、事務チェックで差し戻される
  (2026-09 実例: 括弧欄に総額を書いて「分担者配分を除いた本人使用額に」と赤字指摘)。
- **(4) 兼業欄は兼業・非常勤専用** — 本務の所属・役職は書かない (システムが別途保持している)。
  他大学の非常勤講師や学外の兼業がある場合のみ行を立てる。空でも正常。
- **エフォート合計 ((1)(2)(3) の和) に機関ローカルの目安がある場合がある** (「30〜50% 以内」等)。
  JSPS の公募要領には上限の規定が無いので、超過を指摘されたら**機関の運用目安かどうかを
  事務に確認**した上で、上げたいなら理由 (= 応募 1 件あたりの最低確保分) を添えて相談する。
  各行のエフォートは金額規模に対して単調であることが読み手の期待 (小額課題に大きな値を置くと
  相違点欄の説明と齟齬して見える)。
- 相違点欄には「左記の研究課題を応募 (受入れ) するに当たっての所属組織・役職」の必須
  sub-field が付く。エフォートは e-Rad の分担者承諾時に入力した値と整合させる。
- 同時応募する種目間 (例: 基盤と挑戦的) では本欄は互いの鏡像になる。転記表を 1 つ作って
  両方に使い、**片方だけ直した場合のもう片方への波及**を必ず確認する。同日に複数種目を
  順に提出する場合、先に出した種目の本欄には後の種目の行が構造的に載らない — 差し戻し・
  修正の機会に後追いで足す宿題を TODO 化しておく。
- 「e-Rad登録情報を参照」で自動投入される行は、**課題名・研究期間が e-Rad 登録値のまま入る**
  (画面で修正可)。応募書類側で通称・略称を使っていても、本欄は e-Rad 値を採用するのが安全
  (整合性照合の基準が e-Rad 側にあるため)。金額・エフォート・相違点は自動では入らず手入力。
  e-Rad との連携ラグは通常 60 分程度と画面に注記される。
- **本欄はシステム生成の提出確認用 PDF に頁として含まれない** (2026-08 に 2 種目で実測)。
  提出前検品で「確認用 PDF に本欄が無い」のは正常であり、本欄の検品は入力画面 (エフォート
  合計・行数) で行う。提出後に本欄の確定値を残したければ入力画面の値を転記表へ書き戻す。
- **e-Rad 自動連携で行が立つものの実測射程** (2026-08、学術変革公募で実測): 自動で立つのは
  ① 自分が e-Rad 経由で応募中の他制度課題のうち**研究期間が応募年度に掛かるもの**
  (応募年度前に完結する課題は出ない)、② **受入予定の科研費分担課題** (承諾済み)。
  **出ないもの** = 科研費の応募中課題 (自分が代表でも出ない。画面注記「研究経費や
  研究機関単位の応募課題は連携しておりません」= 機関経由で応募する課題は対象外) →
  基盤・挑戦的等の応募中行はすべて手入力。
- 数値欄 (総額等) は**全角数字を「半角数字で入力してください」で reject** する。手打ち・
  コピペとも半角で。

### その他の欄仕様 (実測)

- 「内容を表す用語」欄は**特設審査領域で応募する場合専用** — 中区分・小区分での応募では
  グレーアウトされ入力できない (空のままで正常)。
- 要約系のテキスト欄は「改行不可」「改行 1 回 = 全角 1 文字換算」等の欄ごとの制限が
  注記されている。字数は貼る前に len() で検査しておく。
- 経費の「必要性」テキスト欄は**費目ごとではなく 2 欄構成** (「設備備品費、消耗品費の必要性」/
  「旅費、人件費・謝金、その他の必要性」= 3 費目まとめて一欄)。各欄「500 字以内」の実体は
  **1000 バイト制限 (全角 2 バイト・半角 1 バイト換算、改行 3 回まで・1 回 = 全角 1 字扱い)** で、
  半角英数を含めば 500 字を超えても通ることがある一方、超過はエラーで保存されない
  (2026-08 実測: 737 字で byte 超過)。貼る前に `2*全角数 + 半角数 + 2*改行数 <= 1000` を検算する。
  0 円の費目 (人件費等) も同欄内に「計上しない (理由)」と 1 文書いておくと欄の完結性が保てる。

## <a id="track-record-section"></a>欄「研究遂行能力及び研究環境」— 論文以外の材料を CV から発掘する

評定要素「研究遂行能力及び研究環境の適切性」に対応する欄の記入要領は、**論文以外の材料を明示的に
招いている**: 「研究計画に関連した国際的な取組（国際共同研究の実施歴や**海外機関での研究歴**等）」
「研究業績（論文、著書、産業財産権、**招待講演**等）」。書き手の意識は論文リストに寄りがちで、
以下が CV に眠りやすい (2026-09 の基盤(B) 改訂で実測):

- **海外機関での研究歴** (ポスドク歴・長期滞在) — 記入要領の文言に literal 正対する一級材料。
- **受賞と、その選考委員等の役務** — コミュニティでの位置の evidence。
- **競争的資金の獲得状況** — 代表課題の完遂数 + 異分野 (実験系等) との分担参画は計画の実行可能性に直結。
- **日付つき業績統計** (総被引用数・h 指数・直近 N 年の誌上掲載数・招待講演の通算数、出典 DB と取得月を明記) —
  看板業績が古い場合、「直近 3 年で N 編」型の自己申告より統計の方が「近年の生産性」への割引を正面から反証する。

注意点 3 つ:

- **年数・件数の self-claim は、審査員に見える業績リストから検証可能な形にする**。「10 年以上主導」と
  書いてリスト最古の論文が 8 年前なら、欄内の証拠と矛盾する誇張と読まれる (実例あり、独立査読で検出)。
  「YYYY 年から」型 (= リスト最古の年を使う) が同じ強さで反証不能。
- 🔴 **「論文は既に掲載されているもの又は掲載が確定しているものに限って記載すること」** (記入要領)。
  参考文献リストの見出しを「研究業績」とすると、計画説明で引いた arXiv preprint がこの制限に抵触して
  見える。**見出しを「引用文献」に変えれば** preprint は計画の引用として正当に並び、本文で名指しする
  主要業績を掲載済みに限れば compliant になる。⚠️ 見出しの改称だけでは事務チェックを通らない —
  **1 件ごとに掲載状態が読めること**まで要る (2026-09 に arXiv 番号だけの entry へ「雑誌名？」と
  赤字。見出し改称済みの種目でも同じ指摘が来た)。**状態ラベルを機械で付ける**のが安全:
  誌名/DOI を持つ entry に「（査読有）」、持たない entry に「（プレプリント）」、査読誌に投稿中と
  一次記録で確認できる entry だけ「（投稿中）」。**見出しにも凡例を書く**
  (「引用文献（…査読有＝誌上掲載済、arXiv 番号のみ＝プレプリント）」)。
  実装は `.bbl` の後処理が確実 — `\bibitem` で split し、DOI 有無で分岐して entry 末尾の
  `.` の直前に挿入し、**付与件数を assert** する (末尾 entry は `\end{thebibliography}` を
  従えるので正規表現の末尾 anchor がずれやすく、silent に 1 件落ちる)。
  「（投稿中）」は**投稿の一次記録 (投稿番号・審査状態) がある entry に限る** — 状態の粉飾は
  掲載状態そのものより重い瑕疵になる。
- **著者名の下線は事務が明示的に求めることがある** (「先生のお名前の下に線があると分かりやすい」)。
  種目の様式が下線規則を持つなら (研究代表者＝二重下線 / 分担者＝一重下線 等) それに従い、
  無くても申請者名に下線を引く。これも `.bbl` 後処理で全 entry 一括 (手で引くと漏れる)。
  ⚠️ 姓名の綴りが bib entry 間で揺れると (`K.-Y.` / `K.-y.`) 置換が一部だけ当たる — **正規化 →
  置換 → 件数 assert** の順に組む。
- **引用は代表 2–3 本に絞る**。自著 N 本の並列 cite はリスト行を食い、審査員には件数の主張にしか
  見えない。「N 編を産出（代表例 [x--z]）」と件数と代表を分離する。**被引用数を書くときは必ず一次 DB と
  突合する** — 同著者・同テーマの姉妹論文と arXiv ID を取り違えて別論文の被引用数を焼く事故は実際に
  起こる (審査員が DB を引けば水増しに見える、最悪の誤記類型)。

## <a id="collaborator-naming"></a>研究協力者の書き方 — 実名×役割が匿名の分野列挙に勝る

- 研究協力者は e-Rad の応募資格登録も機関承諾も不要で、大学院生等も参画できる (公募要領の研究組織節に
  例示。学部生を排除する文言もない)。氏名記載に手続き上の同意要件は無い — 事前の一報は礼儀の問題。
- **「◯◯分野の共同研究者」という匿名の役割列挙は、検証不能な体制として弱く読まれる**。「氏名 (担当分野)」の
  実名列挙は、審査員には未知の名前でも「計画の柱ごとに実在の担当者がいる」証拠になる — 研究方法の
  各柱に 1:1 で named 対応させると効果が最大 (2026-09 実測: 3 本柱 + 横断 2 役の 5 名構成)。
- **調書に書くのは氏名と役割だけでよい**: 所属・身分を書かなければ審査員には見えない (協力者は
  researchmap/KAKEN 参照の対象外で、検索しても出ない名前が普通)。学生協力者の身分をあえて開示する
  利得は、評定要素に人材育成が無い種目では無い — 「この柱は学生頼みか」と読まれる下方リスクだけが残る。
- 実名化の前に氏名の SoT 照合を通す (漢字は連絡先 DB・共著論文の author block から取り、推測で
  起こさない = [name-rendering.md](name-rendering.md) の一般則)。

## <a id="mock-review-and-claims"></a>提出前の模擬書面審査と、主張の帰属検証

- **模擬書面審査**: 別 session (または別人) に**審査員 persona を指定し、調書本体のみを読ませて**
  (内部資料・準備 note は意図的に不読 = 先入観排除) 模擬審査させると、評定要素別の評点と「審査で最も
  突かれる穴」が具体的に返る。改訂担当と査読担当を分離すると採否判断も冷静になる (adopt/reject を理由
  つきで記録)。物理検証の「独立した第二の目」kernel ([physics-verification-cycle.md](physics-verification-cycle.md))
  の文書版 instance。実測では、真物理の穴 (質量スケール未特定・アノマリー無言及)・compliance・記号 drift
  まで 1 往復で挙がった。
- 🔴 **第三者の誤りを名指しする主張は、書く前に一次記録と突合する**。「X らの計算の誤りを特定・訂正した」
  型の文は審査員に検証されうる最強度の主張であり、誤っていれば方法論の看板ごと崩れる。実例: グループ内の
  人名略称を、同分野の著名研究者の名前に**誤展開する名前衝突**で、自分たちの論文の誤植訂正を他人の論文の
  訂正として書いた事故 (独立査読で検出)。検証できない名指しは削る方が強い — 多くの場合、真実 (機械検証が
  自分の出版済み論文の誤りを検出した等) の方が宣伝として優れる。一般則 (帰属の第二軸 = claim-target /
  内部略称の衝突展開 / 確認設問の照準) = [actor-attribution.md#claim-target-attribution](actor-attribution.md#claim-target-attribution) +
  [convention-design-principles.md#confirmation-question-aim](../docs/convention-design-principles.md#confirmation-question-aim)。
- **図が語る不都合は本文で先回りする**: 理論点が観測許容域の外に落ちる図を載せるなら、その事実と含意
  (緊張こそが動機になる等) を本文で言語化する。図と本文の黙った不整合は審査員の第一の突っ込み所。
- **観測到達性の数字を最低 1 つ書く**: 効果の桁 (Δ観測量 ∼ 10^{-x}) と現行・次世代精度の比較が 1 文
  あるだけで、「小さすぎて見えない」と「大きすぎて信用できない」の双方向の批判を同時に塞げる。数字ゼロの
  調書は審査員に算術をさせる (= 減点側に倒れる)。
- **「未解決/係争中」と框付ける問いは、先行研究が「解決済み」と結論していないか検査する**。結論している
  場合は帰属 1 句 (「先行解析 (X ら YYYY) は…と結論したが——」型) を添えて、何が新しく何を裁定するかを
  明示する — その分野を知る審査員が「あれは X らで決着済みでは」と誤認して斬新性を割り引く事故の予防接種。
  自分の基盤論文が当該先行研究を引用していれば、その引用文脈をそのまま流用できる (論文と調書の整合も保たれる)。
- **同一量の別表式は定義点で恒等式に繋ぐ**: 本文で n = a/b、図 caption で n ≃ c/d のように同じ記号の
  異なる表式が離れて置かれると、恒等式を明記しない限り検算する審査員には矛盾に見える。定義箇所で
  chain (n = a/b ≃ c/d) にして本文と図の軸ラベルを接続する (= 図の境界線が軸から導出可能になる副作用も大きい)。

## <a id="frozen-revision-geometry"></a>提出後の差し戻し改訂 — 頁ジオメトリを保存して差し替え可能に保つ

学内提出後の調書は凍結されるが、機関承認前なら**差し戻し**で添付 PDF を差し替えられる (依頼は担当事務
経由、JSPS 本〆から逆算した hard deadline で TODO 化)。提出済み文書の改訂は「いつでも差し替えられる形」を
保って組むと安全域が最大になる (2026-09 に 2 種目で実測):

- **Web 入力項目を触らない改訂に絞る**: 差し戻し窓の作業が「添付 file の再アップロードのみ」になり、
  再入力ミス (字数の改行換算・全角 reject・波ダッシュ実体参照 [#textfield-wavedash-entity](#textfield-wavedash-entity)) の
  リスクと所要時間を最小化できる。
- **頁が満杯の文書への挿入は、同一段落内の等量トリムとペアで設計する** (字数収支ペアリング)。
  [#layout-pendulum](#layout-pendulum) の「文字数トリムは行数に効かないことが多い」の逆用 — 行数を**変えない**ためにこそ
  段落単位で文字数を数える。行単位の不足は縦レバー (文献リストの `\itemsep`、見出し前の小さな負 `\vspace`) で補う。
- **検証は目視でなく座標で** (PyMuPDF): ①頁数不変 ②各頁の最終行 bbox y 座標を改訂前 PDF と比較
  (全頁一致 = 行数レベルで無変化の証明。伸びた頁は下余白限界との差を実測して残余白を数値で残す)
  ③ `.log` の Overfull/Underfull `\vbox` = 0 ④行頭句読点 scan ([latex.md#line-initial-punct-scan](latex.md#line-initial-punct-scan))
  ⑤新旧文字列の存在確認 (テキスト抽出は空白が揺れるので `\s+` を潰してから照合)。
- 残余白を使い切ったら「この頁にはもう 1 字も足せない」と状態記録に明記する (= 次の改訂者への guard)。
- 提出時 snapshot は不変に保ち、改訂は作業 tree で組む。差し替え予定物の一覧は差し戻し窓の carrier TODO に
  追記する (同じ窓で処理する修正が複数種目にまたがるなら 1 TODO に集約 = 窓を 1 回で使い切る)。

## <a id="office-review-loop"></a>機関事務のチェックと差し戻しループ — 書き込み PDF の読み方と指摘の類型

学内提出後、機関承認までの間に事務が全種目を通読して**差し戻し**を掛ける。e-Rad 応募と同じく
**差し戻しは正常フロー**で、手順の checklist は [erad-submission.md#sashimodoshi-response](erad-submission.md#sashimodoshi-response)
と共通 (赤字 PDF を全頁解読 / 指摘箇所のみ直す / 完了報告)。科研費電子申請システム固有の点:

- **差し戻し窓は何度でも開けられる** (機関承認前なら事務に依頼すれば再度差し戻してもらえる)。
  「1 回しか直せない」前提で妥協した修正を積まない。**同じ窓で処理する修正は 1 つの carrier に
  集約**し、種目をまたぐ宿題 (応募状況欄の鏡像追加など) も同じ窓で一緒に片付ける。
- **通知が本人に届かないことがある** (機関の ML 宛に出て転送されない等)。**差し戻しの有無を
  受信箱の有無で判断しない** — 種目ごとに再提出期限が別々に設定されることもある
  (2026-09 実例: 2 種目 = 9/9、別 2 種目 = 9/10 で、後者の通知は本人に届いておらず 1 日遅れて発覚)。
  期限を確認する第一手は事務への 1 問い合わせか、システムの課題一覧のステータス。
- **書き込み PDF はスキャン画像でテキストを持たない**ことが多い (紙に手書き → スキャン → 添付)。
  `get_text()` は空を返す。**色領域検出で全頁を機械走査**してから読む: 頁を raster 化し、
  彩度の高い画素 (赤・青・付箋の黄) の連結成分を取り、bbox を余白込みで crop して 1 枚ずつ読む。
  ⚠️ **「本文には書き込みが無い」と早合点しない** — 頁単位の色画素数だけ見て「応募状況欄だけ」と
  報告し、実際は本文・経費に十数箇所あった実例がある。走査は**全頁 × 全連結成分**で。
  crop file の命名に種目 tag を入れる (複数種目の PDF を同じ dir に出すと衝突する)。
- **指摘の類型は毎回ほぼ同じ**。着手前にこの順で自分の全種目を自己点検すると往復が減る:
  ① 表記 (略称 →正式名称。「文科省」→「文部科学省」等) ② 業績リストの下線と掲載状態
  ([#track-record-section](#track-record-section)) ③ 紙面の空き (下記) ④ 経費明細の粒度
  ([#keihi-meisai-granularity](#keihi-meisai-granularity)) ⑤ 応募状況欄の行の過不足・金額・
  兼業欄・エフォート合計 ([#oubo-jokyo-form](#oubo-jokyo-form))。
- 🔴 **「〈頁数〉以内とありますが、スペース的余裕があるので…7 割は埋めてください」** — 事務は
  **紙面の空きを差し戻し事由にする**。[#layout-pendulum](#layout-pendulum) は「詰めすぎ」側の危険を扱うが、
  **下限側にも実務的な閾値がある** (体感で最終頁まで 7 割)。埋め方は水増しでなく、
  審査基準に効く材料の追加 (リスクと対応 / 年次計画表 / 手法の具体化 / 成果物の共有と人材育成)。
  ⚠️ 空き頁は**差し戻しを受ける前に**埋めておくのが安い (提出前の自己点検項目に入れる)。
- 事務の付箋には**申請者が対応すべきでない情報メモ**も混じる (審査のカラー/モノクロ運用、
  重複制限の件数、領域代表者名など)。**指摘と情報を分けて台帳化**し、対応不要と判断したものは
  「対応不要」と理由を書いて残す (次の窓で読み返したときに再検討しないで済む)。

## <a id="submission-artifact-staging"></a>差し替え物の版を取り違えないための staging 機構

差し戻し改訂の最大の事故は物理的な取り違え — 同名の調書 PDF が複数系統 (提出済 snapshot /
自己改訂版 / 事務対応版 / 盲検レビュー用 referee copy / 次版) 並存し、人間がファイル選択
ダイアログで拾い間違える。**「どれが最新か」を人間の記憶に置かない**設計にする:

1. **build stamp** — ビルド script が `source の sha256` と `出力 PDF の sha256` を stamp file に
   書く。staging はこの stamp と現物を照合し、**tex を直したのに再ビルドしていない / PDF だけ
   別経路で作った**状態を拒否する。
2. **staging dir 一本化** — `upload/` 等 1 つの dir を毎回**空にしてから**再生成し、
   「ここ以外からは上げない」を規約にする。file 名に `<日付>_<hash 先頭 8>` を入れると、
   画面で選んだ物と手元の物の同一性が目視で照合できる。同じ dir に**転記シート・取込 CSV・
   手順 README** も一緒に吐くと、提出作業中に別 dir を開く理由がなくなる。
3. **content gate** — 頁数・欄の最終行 y 座標・**必須語 / 禁止語**を staging 時に検査する。
   必須語 = 改訂で入れた語、禁止語 = 改訂で消した語。改訂を重ねると「直したはずの語が
   別 build で復活」が起きるので、**回帰 guard として語のリストを育てる**。
   ⚠️ PDF テキスト抽出は和欧間の空白が揺れる — 比較は `\s+` を潰してから。
4. **入力後の突合 (verifier)** — 提出前の最後の gate。システムが吐く提出確認用 PDF と、
   応募状況欄の画面印刷 PDF を読み、SoT (下記) の全項目が**含まれるか**を ✓/✗ で列挙する。
   照合は「空白を潰した部分文字列一致」にすると表のセル分割に依存しない。
   **添付 PDF の全頁が手元の現行ビルドと一致するか**まで見れば版の取り違えが機械で捕まる。
   ⚠️ 応募状況欄の印刷 PDF は**全種目の課題名を行として含む**ので、「どの種目の PDF か」を
   課題名の包含で判定すると誤判定する — **最初に現れた課題名** (= header) で判定する。
5. **Web 入力値の SoT を 1 つの data file に** — 課題・金額・期間・エフォート・相違点文・
   経費・添付名を 1 つの yaml 等に集約し、**転記シートは生成物**にする。生成の前に gate:
   ① 導出関係 (本人使用額 = 年度計 − 分担金) ② **鏡像** (全種目の応募状況欄が同じ課題集合・
   同じ金額・同じエフォート) ③ エフォート合計 ④ 各数値の literal が出典 file に実在
   ⑤ 相違点文の禁止文字 ⑥ 経費 CSV との年度計一致。
   実績: この gate が、事務への打診メールに書いた内訳の合計が 1 ずれていた誤記を検出した
   (= 人間が読んで通した数字を機械が捕まえた事例)。

⚠️ **盲検レビューに出した referee copy は canonical と別物**になる (改訂が進むため)。staging 時に
**両者の hash を比較して古ければ警告 + 本文 diff を残す** — レビュー結果の頁番号・文言は旧版基準
なので、そのまま当てると位置がずれる。反映は必ず**現行 source に対して**行い、referee copy を
書き戻さない (汚染隔離の一般則 = [cold-eyes-isolation.md](cold-eyes-isolation.md))。

## <a id="assisted-web-entry-runbook"></a>Web 入力を人間が打ち AI が照合する時の手順 (2026-09-08 実測、 4 種目 40 分)

差し戻し再提出の Web 入力を「人間が画面を操作し、AI が値と照合を持つ」分担で回した実測手順。
値の正本 (Web 入力 SoT) と転記シートが既にある前提 ([#submission-artifact-staging](#submission-artifact-staging))。

1. **画面ごとに「変えるところだけ」を出す**。転記シート全文を渡しても人間は読まない。差し戻し
   では大半の欄が既入力なので、AI は「この画面で触るのは N 箇所」の形で、**画面の並び順に**
   (役割 → 資金制度 → 経費 → 括弧 → エフォート → 相違点 → 所属役職 → 期間 → 課題名 → 代表者 → 総額)
   表で出す。新規行は「追加ボタンで空枠を出して、その枠を上から順に」と枠単位で書く。
   「所属役職は全部 ○○」のような**まとめ書きは通じない** — 枠ごとに全欄を書く。
2. **人間は画面のテキストを丸ごと貼る** (確認画面 or 入力画面をそのまま select-all → paste)。
   AI はそれを SoT と突き合わせて「合っている / ここが違う」だけを返す。screenshot より
   テキスト貼付の方が照合が速く、確認画面 (入力確認) は全行が 1 頁に出るので最適。
3. **アップロードする file は AI が Finder で選択状態にして前面に出す** (`open -R <file>` +
   Finder activate)。chat のリンクは file 選択ダイアログに使えない。種目が変わるたびに言われる
   前に次の file を出す。
4. **提出確認用 PDF はダウンロードフォルダから AI が拾って verifier にかける** (ZIP なら展開)。
   「研究費の応募・受入等の状況」は確認用 PDF に無いので、2 の貼付テキストで照合したことを
   記録に残す (印刷 PDF は取らなくて済む)。
5. 送信ごとに **snapshot (`submitted/<日付>-sai/`) + status.md §提出記録 + 次の種目の file を Finder に**。
   4 種目を 1 晩で回した順は 基盤B → 萌芽 → 公募 2 件 (期限順、 かつ鏡像の親から)。

罠 (同日実測): 「事項」72 バイト上限 [#keihi-meisai-field-limits](#keihi-meisai-field-limits) /
公募研究の確認用 PDF に明細行が無い [#confirmation-pdf-detail-rows](#confirmation-pdf-detail-rows) /
相違点欄の prefix 照合は画面の現行文を SoT に写してからでないと偽 ✗ になる (SoT に推測 prefix を書かない)。

**次の段階 = AI が打つ**: ログイン (SSO / パスワード) だけ人間、以降の画面操作は browser 自動化
(claude-in-chrome の `form_input` / `find` + 転記シートの値) で AI が入力し、確認画面テキストを
自分で読んで SoT と突合する。人間の役割は「ログインして席を外す → 送信ボタン」の 2 点に縮む。

## <a id="koubo-kenkyu-mechanics"></a>公募研究 (学術変革領域研究) の実務

- **重複制限**: 公募研究の新規応募は **2 件まで、ただし別領域に限る** (同一領域内は 1 件のみ)。
  基盤・挑戦的の代表応募との重複可否は当年の別表 1 で個別確認 (種目×年齢帯で異なる)。
- **Web 入力の入口 = 領域選択画面**: 全領域×研究項目番号×単年度上限額の**行単位**で [登録] を
  押して進む。同一項目に上限額の異なる複数行 (tier) を持つ領域があり、**tier ごとの採択目安件数**が
  公募要領の別表に載っている — 単独理論なら件数の多い低額 tier が通りやすいことが多く、tier 選択も
  応募戦略の一部。領域・項目の公募文言の現物 (別表 2 の当該頁) に調書を literal 正対させる。
- 応募情報は 研究課題情報 / 研究経費とその必要性 / 研究費の応募・受入等の状況 の 3 画面 +
  添付 (S-74)。**応募・受入等の状況は PDF に変換されない** (画面注記) — 提出確認用 PDF の検版で
  「本欄が無い」のは正常。
- 経費明細が少数行 (目安 10 行以下) なら CSV 取込より手入力が速い (CSV は行数が多い種目向け)。
- **学内〆切超過の救済**: 電子申請システム自体は学内〆後も送信を受け付ける (機関承認が後段に
  あるため)。支援課に受付可否を確認の上、送信 → 一報の順で。事後になった説明は事実ベースで
  簡潔に (過剰な謝罪の重ね置きは不要)。

## <a id="title-collision-check"></a>研究課題名の衝突検査 — 語が「よそのホットトピック」と衝突しないか

**課題名を確定する前に、タイトルの各キーワードについて 2 つを検査する**:

1. **正対**: 公募文言・審査区分の語彙に literal に対応する語が入っているか (審査員が公募内容と
   照合したとき課題名だけで対応が見えるか)。
2. **衝突**: その語が**単独では同名の他分野・他文脈のホットトピックとして誤読されないか**。
   タイトルは審査割当と第一印象を決める — 本文中の hedge や定義ではタイトル単独の誤読は解けない。
   衝突が見つかったら、語を機構名や対象に**縛る** (「X」→「X型 Y 崩壊」) か、新規性の否定形
   (「〜に依らない」) を冒頭に置いて generic 読みを遮断する。

実例 (2026-08、学術変革公募): 「超放射」単独 → 回転ブラックホールの superradiance (アクシオン
生成、当該領域でホット) や Dicke 原子系と誤読される → 「超放射インフラトン崩壊」と機構に縛って
遮断。「宇宙再加熱」単独 → 総称すぎて「よくある再加熱研究」に沈む → 「共鳴に依らない」を冒頭に
置いて標準機構 (パラメタ共鳴) との差分を宣言。
