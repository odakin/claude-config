# 科研費 研究計画調書 — 審査基準への正対と紙面設計

公募要領・様式の年度個別値はその年の公募要領が正本。本 doc は**年度をまたいで効く機構知見**のみ
(2026-08 の挑戦的研究(萌芽) 調書作成の実測から)。sibling: e-Rad フォーム機構 =
[erad-submission.md](erad-submission.md) / JPS 講演申込 = [jps-talk-submission.md](jps-talk-submission.md) /
LaTeX 紙面の罠 = [latex.md](latex.md) / 図の機械 QA = [matplotlib-figure-qa.md](matplotlib-figure-qa.md)。

## <a id="drafting-entry-point"></a>起草の入口 — 書き始める前に / 書いている最中に

⚠️ **本 doc の実務規律の多くは [#office-review-loop](#office-review-loop) (= 差し戻しを受けたときの節) に
書いてある**が、その大半は**書くときに効く規律**である。差し戻しを受けてから読むのでは遅いので、
起草の入口をここに置く (payload は各節が持つ。ここは routing のみ)。

### 起草を始める前 (= 当年の公募が出て様式を入手した日)

1. **前年の赤入れを読み返す** — 🔴 これが最も安い。実測で、ある年に受けた指摘は
   **ほぼ全類型が前年の同じ種目・同じ事務の差し戻しに既に在った**
   ([#office-review-loop](#office-review-loop) 冒頭)。赤入れは text 層を持たないスキャンが多く
   grep に掛からないので、**file 単位の台帳**で「どこにあり読んだか」を持つ (同節)。
   ⚠️ **台帳だけでは読み返せない**。台帳は所在の記録であって中身ではないので、
   毎回スキャンを開いて色領域抽出をやり直すことになる (= 一番高い工程)。
   **事務の文言を書き起こした file を制度ごとに 1 つ持ち、新しい順に並べる**:
   - 制度ごとにするのは「同じ種目で何を言われ続けているか」が読む単位だから。
     **再発が file を開いた瞬間に見える**構造になる (年ごとに切ると制度が混ざって消える)
   - 🔴 **文言は言い回しのまま残す**。要約すると次に読む人が同定できない —
     「様式の改変は認められません」が**同一文言で 2 年前にもあった**と気づけたのは
     文言が残っていたから
   - 行頭に**検出器コードと同じタグ**を置くと `grep <CODE>` で全年を横断でき、
     機械が見ない分は `👁` で引ける (schema 不要。yaml にしない)
   - **文言 / 所在 / 対応**を混ぜない (3 file の分業)。混ぜると drift する
2. **当年の様式から指示を吸い出す** — `kakenhi-preflight.py --form <当年の様式>.docx` の
   ℹ️ INSTRUCTION 出力を checklist にする ([#form-template-integrity](#form-template-integrity))。
   🔴 **要求項目は年ごとに増える**ので、前年の調書を土台にすると新しく必要になった欄が空のまま通る。
   1 と 2 は**両方**要る (1 = 毎年言われるもの / 2 = 今年増えたもの)。
3. **審査基準 (評定要素) を取得して欄構成を正対させる** ([#review-criteria-alignment](#review-criteria-alignment))。
4. **課題名の衝突検査** ([#title-collision-check](#title-collision-check))。

### 書いている最中 (= 機械が見られない、人が判断するもの)

| 見るもの | なぜ |
|---|---|
| **進捗の時制** — 進行中の事業を「実証済み」と書かない | 「事業はまだ終わっていませんが…」と必ず突かれる ([#office-review-loop](#office-review-loop) ⑧) |
| **人的資源の制度制約** — 専念義務のある身分を戦力に数えない | 同 ⑨。⚠️ **制度ごとに逆になる**ので他制度へ横展開しない |
| **これまでの研究 → 本課題の流れ**を 1 段落で | 同 ⑩。紙面の空きの埋め方としても最良 |
| **用語を揺らさない** (研究補助員 ⇄ 研究補助者) | 同 ⑫。人的資源の呼称が特に揺れる (`TERM_DRIFT` が拾う) |
| **経費と本文を同時に設計する** — 人件費が大きいなら本文に役割分担と雇用の必要性 | 審査は「経費と研究計画の整合性」を見る (同節) |
| **文字サイズを変えない / 段落の一字下げ / 分野の略記を正式名称に** | 同節。書式は後から直すと紙面が動く |
| **空欄で出す欄と必ず書く欄**を欄ごとに読む | 丁寧に埋めたことが誤りになる欄がある ([#form-template-integrity](#form-template-integrity)) |

### 組み上がったら

`kakenhi-preflight.py --form … --pdf … --keihi … --strict` を提出手順の script から呼ぶ
([#submission-artifact-staging](#submission-artifact-staging) 6)。⚠️ **呼ばなければ何も起きない**ので、
年が替わって kit を作り直すときは**その staging script に呼び出しを入れるところまでが移行作業**。

🔴 **呼び出し口は 2 つ以上持つ**。提出手順の script だけだと、(a) 年が替わって呼び出しが
失われる (b) staging を回さずに触っている間は誰も見ない、の 2 経路で静かに無効化する。
2 つ目は**常設の検査 (dashboard 等) から kit を自動発見して通す**形がよい:
`forms/*.docx` と組み上がり PDF の**両方を持つ応募 dir** を kit とみなせば、対象を手で
列挙し続けなくて済む。あわせて「kit があるのに repo 内のどの script も preflight を
呼んでいない」= **配線切れ**も見る (= (a) の直接の検出)。
⚠️ **経費 CSV は kit から構造的に決まらない** (作業室に在り、`submitted/` には訂正前の凍結版が
居る)。推測で渡すと過去の snapshot を現物として叩くので、常設側は form + PDF だけを見て、
CSV は対応を知っている提出手順の script に任せる。

## <a id="review-criteria-alignment"></a>審査基準 (評定要素) を取得して欄構成を正対させる

JSPS は種目別の**書面審査における評定基準等** (審査委員に渡る評定要素の全文) を公開している
(jsps.go.jp の審査関係規程ページ)。調書を書く前・仕上げる前に**必ず現物を取得**し、
評定要素の各項目に「調書のどの段落が答えるか」をマップする。実測での効き方:

- **評定要素にあるのに調書に対応段落が無い項目が炙り出せる**。挑戦的研究の評定要素は
  (1) 挑戦的研究としての妥当性 (2) 研究目的・計画の妥当性 (3) 研究遂行能力 (4) **研究課題の
  波及効果** (学術・科学技術・産業・文化など幅広い社会へのインパクト) の 4 つで、
  (4) は書き手が自然には書かない = 明示的な段落を与えないと審査員に材料が渡らない。
- **評定要素の literal キーワードを見出しに掲げる**と審査員の checklist 照合が速い。
  例: 萌芽は「**探索的性質の強い、あるいは芽生え期**の研究計画の場合には可能性を有するか」が
  評定要素の文言 → 「探索的性質と芽生え期の可能性——なぜ萌芽か」のような見出しで正対する。
- 審査 process の機構も同文書にある。挑戦的研究は応募多数だと**事前の選考** (プレスクリーニング)
  があり、評点分布は 4=10% / 3=10% / 2=10% / **1=70%** の相対評価 — 事前選考が参照する様式
  (概要版) が生死を握る。概要版と本審査様式が独立に読まれる種目では両方を自己完結に書く。
- 「答えがどちらであっても成果になる」型の主張 (either-way wins) は、挑戦性と実現可能性の
  両評定要素に同時に効く — 高 risk の問いには入れる価値が高い。

## <a id="layout-pendulum"></a>紙面設計 — 詰めすぎ⇄空きすぎの振り子を頁数制限の中で

頁数上限との攻防で紙面は「隙間が空きすぎ (書けるのに書いていない)」と「ぎっしりで読む気が
しない」の間を振り子する。実測で収束した型:

- **見出しは run-in (段落頭の太字) でなく独立行 + 前後空き**。壁が節に割れ、斜め読みで骨格が
  拾える。`\newcommand{\gh}[1]{\par\vspace{.5em}\noindent\textbf{#1}\par\vspace{.1em}\noindent}` 程度。
- 空白を「詰める」のは頁が本当に溢れる時だけ。**頁下端に余裕があるのに float 間隔や
  caption 下を負の `\vspace` で詰めない** (過去の圧縮の残骸が読みづらさとして残りやすい —
  溢れが解消したら詰め物も戻す)。
- 収める順序: 図中と caption の重複説明を削る → 文単位のトリム (文字数トリムは折り返しに
  吸収されて行数が減らないことが多い) → 文献リストの `\small` 化 → 最後に間隔。
- **図の canvas 高さは本文行の回収源**: 実寸フォント設計 (文字 pt を canvas サイズと独立に固定) で
  作った matplotlib 図なら、figsize の高さだけ削っても文字は小さくならない — 0.1 in ≈ 0.6 行を
  可読性を落とさず回収できる (2026-09 実測: 3.8→2.9 in で約 5 行、ラベル衝突なし)。
- 引用の絞り方・業績統計は [#track-record-section](#track-record-section) 参照 (欄 2 側の紙面にも効く)。
- **審査はモノクロ印刷**の種目が多い (公募要領に明記)。図は白黒設計 + グレースケール検版
  PDF を毎ビルド生成して確認する。
- キャプション・行内数式の行かぶり検査と wrapfigure の罠は [latex.md](latex.md) の各 anchor
  (`#pdf-line-collision-detection` / `#wrapfig-caption-page-overflow-loss` 等) を参照。

## <a id="web-submission-system"></a>科研費電子申請システムの機構

- **毎日早朝 5:00 にシステム再起動**があり、またいだ編集は保存されない (トップページに明記)。
  長い入力セッションはこまめに「一時保存」。
- **応募情報は審査終了後の所定日に削除される** (毎年トップページで告知)。翌年度の再応募で
  流用するなら削除前に各自保存が必要 — 調書 source を手元リポで管理していれば実害はないが、
  Web 入力欄 (応募情報) の値は別途控える。
- 添付ファイル項目 (PDF) の登録後は、システム生成の**提出確認用 PDF を白黒で検品**する
  (崩れ・文字化け確認は公募要領上の義務)。
- ログイン ID/パスワードは e-Rad と共通 (e-Rad 側で変更すると反映に 30 分〜1 時間)。

### <a id="ai-read-route"></a>AI がログイン後の画面を読む経路 (2026-09-08 実測)

科研費電子申請システムには API も CLI も無いので、AI の読み書きは browser 経由になる。実測で分かった構造:

- **Claude in Chrome 拡張は本体ドメイン `www-kaken.jsps.go.jp` への navigate を prompt なしで拒否する**
  (トップ `www-shinsei.jsps.go.jp` は許可 prompt が出て通る)。**Claude アプリ内蔵の Browser pane は通る**ので、driver は pane。
  ログイン (e-Rad ID/PW) は pane を表示して人間が打つ。
- ログイン後は **frameset** (frames[0] = `tmp`、frames[1] = `main`)。`get_page_text` / `read_page` は frameset を見て空を返すので、
  読みは JS で `window.frames[1].document.body.innerText`、遷移は `frames[1].location = '/kaken1/shinsei/<画面>.do'`。
  主な画面: `showMainMenu.do` (メニュー) / `processStatusList.do` (処理状況一覧 = 提出済み調書 + systemNo) / 各種 `searchList*.do` (応募開始)。
- **popup で開く画面 (応募情報参照「参照」等) は `window.open('', name)` + hidden form の `target=name` で開く**。pane では popup が潰れて
  「Error-99021 権限なし」になるが、同じ form を **`target='_self'` にして submit すれば同 frame に出る** (= 権限エラーは popup 不成立の副作用で、
  データ権限の問題ではない)。読み終えたら `frames[1].history.back()`。
- 応募情報参照のテキストは入力時の確認画面と同じ構造 (期間の空白の有無だけ違う) なので、確認画面用の parser がそのまま使える。
- 合成 click は page script の copy handler を発火させて OS clipboard を書き換えることがある (pane が警告する) — 読み取りは JS の innerText で済ませ、click を減らす。

### <a id="ai-write-route"></a>AI が応募情報を書く経路 (2026-09-08 実測、sandbox 調書で 3 画面の往復 + 参照読み戻し + 削除まで)

読み経路 (上) の上に、**JS で frame 内 form に値を代入 → 画面の保存関数を呼ぶ** だけで入力が通る。`form_input` は frameset で ref が取れないので使わない。
構造 (基盤研究(C) で実測、他種目は field 名が一部違う):

- **新規 = 受付中種目一覧 `searchListKiban.do` → `onInputApplication('<事業ID>')` → 重複応募注意 → `checkMaking.do`** (= 研究計画調書管理、ここで systemNo が採番される)。
  **再開 = `processStatusList.do` → `onUpdate(systemNo,'1',jigyoCd)`**。管理画面から各画面は `onInputApplication('01'|'03'|'04'|'06')`。
- **入力 = `frames[1].document.shinsei_form.elements[name].value = v`**。select も value 代入で可。役割→種目のような連動 select は
  `dispatchEvent(new Event('change'))` で **client-side に選択肢が入る** (種目リストは page script 内蔵、option の value = label 文字列。
  SoT の表記と括弧の全角/半角が違うので、正規化して一致する option を選ぶ)。
- **保存 = 画面の `onTransientSaveWithUpload()`** (一部の画面は引数付き = link の href をそのまま eval する)。中は `lockButton` + `setTimeout(500ms)` で submit
  するので、**呼んだら 4 秒待ってから次の JS**。成功は本文の「一時保存が完了しました」で判定し、エラー語 (バイト以内 / 文字以内 / できません) も同時に grep。
- **行の追加はすべてサーバ往復** (経費明細 `addMeisaiA()`〜`F()`、応募状況 `onAddOuboJokyo` / `onAddUkeireJokyo` / `onAddERadSonotaJokyo` / `onAddSonotaJokyo`)。
  1 回ごとに待つ (連続呼びは lockButton で 2 回目以降が捨てられる)。入力済みの値は往復で保たれる。CSV 取込 (file input) と添付 upload は
  **JS から file を置けない** = 明細は行追加 + 代入で代替 (行数分の往復、50 行で 3 分程度)、添付だけ人間の 1 操作。
- 値の意味 (応募状況): `[0]` は本応募行 (期間全体額のみ入力、経費とエフォートは研究課題情報の研究組織から来る)、期間全体額 = `zentaigaku`、
  相違点欄の「総額」= `ukeiregaku`、2027 年度経費 = `keihi`、相違点 = `riyu1`、所属役職 = `kikanYakusyoku`。e-Rad 外は 契約種類 0-4 / 国コード
  (JPN → 「日本」に解決) / 通貨 JPY / 年月分離。合計 (再計算・エフォート合計) はサーバが埋めるので、保存後に読み戻して SoT の期待値と突合する。
- **検証は sandbox で**: 提出済み調書はロックされるので、テストは別種目 (基盤研究(C) 等) の新規調書を作り → 入れて → 参照で読み戻し → parser →
  `onDeleteConfirm(systemNo,'')` → `onDelete(systemNo)` で削除。本番の調書に試し書きしない。
- 分担: **人間 = ログイン / 添付 upload / 分担者の追加 (検索 popup + 承諾) / 送信**、AI = それ以外の全画面 + 読み戻し照合。
  driver は「値の正本 → 画面ごとの JS step 列」を決定的に出す script にし、AI は step を順に流すだけにする (= 値を頭から出さない)。
  odakin の instance = `grant-applications/applications/2027-kakenhi-r9/sashimodoshi-2026-09-07/web-driver.py` (docstring が field 名の実測 ledger)。
  **汎用 harness は層1 [`web-form-automation.md#step-driver-harness`](web-form-automation.md#step-driver-harness)**
  (実体 `scripts/lib/web_driver.py`) — 本節は「科研費という 1 サイトの台帳」 側で、 step schema・JS 生成・
  読み戻し・不変条件の検査はそちらが正本 (2026-09-10 に分離)。

### <a id="keihi-csv-import"></a>経費明細の CSV 一括取込 (2026-08 実測)

「研究経費とその必要性」画面の明細 (費目×年度×事項×金額の行群) は CSV 取込で一括投入できる。
手入力 30–50 行が 1 操作になるので、行数が多ければ迷わず CSV。仕様は画面の「フォーマットを
ダウンロード」で得られるヘッダ行から読み取れるが、罠が 2 つ:

- **エンコーディング = Shift-JIS (CP932) + CRLF**。UTF-8 は文字化けする。
- **費目区分は「A」〜「F」の記号指定** (画面の費目表示順: A=設備備品費 / B=消耗品費 /
  C=国内旅費 / D=外国旅費 / E=人件費・謝金 / F=その他)。日本語の費目名を書くと
  全行「費目項目が「A」〜「F」ではありません」で弾かれる。年度は西暦 4 桁。
- 8 列 = 費目区分 / 年度 / 品名・仕様 (設備のみ) / 設置機関 (設備のみ) / 事項 (設備以外) /
  数量 (設備のみ) / 単価 (設備のみ) / 金額。
- script で生成するなら、**年度別合計・費目別合計を予算表と assert で突合してから**書き出す
  (取込後の画面の「再計算」値と予算表の一致が最終確認)。

### <a id="keihi-meisai-granularity"></a>経費明細の粒度 — 事務チェックが必ず突く 3 点

金額の合計が合っていても、**行の書き方**で差し戻される。2026-09 に 4 種目同時で同じ 3 点を
指摘された (= 種目非依存の定型チェック項目とみなしてよい):

1. **設備備品費は「品名・型番」まで書く**。「数値計算用計算機」だけでは通らず、
   「〜用計算機（用途）・〈製品名 / メモリ等の仕様〉相当」まで要る。"相当" を付ければ
   特定ベンダーへの拘束にはならない。
2. **1 行に複数事項を詰めない**。「論文投稿・掲載料、クラウド計算資源利用料」は 2 行に割る
   (事務の指示は「別項目となるため行を分けて計上してください」)。**費目内の内訳が見えることが
   目的**なので、同種のものを 1 行にまとめるのは可。
3. **旅費は 事項欄に「場所・日数・人数」**。「国際会議での成果発表」→「国際会議での成果発表
   （欧州または米国、年 1 回、7 日間、1 名）」。行き先未定なら「〈地域〉または〈地域〉」で可。
   国内も「（年 2 回、各 1 泊 2 日、1 名）」まで。同じ内訳を**必要性テキスト側にも反映**する
   (明細と必要性で内訳が食い違うと再差し戻し)。

派生規律: 明細を script 生成するなら、必要性テキストも**同じ data から**書き出すか、
少なくとも同じ file に隣接させて置く (= 明細だけ直して必要性が旧内訳のまま残る drift の防止)。

**行をどの費目に置くか**は別軸の差し戻し事由 → [#keihi-meisai-expense-category](#keihi-meisai-expense-category)。

### <a id="keihi-meisai-expense-category"></a>費目の帰属と二重計上 — 「どの費目に載せるか」も差し戻し事由

上の粒度 3 点は「行の書き方」だが、**行をどの費目に置くか**でも同じだけ赤字が付く (2026-09、4 種目共通)。
金額合計は変わらないので自己点検では気づきにくい。

⚠️ **これは科研費固有ではない**。同じ帰属 (論文投稿料・OA 掲載料 → その他) は
**別制度・別年で 3 度独立に**同じ機関事務に赤入れされている (2026-05 / 2026-07 / 2026-09)。
**制度をまたいで同じ人が同じ観点で読む**ので、他制度の赤入れも同じ台帳に集約して先回りする。

| 事項 | 正しい費目 | やりがちな誤り |
|---|---|---|
| ソフトウェアライセンス / サブスクリプション / API 利用料 / クラウド計算資源 / 保守 | **その他** | 消耗品費に置く |
| 学会・国際会議の**参加登録料** | **その他** | 旅費の「国際会議発表 (登録料・渡航・滞在)」に混ぜる |
| 印刷費 / 保存媒体 | **その他** | 消耗品費に置く (2025 実測) |
| 英文校閲・データ整形などの**業者委託** | **その他** | 人件費・謝金に置く |
| RA 謝金・研究補助者への謝金 | **人件費・謝金** | 業者委託と 1 行に混ぜる |
| 招聘者の渡航費・滞在費 | **外国旅費** (招聘旅費の行に含める) | 「その他」の研究会開催費に**重ねて**計上 |
| 専門書・文献 | 消耗品費 | — |

- ⚠️ **二重計上**: 「研究会開催費（会場費・招聘者滞在費）」型の行は、滞在費が外国旅費側にも立っていれば
  二重計上になる (事務の赤字は「滞在費は外国旅費に含まれるため削除」)。**「その他」の行に旅費語
  (滞在費・宿泊費・渡航費・航空券・交通費) が出たら疑う**。
- **人件費は積算根拠を事項に埋める**: 「博士研究員 1 名（特任研究員、月額 N 万円＋法定福利費、下半期 6 か月）」。
  ⚠️ 事務は**通勤交通費を含むかどうか**を突く — 含めるなら他費目から削る設計を先に決めておく
  (72 バイト上限 [#keihi-meisai-field-limits](#keihi-meisai-field-limits) と競合するので、削る側を先に決める)。

**同じ事項なのに年度で金額が違う行**は必ず問われる (「同一日数ですが旅費が異なりますが…
**異なる理由は必要性の欄に**ご記入ください」「前年までと異なりますが、最終年度のためでしょうか」)。
金額が合っていても**説明が無ければ**差し戻し事由になる。同様に、**人件費の事項には人数**を書く
(旅費の「場所・日数・人数」と同型)。⚠️ **RA 謝金は機関の定める単価表**に従うので自由に積算できない
— 単価は機関の事務に確認する (自分の想定額で書くと必ず直される)。

機械化: `kakenhi-preflight.py --keihi <明細.csv>` が `KEIHI_CATEGORY` / `KEIHI_DOUBLE_COUNT` /
`KEIHI_SPEC_MISSING` / `KEIHI_TRAVEL_DETAIL` / `KEIHI_MULTI_ITEM` / `KEIHI_FIELD_BYTES` /
`KEIHI_WAVEDASH` / `KEIHI_AMOUNT_VARY` (= 同じ事項が年度で違う金額) を出す。2026-09 の差し戻し前 CSV を食わせると当時の赤字がそのまま再現し、
修正後 CSV では 0 件になる (= 回帰 fixture として `--selftest` に焼いてある)。

### <a id="keihi-meisai-field-limits"></a>明細の各欄にはバイト上限がある — 「場所・日数・人数」を足すと踏む

上の 3 点 (特に旅費の「場所・日数・人数」) を素直に書くと、**「事項」欄の上限 72 バイト
(全角 1 文字 = 2 バイト、半角 = 1 バイト → 全角 36 字) を超える**。超過は CSV 取込時ではなく
**一時保存時に行番号つきの error** で返り、error が 1 つでも残ると画面の入力全部が保存されない
(2026-09-08 実測: 「国内旅費：事項 - 1行目は72バイト以内で入力してください」。CSV 取込自体は
通ってしまうので、必要性テキストまで貼ってから発覚し、4 種目分の CSV を作り直す羽目になった)。
実測で分かっている上限 (他の欄は未計測、超えたら error 文が上限を教えてくれる):

| 欄 | 上限 | 備考 |
|---|---|---|
| 各費目の「事項」 (消耗品費 / 国内旅費 / 外国旅費 / 人件費・謝金 / その他) | **72 バイト** | 全角 36 字 |
| 設備備品費の「品名・仕様」 | 72 より大 (77 バイトが通った) | 正確な上限は未計測 |
| 必要性テキスト (2 欄) | 500 字 / 改行 3 回 (画面に明記) | 改行は 1 回 = 全角 1 字換算 |

規律: **明細を生成する script は「事項」を書く時点で 72 バイトを assert する** (取込前に落とす)。
書き方の型 = 「〈用件〉（〈場所〉、年 N 回、各 M 泊、K 名）」で 36 字に収まるよう、用件側を削る
(「〜への参加と〜との研究打合せ」→「〜・〜との打合せ」、「対面研究打合せ」→「研究打合せ」)。
「場所・日数・人数」は落とさない (= 粒度の指摘の方が再差し戻しに直結する)。

### <a id="confirmation-pdf-detail-rows"></a>提出確認用 PDF には経費明細の行が印字される — 「出ない種目がある」は誤診だった

提出確認用 PDF には「各経費の明細」の全行 (事項・品名/仕様・金額) が印字される。**基盤研究・
挑戦的研究だけでなく、学術変革領域研究(A) 公募研究 (S-74) でも印字される** (2026-09-12 に
2026-09-08 提出の 4 本 = 基盤B / 挑戦的研究(萌芽) / 学術変革(A) 公募研究 2 件 で実測)。∴ **入力後の突合は
「明細の各行が確認用 PDF に在るか」で組んでよい**。

- 明細を分割してもしなくても**費目 × 年度の合計は不変**なので、合計だけの照合では取込漏れを
  検出できない。照合は必ず**行の literal** で行う。
- 「研究費の応募・受入等の状況」は全種目とも確認用 PDF に含まれないので別途 (画面印刷 or
  確認画面の全行照合) — [#submission-artifact-staging](#submission-artifact-staging) 3 参照。

⚠️ **2026-09-08 に本節は逆の内容 (「公募研究では費目合計しか出ない」) で書かれていた。それは誤りで、
実害を出した**: 公募研究の一方で経費明細 CSV の取込が実行されず旧行のままだったのに、verifier の全行 ✗ を
「この様式では印字されないから偽陽性」と解釈して送信し、機関事務から**同じ指摘を 2 度**受けた。
反証は同じ run の中に既に在った (= **同じ様式のもう 1 件**が全行 ✓)。しかも層 1 には
「2 件とも実測」と、**していない測定**が実測として記録されていた。一般則 =
[convention-design-principles.md#false-positive-declaration-needs-control](../docs/convention-design-principles.md#false-positive-declaration-needs-control)
(= 検査の出力を「偽陽性」と宣言するには positive control が要る)。

### <a id="textfield-wavedash-entity"></a>テキスト欄の波ダッシュは PDF に「&amp;#12316;」と焼かれる

Web 入力のテキスト欄 (経費の必要性等) に**波ダッシュ「〜」(U+301C) を貼ると、システム生成の
提出確認用 PDF に HTML 実体参照の文字列 `&#12316;` がそのまま印字される** (2026-08 実測。
入力・確認画面では正常に見えるため気づきにくい)。対策:

- テキスト欄では「〜」を使わない (「から」「1、2名」等に言い換える。全角チルダ「～」も
  同系の変換系を通るため避けるのが安全)。
- **検品を機械化する**: 提出確認用 PDF を PyMuPDF 等でテキスト抽出し、正規表現
  `&#\d+;|&[a-z]+;` の全頁掃引で実体参照の残置ゼロを確認する。あわせて図の入る頁を
  グレースケールで render して CJK ラベルの化け・キャプション切断を目視する
  (審査はモノクロ印刷。図の作り側の gate は `matplotlib-figure-qa.md`)。
- 添付様式が複数ある種目 (挑戦的研究の概要版+本文等) では提出確認用が **ZIP** で来る
  (中に本文 PDF と `GAIYO_` 概要 PDF)。

### <a id="oubo-jokyo-form"></a>「研究費の応募・受入等の状況」画面の落とし穴

- **「e-Rad登録情報を参照」は応募年度に研究期間が掛かる課題しか出さない**模様 (応募年度前に
  終了する応募中課題は一覧に現れない)。さらに**他人が代表の応募中課題 (自分は分担者として
  承諾済み) も自動では出ない** — 分担承諾した応募中課題は記憶と記録から能動的に洗い出して
  手入力しないと欠落する (実例あり。承諾操作をした課題は必ずここに載る、を checklist に)。
- 行の「1. 資金制度・研究費名」は**「役割」を選択して初めて活性化するプルダウン**。
  未選択のまま保存すると「必須項目です」で全行エラーになる。科研費以外は「その他」+ 自由記入。
- 金額欄の使い分け: 表の金額欄 = **応募年度の経費**、括弧欄 = 期間全体額、「総額」欄 =
  **科研費の研究代表者のみ**記入。⚠️ **上段・括弧欄はどちらも「本人が使用する額」** — 自分が
  代表で分担者に配分する課題では、**分担金を差し引いた額**を書く (総額は総額欄が別に受け持つ)。
  「代表だから総額を書く」と思い込むと括弧欄が総額と同値になり、事務チェックで差し戻される
  (2026-09 実例: 括弧欄に総額を書いて「分担者配分を除いた本人使用額に」と赤字指摘)。
- **(4) 兼業欄は兼業・非常勤専用** — 本務の所属・役職は書かない (システムが別途保持している)。
  他大学の非常勤講師や学外の兼業がある場合のみ行を立てる。空でも正常。
- **エフォート合計 ((1)(2)(3) の和) に機関ローカルの目安がある場合がある** (「30〜50% 以内」等)。
  JSPS の公募要領には上限の規定が無いので、超過を指摘されたら**機関の運用目安かどうかを
  事務に確認**した上で、上げたいなら理由 (= 応募 1 件あたりの最低確保分) を添えて相談する。
  各行のエフォートは金額規模に対して単調であることが読み手の期待 (小額課題に大きな値を置くと
  相違点欄の説明と齟齬して見える)。
- 相違点欄には「左記の研究課題を応募 (受入れ) するに当たっての所属組織・役職」の必須
  sub-field が付く。エフォートは e-Rad の分担者承諾時に入力した値と整合させる。
- 同時応募する種目間 (例: 基盤と挑戦的) では本欄は互いの鏡像になる。転記表を 1 つ作って
  両方に使い、**片方だけ直した場合のもう片方への波及**を必ず確認する。同日に複数種目を
  順に提出する場合、先に出した種目の本欄には後の種目の行が構造的に載らない — 差し戻し・
  修正の機会に後追いで足す宿題を TODO 化しておく。
- 「e-Rad登録情報を参照」で自動投入される行は、**課題名・研究期間が e-Rad 登録値のまま入る**
  (画面で修正可)。応募書類側で通称・略称を使っていても、本欄は e-Rad 値を採用するのが安全
  (整合性照合の基準が e-Rad 側にあるため)。金額・エフォート・相違点は自動では入らず手入力。
  e-Rad との連携ラグは通常 60 分程度と画面に注記される。
- **本欄はシステム生成の提出確認用 PDF に頁として含まれない** (2026-08 に 2 種目で実測)。
  提出前検品で「確認用 PDF に本欄が無い」のは正常であり、本欄の検品は入力画面 (エフォート
  合計・行数) で行う。提出後に本欄の確定値を残したければ入力画面の値を転記表へ書き戻す。
- **e-Rad 自動連携で行が立つものの実測射程** (2026-08、学術変革公募で実測): 自動で立つのは
  ① 自分が e-Rad 経由で応募中の他制度課題のうち**研究期間が応募年度に掛かるもの**
  (応募年度前に完結する課題は出ない)、② **受入予定の科研費分担課題** (承諾済み)。
  **出ないもの** = 科研費の応募中課題 (自分が代表でも出ない。画面注記「研究経費や
  研究機関単位の応募課題は連携しておりません」= 機関経由で応募する課題は対象外) →
  基盤・挑戦的等の応募中行はすべて手入力。
- 数値欄 (総額等) は**全角数字を「半角数字で入力してください」で reject** する。手打ち・
  コピペとも半角で。

### その他の欄仕様 (実測)

- 「内容を表す用語」欄は**特設審査領域で応募する場合専用** — 中区分・小区分での応募では
  グレーアウトされ入力できない (空のままで正常)。
- 要約系のテキスト欄は「改行不可」「改行 1 回 = 全角 1 文字換算」等の欄ごとの制限が
  注記されている。字数は貼る前に len() で検査しておく。
- 経費の「必要性」テキスト欄は**費目ごとではなく 2 欄構成** (「設備備品費、消耗品費の必要性」/
  「旅費、人件費・謝金、その他の必要性」= 3 費目まとめて一欄)。各欄「500 字以内」の実体は
  **1000 バイト制限 (全角 2 バイト・半角 1 バイト換算、改行 3 回まで・1 回 = 全角 1 字扱い)** で、
  半角英数を含めば 500 字を超えても通ることがある一方、超過はエラーで保存されない
  (2026-08 実測: 737 字で byte 超過)。貼る前に `2*全角数 + 半角数 + 2*改行数 <= 1000` を検算する。
  0 円の費目 (人件費等) も同欄内に「計上しない (理由)」と 1 文書いておくと欄の完結性が保てる。

## <a id="track-record-section"></a>欄「研究遂行能力及び研究環境」— 論文以外の材料を CV から発掘する

評定要素「研究遂行能力及び研究環境の適切性」に対応する欄の記入要領は、**論文以外の材料を明示的に
招いている**: 「研究計画に関連した国際的な取組（国際共同研究の実施歴や**海外機関での研究歴**等）」
「研究業績（論文、著書、産業財産権、**招待講演**等）」。書き手の意識は論文リストに寄りがちで、
以下が CV に眠りやすい (2026-09 の基盤(B) 改訂で実測):

- **海外機関での研究歴** (ポスドク歴・長期滞在) — 記入要領の文言に literal 正対する一級材料。
- **受賞と、その選考委員等の役務** — コミュニティでの位置の evidence。
- **競争的資金の獲得状況** — 代表課題の完遂数 + 異分野 (実験系等) との分担参画は計画の実行可能性に直結。
- **日付つき業績統計** (総被引用数・h 指数・直近 N 年の誌上掲載数・招待講演の通算数、出典 DB と取得月を明記) —
  看板業績が古い場合、「直近 3 年で N 編」型の自己申告より統計の方が「近年の生産性」への割引を正面から反証する。

注意点 3 つ:

- **年数・件数の self-claim は、審査員に見える業績リストから検証可能な形にする**。「10 年以上主導」と
  書いてリスト最古の論文が 8 年前なら、欄内の証拠と矛盾する誇張と読まれる (実例あり、独立査読で検出)。
  「YYYY 年から」型 (= リスト最古の年を使う) が同じ強さで反証不能。
- 🔴 **「論文は既に掲載されているもの又は掲載が確定しているものに限って記載すること」** (記入要領)。
  参考文献リストの見出しを「研究業績」とすると、計画説明で引いた arXiv preprint がこの制限に抵触して
  見える。**見出しを「引用文献」に変えれば** preprint は計画の引用として正当に並び、本文で名指しする
  主要業績を掲載済みに限れば compliant になる。⚠️ 見出しの改称だけでは事務チェックを通らない —
  **1 件ごとに掲載状態が読めること**まで要る (2026-09 に arXiv 番号だけの entry へ「雑誌名？」と
  赤字。見出し改称済みの種目でも同じ指摘が来た)。**状態ラベルを機械で付ける**のが安全:
  誌名/DOI を持つ entry に「（査読有）」、持たない entry に「（プレプリント）」、査読誌に投稿中と
  一次記録で確認できる entry だけ「（投稿中）」。**見出しにも凡例を書く**
  (「引用文献（…査読有＝誌上掲載済、arXiv 番号のみ＝プレプリント）」)。
  実装は `.bbl` の後処理が確実 — `\bibitem` で split し、DOI 有無で分岐して entry 末尾の
  `.` の直前に挿入し、**付与件数を assert** する (末尾 entry は `\end{thebibliography}` を
  従えるので正規表現の末尾 anchor がずれやすく、silent に 1 件落ちる)。
  「（投稿中）」は**投稿の一次記録 (投稿番号・審査状態) がある entry に限る** — 状態の粉飾は
  掲載状態そのものより重い瑕疵になる。
- **著者名の下線は事務が明示的に求めることがある** (「先生のお名前の下に線があると分かりやすい」)。
  種目の様式が下線規則を持つなら (研究代表者＝二重下線 / 分担者＝一重下線 等) それに従い、
  無くても申請者名に下線を引く。これも `.bbl` 後処理で全 entry 一括 (手で引くと漏れる)。
  ⚠️ 姓名の綴りが bib entry 間で揺れると (`K.-Y.` / `K.-y.`) 置換が一部だけ当たる — **正規化 →
  置換 → 件数 assert** の順に組む。
- **引用は代表 2–3 本に絞る**。自著 N 本の並列 cite はリスト行を食い、審査員には件数の主張にしか
  見えない。「N 編を産出（代表例 [x--z]）」と件数と代表を分離する。**被引用数を書くときは必ず一次 DB と
  突合する** — 同著者・同テーマの姉妹論文と arXiv ID を取り違えて別論文の被引用数を焼く事故は実際に
  起こる (審査員が DB を引けば水増しに見える、最悪の誤記類型)。

## <a id="collaborator-naming"></a>研究協力者の書き方 — 実名×役割が匿名の分野列挙に勝る

- 研究協力者は e-Rad の応募資格登録も機関承諾も不要で、大学院生等も参画できる (公募要領の研究組織節に
  例示。学部生を排除する文言もない)。氏名記載に手続き上の同意要件は無い — 事前の一報は礼儀の問題。
- **「◯◯分野の共同研究者」という匿名の役割列挙は、検証不能な体制として弱く読まれる**。「氏名 (担当分野)」の
  実名列挙は、審査員には未知の名前でも「計画の柱ごとに実在の担当者がいる」証拠になる — 研究方法の
  各柱に 1:1 で named 対応させると効果が最大 (2026-09 実測: 3 本柱 + 横断 2 役の 5 名構成)。
- **調書に書くのは氏名と役割だけでよい**: 所属・身分を書かなければ審査員には見えない (協力者は
  researchmap/KAKEN 参照の対象外で、検索しても出ない名前が普通)。学生協力者の身分をあえて開示する
  利得は、評定要素に人材育成が無い種目では無い — 「この柱は学生頼みか」と読まれる下方リスクだけが残る。
- 実名化の前に氏名の SoT 照合を通す (漢字は連絡先 DB・共著論文の author block から取り、推測で
  起こさない = [name-rendering.md](name-rendering.md) の一般則)。

## <a id="mock-review-and-claims"></a>提出前の模擬書面審査と、主張の帰属検証

- **模擬書面審査**: 別 session (または別人) に**審査員 persona を指定し、調書本体のみを読ませて**
  (内部資料・準備 note は意図的に不読 = 先入観排除) 模擬審査させると、評定要素別の評点と「審査で最も
  突かれる穴」が具体的に返る。改訂担当と査読担当を分離すると採否判断も冷静になる (adopt/reject を理由
  つきで記録)。物理検証の「独立した第二の目」kernel ([physics-verification-cycle.md](physics-verification-cycle.md))
  の文書版 instance。実測では、真物理の穴 (質量スケール未特定・アノマリー無言及)・compliance・記号 drift
  まで 1 往復で挙がった。
- 🔴 **第三者の誤りを名指しする主張は、書く前に一次記録と突合する**。「X らの計算の誤りを特定・訂正した」
  型の文は審査員に検証されうる最強度の主張であり、誤っていれば方法論の看板ごと崩れる。実例: グループ内の
  人名略称を、同分野の著名研究者の名前に**誤展開する名前衝突**で、自分たちの論文の誤植訂正を他人の論文の
  訂正として書いた事故 (独立査読で検出)。検証できない名指しは削る方が強い — 多くの場合、真実 (機械検証が
  自分の出版済み論文の誤りを検出した等) の方が宣伝として優れる。一般則 (帰属の第二軸 = claim-target /
  内部略称の衝突展開 / 確認設問の照準) = [actor-attribution.md#claim-target-attribution](actor-attribution.md#claim-target-attribution) +
  [convention-design-principles.md#confirmation-question-aim](../docs/convention-design-principles.md#confirmation-question-aim)。
- **図が語る不都合は本文で先回りする**: 理論点が観測許容域の外に落ちる図を載せるなら、その事実と含意
  (緊張こそが動機になる等) を本文で言語化する。図と本文の黙った不整合は審査員の第一の突っ込み所。
- **観測到達性の数字を最低 1 つ書く**: 効果の桁 (Δ観測量 ∼ 10^{-x}) と現行・次世代精度の比較が 1 文
  あるだけで、「小さすぎて見えない」と「大きすぎて信用できない」の双方向の批判を同時に塞げる。数字ゼロの
  調書は審査員に算術をさせる (= 減点側に倒れる)。
- **「未解決/係争中」と框付ける問いは、先行研究が「解決済み」と結論していないか検査する**。結論している
  場合は帰属 1 句 (「先行解析 (X ら YYYY) は…と結論したが——」型) を添えて、何が新しく何を裁定するかを
  明示する — その分野を知る審査員が「あれは X らで決着済みでは」と誤認して斬新性を割り引く事故の予防接種。
  自分の基盤論文が当該先行研究を引用していれば、その引用文脈をそのまま流用できる (論文と調書の整合も保たれる)。
- **同一量の別表式は定義点で恒等式に繋ぐ**: 本文で n = a/b、図 caption で n ≃ c/d のように同じ記号の
  異なる表式が離れて置かれると、恒等式を明記しない限り検算する審査員には矛盾に見える。定義箇所で
  chain (n = a/b ≃ c/d) にして本文と図の軸ラベルを接続する (= 図の境界線が軸から導出可能になる副作用も大きい)。

## <a id="frozen-revision-geometry"></a>提出後の差し戻し改訂 — 頁ジオメトリを保存して差し替え可能に保つ

学内提出後の調書は凍結されるが、機関承認前なら**差し戻し**で添付 PDF を差し替えられる (依頼は担当事務
経由、JSPS 本〆から逆算した hard deadline で TODO 化)。提出済み文書の改訂は「いつでも差し替えられる形」を
保って組むと安全域が最大になる (2026-09 に 2 種目で実測):

- **Web 入力項目を触らない改訂に絞る**: 差し戻し窓の作業が「添付 file の再アップロードのみ」になり、
  再入力ミス (字数の改行換算・全角 reject・波ダッシュ実体参照 [#textfield-wavedash-entity](#textfield-wavedash-entity)) の
  リスクと所要時間を最小化できる。
- **頁が満杯の文書への挿入は、同一段落内の等量トリムとペアで設計する** (字数収支ペアリング)。
  [#layout-pendulum](#layout-pendulum) の「文字数トリムは行数に効かないことが多い」の逆用 — 行数を**変えない**ためにこそ
  段落単位で文字数を数える。行単位の不足は縦レバー (文献リストの `\itemsep`、見出し前の小さな負 `\vspace`) で補う。
- **検証は目視でなく座標で** (PyMuPDF): ①頁数不変 ②各頁の最終行 bbox y 座標を改訂前 PDF と比較
  (全頁一致 = 行数レベルで無変化の証明。伸びた頁は下余白限界との差を実測して残余白を数値で残す)
  ③ `.log` の Overfull/Underfull `\vbox` = 0 ④行頭句読点 scan ([latex.md#line-initial-punct-scan](latex.md#line-initial-punct-scan))
  ⑤新旧文字列の存在確認 (テキスト抽出は空白が揺れるので `\s+` を潰してから照合)。
- 残余白を使い切ったら「この頁にはもう 1 字も足せない」と状態記録に明記する (= 次の改訂者への guard)。
- 提出時 snapshot は不変に保ち、改訂は作業 tree で組む。差し替え予定物の一覧は差し戻し窓の carrier TODO に
  追記する (同じ窓で処理する修正が複数種目にまたがるなら 1 TODO に集約 = 窓を 1 回で使い切る)。

## <a id="form-template-integrity"></a>様式を組み直したら、様式の骨格と埋め込み指示は自分で持つしかない

調書を**様式 docx のまま埋めず、LaTeX 等で組み直す**運用 (頁ジオメトリを自分で制御したい / 数式・図が要る
場合の定番) には、docx 運用には無い構造的な穴が 2 つある。どちらも 2026-09 に差し戻し事由になった。

🔴 **この赤字は繰り返される**。「様式の改変は認められません」は 2025 年に**図形**の改変
(様式のひな型が直角二等辺三角形なのに別形になっていた) で、2026 年に**表と見出しの消失**で、
別々の制度・別々の年に同じ文言で来た。**1 度言われたら台帳に載せ、以後は毎回検査する**。
⚠️ 図形の改変は文字列比較では拾えない — 様式を組み直す / 図を差し替えるときは
**様式のひな型と図形を目視で突き合わせる**しかない (機械化していない残り)。
同じ回に「元の様式からフォントが崩れている (Word で作成したか)」も来ている。

1. **様式の骨格が「自分が打った文字列」に化ける**。docx を埋める運用なら
   [`diff-form-docx.py`](../scripts/diff-form-docx.py) が LABEL_OVERWRITE / 見出し消失を捕まえるが、
   組み直すとその網が丸ごと外れる。改訂を重ねるうちに**様式にあった見出し・表・記述欄が黙って消える**。
   実例: 「研究計画最終年度前年度応募」欄の表 (研究種目名 / 課題番号 / 研究課題名 / 研究期間) を落として提出し、
   「元の様式にあった部分が消えている、様式の改変は認められない」と赤字。
   ⚠️ **様式に無い見出しを足すのは自由だが、様式にある見出しを消すのは改変**。該当者でない欄も空欄で残す。
  ⚠️🔴 **様式には「空欄で出す欄」と「必ず書く欄」が両方ある**。片方だけ見ても事故は防げない —
  空欄指定の欄に書いて「トル」(2024)、必須の欄を空けて「記載して下さい」(2022)、どちらも実際に受けた。
  ⚠️🔴 **「該当しない場合」の扱いは欄ごとに逆**なので、欄ごとに様式の文言を読む。
  人権の保護の欄は「該当しない場合には、**その旨記述**すること」= 書く。
  最終年度前年度応募の欄は「記述欄を削除することなく、**空欄のまま提出**すること」= **書かない**。
  実例 (2024): 後者に「該当しない。」と書いて「トル / 空欄のまま提出するため」と赤字が入った。
  つまり**丁寧に埋めたことが誤り**になる欄がある。
2. **様式 docx に印字された指示が読まれない**。様式本体には守るべき要件が literal で書かれている —
   上の実例はまさに様式自身が「**該当しない場合は記述欄を削除することなく、空欄のまま提出すること。**」と
   印字していた欄で起きた。他にも「各頁の上部のタイトルと指示書きは動かさないこと」「空白の頁が生じても
   削除しないこと」「本文は 11 ポイント以上」「論文は既に掲載されているもの又は掲載が確定しているものに
   限って記載すること」等。**事務の赤字の相当部分は、様式が既に言っていたことの未適用**にすぎない。
   xlsx 様式の同型 = [office-automation.md#embedded-instruction-in-label](office-automation.md#embedded-instruction-in-label)
   ([`scan-form-instructions.py`](../scripts/scan-form-instructions.py) は xlsx 専用で、docx 様式は射程外だった)。

### 裏返しの失敗 — **消すべき注意書きを残す**

様式の骨格は消してはいけないが、**注意書き・記入要領は消さなければいけない**。様式にそう印字されている
(「○…このテキストボックスごと削除すること○」「青字の注意書きは提出時に削除」)。組み直し運用では骨格の消失が、
**様式を埋める運用では注意書きの残存**が起きる — 同じ様式の二つの端。

2026 年度の実例 (科研費以外の助成・機関事務の赤入れ):

- 事務が削除を求めた §予算の記入要領が提出版に残り、**2 段構えの検証を両方すり抜けた**。
  ① phrase list 照合 = list に無い文言は見えない (list-based audit の implicit-scope 盲点)
  ② 目視 = 縮小 render で色を判別できなかった。
- 原因は **色の判定を docx の run 属性で行ったこと**。当該段落は**段落 style が色を定義**しており
  run に `w:color` が無いため、run 色だけを見る判定は `None` を返して 10 段落を素通しした。
- 🔴 **色で意味を持つ要素の検証は、色そのものを ground truth にする** — すなわち
  **提出 PDF の render span 色**を見る。docx の属性は style 継承で嘘をつく。
  審査員・事務が見るのも render である。
- 🔴 **削除に使った判定 (predicate) で検証しない** (循環)。predicate が漏らすものは検証も漏らすので
  「OK」が嘘になる。検証の ground truth は**空の様式**に置く (= 削除ロジックとは独立な source)。
- 別の助成では、様式の赤字「収入合計と支出合計を一致させてください」を残したまま郵送・受理された
  (2026-07、事後に検査器で発見)。**受理されても瑕疵は瑕疵**として台帳に残す。

無彩色を色と数えないこと (= 本文が `#111111`、スキャンが `#231f20`、白抜き、灰の透かし)。
彩度 (max−min) で切ると、赤 `#ff0000` と青 `#0070c0` は通り、これらは落ちる。
⚠️ この検査は**提出物そのもの**にだけ当てる — 公募要領・受領論文・見積書は色で意味を持つのが正常。
⚠️ **スキャンには効かない** (text span が無い)。事務が返してくる赤入れは大抵スキャンなので、
そちらは file 単位の台帳が担当する — 2 つの機構は補完関係で、片方では塞げない。
実例 (2026): 同じ年に 2 つの財団・事業で「青字を削除してください」を受けている。

機械化 = [`kakenhi-preflight.py`](../scripts/kakenhi-preflight.py) (年非依存、`--selftest` 内蔵):

```
kakenhi-preflight.py --form 様式.docx --pdf 組上がり.pdf [--keihi 明細.csv]
```

- 🔴 `SKELETON_LOST` — 様式が**削除を禁じた欄** (「削除することなく」「削除しないこと」「動かさないこと」) の
  見出し・ラベルが PDF に無い。保護の scope は**文書順**で取る (マーカーと見出しは別ノードにあるので、
  同一ノードの文字列一致で紐付けると実例を取り逃す)。
- 🟠 `SKELETON_MISSING` — その他の番号付き見出し・表ヘッダの消失。
- 🟠 `BLANK_SECTION_FILLED` / `MUST_FILL_EMPTY` — 様式が空欄を指定した欄に書いた / 記述を求めた欄が空。
  どちらも**様式の文からその欄を特定**する (欄名を焼き込まない)。判定は「空の様式に在る文字を
  引いた残りがあるか」。⚠️ 短いラベルだけ引くと様式自身の指示書きが残って偽陽性になる。
- 🔴 `INSTRUCTION_RESIDUE` — 様式が「提出時に削除せよ」と言ったブロックの文が提出版に残存。
  署名は**様式側から自動で取る** (手で phrase list を書くと上記の implicit-scope 盲点を再現する)。
- 🟠 `COLORED_TEXT` — 提出版の有彩色の文字。記入要領の色字のほか、**著者注 (`\red{…}` 等) の
  消し忘れ**もここで捕まる。
- ℹ️ `INSTRUCTION` — 様式の埋め込み指示を category 別 (欄の保持 / 分量 / 書式 / 業績 / 内容) に列挙。
  **1 つずつ「適用したか」を verify する**のが起草時の checklist になる。
- 骨格の照合は **NFKC + 空白全除去**で行う (全角/半角・和欧間空白・組版由来の改行が揺れるため)。

規律: **様式 docx は調書 kit と同じ repo に置き** (`forms/` 等)、build のたびに preflight を通す。
様式は年ごとに改訂されるので、**当年の様式**と照合する (前年の docx で通しても意味がない)。

🔴 **「去年と同じでよい」は成り立たない — 要求項目そのものが増える**。実例 (2024):
「今年度から、本学以外の機関での**兼業状況の入力が必要**となりました」と赤字で通知された。
前年の調書を土台にすると、**新しく必要になった欄が空のまま**通る (誰も「無い」ものは見ない)。
毎年、当年の様式から指示を吸い出し直すこと ([#form-template-integrity](#form-template-integrity) の
ℹ️ INSTRUCTION 出力を起草の最初に取る)。前年の赤入れを読む ([#office-review-loop](#office-review-loop))
のと**両方**要る — 前者は「今年増えたもの」、後者は「毎年言われるもの」を捕まえる。

## <a id="office-review-loop"></a>機関事務のチェックと差し戻しループ — 書き込み PDF の読み方と指摘の類型

学内提出後、機関承認までの間に事務が全種目を通読して**差し戻し**を掛ける。e-Rad 応募と同じく
**差し戻しは正常フロー**で、手順の checklist は [erad-submission.md#sashimodoshi-response](erad-submission.md#sashimodoshi-response)
と共通 (赤字 PDF を全頁解読 / 指摘箇所のみ直す / 完了報告)。科研費電子申請システム固有の点:

- **差し戻し窓は何度でも開けられる** (機関承認前なら事務に依頼すれば再度差し戻してもらえる)。
  「1 回しか直せない」前提で妥協した修正を積まない。**同じ窓で処理する修正は 1 つの carrier に
  集約**し、種目をまたぐ宿題 (応募状況欄の鏡像追加など) も同じ窓で一緒に片付ける。
- **通知が本人に届かないことがある** (機関の ML 宛に出て転送されない等)。**差し戻しの有無を
  受信箱の有無で判断しない** — 種目ごとに再提出期限が別々に設定されることもある
  (2026-09 実例: 2 種目 = 9/9、別 2 種目 = 9/10 で、後者の通知は本人に届いておらず 1 日遅れて発覚)。
  期限を確認する第一手は事務への 1 問い合わせか、システムの課題一覧のステータス。
- **書き込み PDF はスキャン画像でテキストを持たない**ことが多い (紙に手書き → スキャン → 添付)。
  `get_text()` は空を返す。**色領域検出で全頁を機械走査**してから読む: 頁を raster 化し、
  彩度の高い画素 (赤・青・付箋の黄) の連結成分を取り、bbox を余白込みで crop して 1 枚ずつ読む。
  ⚠️ **「本文には書き込みが無い」と早合点しない** — 頁単位の色画素数だけ見て「応募状況欄だけ」と
  報告し、実際は本文・経費に十数箇所あった実例がある。走査は**全頁 × 全連結成分**で。
  crop file の命名に種目 tag を入れる (複数種目の PDF を同じ dir に出すと衝突する)。
- **指摘の類型は毎回ほぼ同じ**。着手前にこの順で自分の全種目を自己点検すると往復が減る
  (2026-09 の 4 種目 28 箇所を類型化。①②④⑤⑥は
  [`kakenhi-preflight.py`](../scripts/kakenhi-preflight.py) が機械で拾う):

  | # | 類型 | 正本 |
  |---|---|---|
  | ① | 表記 — 略称 → 正式名称 (「文科省」→「文部科学省」)、裸の数字 (「(160)」→「被引用 160」) | 本節 |
  | ② | 業績リストの下線と掲載状態 (arXiv 番号だけの entry に「雑誌名？」) | [#track-record-section](#track-record-section) |
  | ③ | 紙面の空き (下限は最終頁まで 7 割) | 本節 🔴 |
  | ④ | 経費明細の粒度 (品名・型番 / 行分け / 場所・日数・人数) | [#keihi-meisai-granularity](#keihi-meisai-granularity) |
  | ⑤ | 経費の費目帰属と二重計上 | [#keihi-meisai-expense-category](#keihi-meisai-expense-category) |
  | ⑥ | **様式の骨格の消失** (組み直し運用に固有) | [#form-template-integrity](#form-template-integrity) |
  | ⑦ | 応募状況欄の行の過不足・金額・兼業欄・エフォート合計 | [#oubo-jokyo-form](#oubo-jokyo-form) |
  | ⑧ | **進捗の時制** — 進行中の事業を成果として断定しない (下記) | 本節 |
  | ⑨ | **人的資源の制度制約** — 専念義務のある身分を戦力に数えない (下記) | 本節 |
  | ⑩ | 欄「研究遂行能力」に**これまでの研究 → 本課題の流れ**が無い (下記) | 本節 |
  | ⑪ | **ID の取り違え** (機関番号 ⇄ 機関コード / 旧値の残存)、本文と file 名の両方 | [#identity-code-verification](#identity-code-verification) |
  | ⑫ | **本文内の用語のゆれ** (同じものを「研究補助員」と「研究補助者」で書く) | 本節 |

- 🔴 **同じ指摘を 2 度受けたら、原稿ではなく「前回の対応が着地したか」を最初に疑う**。事務は
  **システム上の現物**を見ている。こちらの手元には「直した」記録があるが、それは**リポに着地した**
  記録であって**システムに着地した**記録ではない。最初の 1 手 = 前回の提出確認用 PDF と手元の期待値を
  機械で突合する (数分)。原稿を開くのはその後。実例: 2026-09-11 に受けた指摘 3 点は 9/7 の指摘と
  **逐語で同一**で、原因は原稿ではなく経費明細 CSV の取込漏れだった (= 原稿を書き直す方向に時間を
  使いかけた)。差し戻し対応の完了判定も「送信した」ではなく**「送信後の確認用 PDF に前回の指摘が
  反映されている」**に置く ([#confirmation-pdf-detail-rows](#confirmation-pdf-detail-rows))。
- 🔴 **赤字は、指摘された箇所だけでなく全種目・全欄に横展開する**。事務は種目ごとに別々の人が
  別々の深さで読むので、**同じ瑕疵が「指摘された種目」と「されなかった種目」に同時に在る**のが常態。
  1 件直したら同じ語・同じ型を全 kit に grep する (= [convention-design-principles.md](../docs/convention-design-principles.md) の同類問題 sweep の
  この領域での instance)。実例: 2026-09 に「文科省」「(160)」を公募研究 2 件では直したが、
  赤字の付かなかった基盤研究(B) では直さず、同じ語が 3 + 2 箇所残ったまま再提出した
  (後日 preflight を全 kit に通して発覚)。**横展開したことの証拠は「全 kit を検査器に通した出力」**であって、
  「直した記憶」ではない。
- 🟠 **⑧ 進捗の時制**: 補助事業・採択課題の**期間内**に「実証済み」「実証した」と書くと
  「事業はまだ終わっていませんが…」と突かれる。**採択された事実と、そこで得た成果は別**——
  採択・進行は書いてよく、成果の断定を「構築中」「整備しつつある」に落とす。⚠️ 提出から審査までの
  数か月で状況が進むので、時制は**審査時点**でなく**提出時点**で正しい形に揃える (先取りしない)。
- 🟠 **⑨ 人的資源の制度制約**: 「学振特別研究員 (PD/DC) の受入により体制を厚くする」型の記述は、
  **特別研究員は自身の研究に専念する義務がある**ため本課題の戦力として書くべきでないと事務に指摘される。
  代替は「博士研究員の雇用（科研費雇用の実績あり）」等、**課題の経費で雇える身分**に置き換える。
  体制を厚く見せたい動機は正当なので、書き換え先を先に決めておく (削るだけだと⑨と③が競合する)。
- 🟠 **人件費が経費の大きな割合を占めるなら、本文に役割分担と雇用の必要性を書く**。
  審査は「研究経費と研究計画の整合性・研究方法の具体性」を見るので、**経費表だけで人を雇うと
  本文と噛み合わない**。事務は「(4) か (5) あたりで申請者と特任研究員・RA との役割分担と、
  雇用が何故必要なのかも入れた方がよい」と言ってくる (2024 実測)。経費の設計と本文の設計は
  同時に決める。
- 🟠 **⑫ 同じものを指す語を本文内で揺らさない**。事務は「者？ 後述と表記のゆれ」と、
  同一頁で何度でも指摘してくる (2024 実測)。特に**人的資源の呼称**が揺れやすい
  (研究補助員 / 研究補助者 / 特任研究員…) — 経費表・本文・体制説明で別々に書いてしまうため。
  機械化は「語幹が同じで**末尾 1 文字だけ違う**漢字語の共存」で拾える (`TERM_DRIFT`)。
  ⚠️ 語幹は 3 文字以上に限る — 2 文字だと「研究者 ⇄ 研究費」のような別物の対を拾う。
- 🟠 **段落冒頭の一字下げ**を落とさない (2024 実測「一字下げ」)。分野の略記も正式名称に
  (「量子エレ分科」→「量子エレクトロニクス分科」) — [#office-review-loop](#office-review-loop) ① の同族で、
  辞書は分野ごとに違うので機械化していない。
- 🟠 **本文中で文字サイズを変えない**。強調のつもりでも「他よりポイントが大きいですが、
  あえてでしょうか」と問われる。強調は太字など**サイズ以外**で行う。
- 🟠 **⑩ これまでの研究 → 本課題の流れ**: 欄「研究遂行能力」に業績を並べただけだと
  「上記の研究と本課題のつながりの流れ、基盤について、もう少し詳しく書いていただくといい」と返る。
  **年代順に 1 本の線で繋ぐ段落**を 1 つ置く (A を経て B、そこで見つけた障害が本課題の問い、の形)。
  この段落は審査基準の「実行可能性」に直接効くので、紙面の空き③の埋め方としても最良。
- 🔴 **「〈頁数〉以内とありますが、スペース的余裕があるので…7 割は埋めてください」** — 事務は
  **紙面の空きを差し戻し事由にする**。[#layout-pendulum](#layout-pendulum) は「詰めすぎ」側の危険を扱うが、
  **下限側にも実務的な閾値がある** (体感で最終頁まで 7 割)。埋め方は水増しでなく、
  審査基準に効く材料の追加 (リスクと対応 / 年次計画表 / 手法の具体化 / 成果物の共有と人材育成)。
  ⚠️ 空き頁は**差し戻しを受ける前に**埋めておくのが安い (提出前の自己点検項目に入れる)。
- 🔴🔴 **最も安い予防策は「前年の赤入れをもう一度読むこと」**。2026 年の差し戻しで受けた指摘は、
  **ほぼ全類型が前年 (2025 年) の同じ種目・同じ事務からの差し戻しに既に在った**
  (2026-09-10 に前年分を開いて実測):

  | 2026 年に受けた指摘 | 前年 (2025) に同じ指摘があったか |
  |---|---|
  | 様式の欄・見出しが消えている | ✅ 「様式にある内容を消さずに残す必要があります」+ **対処法まで**「学振 HP より Word 様式をダウンロードし確認して下さい」 |
  | 設備の品名・型番を書く | ✅ 「仕様として型番等の詳細をご記入ください」 |
  | 費目帰属 (投稿料・印刷費・登録料 → その他) | ✅ (さらに 2024 年にも。同じ指摘が **4 年で 5 回**) |
  | 応募状況欄に分担課題の行が無い | ✅ 「(1) 応募中の研究費へ入れる」「◯◯先生の基盤B分担も (1) へ」 |
  | 応募状況欄の金額・エフォート | ✅ 金額の赤字訂正 + エフォート合計 |

  つまり **前年の赤入れ PDF を 1 度読み返すだけで、翌年の差し戻しの大半は起きない**。
  起草を始める前の最初の作業をこれにする。⚠️ これが機能しなかったのは能力の問題ではなく、
  **前年の赤入れがどこにあるか誰も知らなかった**から (下記の台帳が無かった)。
- 🔴 **赤入れがスキャン PDF なら、text 検索も検査器も届かない**。過去の指摘を棚卸しするとき、
  markdown に項目化済のものだけを読むと**開いていない PDF の分が丸ごと落ちる** (実測: 2 本の
  スキャンを開いたら新しい類型が 5 つ出て、うち 1 つは「同じ赤字を 1 年前に受けていた」の発見だった)。
  → **赤入れ資産そのものを台帳化する** (制度・年度・repo をまたぐので、年度別の作業 dir に置かない):

  | 台帳が持つ | 持たない |
  |---|---|
  | file path / 日付 / 制度 / 受領経路 / 頁数 / text 層の有無 / **読了か** / 読み方 / 指摘の記録先 | 指摘の中身 (= 各 `findings_home` が持つ) |

  - ⚠️ **受け取った turn で 1 entry 足す**。`read: false` で登録してよい — 読むのは後でも、
    **記録を後回しにすると存在ごと忘れる** (これが 1 年またぎの再発を再発と認識できなかった原因)。
  - **現物の側から台帳の穴を突く検査器**を持つと、登録漏れが自動で出る。赤入れらしさは
    file 名でなく**現物の性質**で見る = ①文書全体の text 層が薄い (スキャン) ②どれかの頁に
    有彩色の画素がまとまってある。図・宛名ラベル等も引っかかるので、構造的除外 +
    台帳側の「赤入れではない」リストで落とす (= 候補を出して人が仕分ける設計。自動判定にしない)。
  - ⚠️ **1 頁目だけ見ない**。書き込みが後半にしか無い赤入れがあり、1 頁目走査では取り逃す (実測)。
  - raster 化は 1 file ~0.1 秒なので、(size, mtime) を key に cache すれば常設検査に載る
    (実測: 121 file を 10.5 秒 → 0.1 秒)。
- **人的体制の書き方は制度ごとに反転しうる**。ある制度では「専念義務のある身分を戦力に数えるな」、
  別の制度では「若手研究者の参加があると望ましい」と来る。**審査基準が違えば逆になる**ので、
  この類型だけは他制度へ横展開しない (経費の費目帰属や表記は横展開してよい)。
- 事務の付箋には**申請者が対応すべきでない情報メモ**も混じる (審査のカラー/モノクロ運用、
  重複制限の件数、領域代表者名など)。**指摘と情報を分けて台帳化**し、対応不要と判断したものは
  「対応不要」と理由を書いて残す (次の窓で読み返したときに再検討しないで済む)。

## <a id="identity-code-verification"></a>ID (機関コード・研究者番号) の取り違えを機械で止める

研究者番号・機関番号・e-Rad 所属機関コード・法人コードは**似た形の数字が複数ある**うえ、
本文にも**提出 file 名**にも埋まる。2026 年度に 2 度差し戻された:

1. **種類の取り違え** — 科研費の**機関番号** (5 桁) を e-Rad の**所属機関コード** (10 桁) の欄と
   file 名に書いた。事務の赤字は「10 桁化」。
2. **値そのものが誤り** — 事務の口頭指示 (11 桁) から末尾 0 を削って推定した 10 桁が誤りで、
   **その値のまま提出・受理・採択された**。3 か月後の別回の差し戻しで初めて確定した。

規律:

- 🔴 **誤りと確定した旧値を記録から消さない**。消すと「提出物に旧値が残っていないか」を機械が
  見られなくなる (捨てた情報は検査できない)。旧値は「使用禁止」と明示して**同じ表に残す** —
  過去の提出物を再現する用途では旧値が正しいので、削除でなく**種別のマーキング**で区別する。
- **値の層と検査の層を分ける**。「誰の機関コードが何番か」は汎用検査器の観客にとって true でないので、
  検査器は**値を持たず**引数で受ける。⚠️ **値が公開情報かどうかは層の判定に関係ない** —
  層は audience で決まる (これらの ID は KAKEN や機関番号一覧に載る公開情報だが、
  「odakin の値」であることが個人層に置く理由)。
- **正本は 1 つ、複製は作らない**。検査器に渡す機械可読形式は、人間が読む正本から**その場で生成**して
  渡す (persisted な複製を置くと drift する)。
- 🔴 **file 名のコードは「桁数」で判定しない**。staging の file 名には日付 `_20260908_` や hash が
  入るので、「N 桁の数字」を ID とみなすと**🔴 の偽陽性で提出が止まる** (実測)。判定は
  **宣言された ID 値と一致するか**で行う (= 値駆動)。宣言のどれとも一致しない token は無視する。

機械化 = `kakenhi-preflight.py --identity <yaml>`:
`IDENTITY_STALE` (🔴 旧値が中身か file 名に残存) / `IDENTITY_FILENAME` (🔴 file 名のコード位置に
別種の ID が入っている)。`--selftest` は上の 2 事故を fixture として持つ。

## <a id="submission-artifact-staging"></a>差し替え物の版を取り違えないための staging 機構

差し戻し改訂の最大の事故は物理的な取り違え — 同名の調書 PDF が複数系統 (提出済 snapshot /
自己改訂版 / 事務対応版 / 盲検レビュー用 referee copy 〔= 作り方と隔離の作法は
`ai-collaboration/conventions/cold-eyes-isolation.md`〕 / 次版) 並存し、人間がファイル選択
ダイアログで拾い間違える。**「どれが最新か」を人間の記憶に置かない**設計にする:

1. **build stamp** — ビルド script が `source の sha256` と `出力 PDF の sha256` を stamp file に
   書く。staging はこの stamp と現物を照合し、**tex を直したのに再ビルドしていない / PDF だけ
   別経路で作った**状態を拒否する。
2. **staging dir 一本化** — `upload/` 等 1 つの dir を毎回**空にしてから**再生成し、
   「ここ以外からは上げない」を規約にする。file 名に `<日付>_<hash 先頭 8>` を入れると、
   画面で選んだ物と手元の物の同一性が目視で照合できる。同じ dir に**転記シート・取込 CSV・
   手順 README** も一緒に吐くと、提出作業中に別 dir を開く理由がなくなる。
3. **content gate** — 頁数・欄の最終行 y 座標・**必須語 / 禁止語**を staging 時に検査する。
   必須語 = 改訂で入れた語、禁止語 = 改訂で消した語。改訂を重ねると「直したはずの語が
   別 build で復活」が起きるので、**回帰 guard として語のリストを育てる**。
   ⚠️ PDF テキスト抽出は和欧間の空白が揺れる — 比較は `\s+` を潰してから。
4. **入力後の突合 (verifier)** — 提出前の最後の gate。システムが吐く提出確認用 PDF と、
   応募状況欄の画面印刷 PDF を読み、SoT (下記) の全項目が**含まれるか**を ✓/✗ で列挙する。
   照合は「空白を潰した部分文字列一致」にすると表のセル分割に依存しない。
   **添付 PDF の全頁が手元の現行ビルドと一致するか**まで見れば版の取り違えが機械で捕まる。
   ⚠️ 応募状況欄の印刷 PDF は**全種目の課題名を行として含む**ので、「どの種目の PDF か」を
   課題名の包含で判定すると誤判定する — **最初に現れた課題名** (= header) で判定する。
5. **Web 入力値の SoT を 1 つの data file に** — 課題・金額・期間・エフォート・相違点文・
   経費・添付名を 1 つの yaml 等に集約し、**転記シートは生成物**にする。生成の前に gate:
   ① 導出関係 (本人使用額 = 年度計 − 分担金) ② **鏡像** (全種目の応募状況欄が同じ課題集合・
   同じ金額・同じエフォート) ③ エフォート合計 ④ 各数値の literal が出典 file に実在
   ⑤ 相違点文の禁止文字 ⑥ 経費 CSV との年度計一致。
   実績: この gate が、事務への打診メールに書いた内訳の合計が 1 ずれていた誤記を検出した
   (= 人間が読んで通した数字を機械が捕まえた事例)。

6. **staging gate から年非依存の事務指摘検査を呼ぶ** ([#office-review-loop](#office-review-loop) の類型のうち機械で拾える分)。
   差し替え物は必ず staging を通るので、**差し戻し窓を開けた瞬間に発火する**のが利点。
   [`kakenhi-preflight.py`](../scripts/kakenhi-preflight.py) を `--strict --ack <ack file>` で呼び、
   🔴 はもちろん **🟠 も「直す」か「ack file に理由つきで記録する」までは PASS させない**。
   - 🟠 を「人が判断すればよい」で素通りさせると横展開漏れになる (2026-09 実例: 略称と裸の数字の
     指摘を、赤字の付いた種目だけ直して他種目に残したまま再提出した。どちらも 🟠 相当)。
   - ack file には **理由 (いつ・誰の判断で・なぜ直さないか) を必須**にし、任意で失効日を持たせる。
   - 🔴 **ack は種目に縛る**。検査対象を跨いで効く ack は、「この種目は見送る」つもりが
     **別種目の同じ指摘まで黙らせる** — ack 自身が横展開漏れを作る (= 塞ごうとした穴と同じ形)。
     finding には常に由来 (PDF file 名等) を持たせ、ack 側に scope を書けるようにし、
     **scope 無しの ack が複数の対象に当たったら警告**する。
     ack 済も出力から消さない (🤝 で毎回出す) — 消すと「直した」と「見送った」が区別できなくなる。
     直したら ack を削除する規律とセットにし、**使われなかった ack は 🧹 で報告**させる
     (= 直したのに残った記録が次の本物を隠すのを防ぐ)。
   - この ack file は副次的に「**次の差し戻し窓で直す宿題リスト**」になる (今回は見送るが記録は残す、
     を機械可読に表現できる唯一の場所)。

⚠️ **盲検レビューに出した referee copy は canonical と別物**になる (改訂が進むため)。staging 時に
**両者の hash を比較して古ければ警告 + 本文 diff を残す** — レビュー結果の頁番号・文言は旧版基準
なので、そのまま当てると位置がずれる。反映は必ず**現行 source に対して**行い、referee copy を
書き戻さない (汚染隔離の一般則 = [cold-eyes-isolation.md](cold-eyes-isolation.md))。

## <a id="assisted-web-entry-runbook"></a>Web 入力を人間が打ち AI が照合する時の手順 (2026-09-08 実測、 4 種目 40 分)

差し戻し再提出の Web 入力を「人間が画面を操作し、AI が値と照合を持つ」分担で回した実測手順。
値の正本 (Web 入力 SoT) と転記シートが既にある前提 ([#submission-artifact-staging](#submission-artifact-staging))。

1. **画面ごとに「変えるところだけ」を出す**。転記シート全文を渡しても人間は読まない。差し戻し
   では大半の欄が既入力なので、AI は「この画面で触るのは N 箇所」の形で、**画面の並び順に**
   (役割 → 資金制度 → 経費 → 括弧 → エフォート → 相違点 → 所属役職 → 期間 → 課題名 → 代表者 → 総額)
   表で出す。新規行は「追加ボタンで空枠を出して、その枠を上から順に」と枠単位で書く。
   「所属役職は全部 ○○」のような**まとめ書きは通じない** — 枠ごとに全欄を書く。
2. **人間は画面のテキストを丸ごと貼る** (確認画面 or 入力画面をそのまま select-all → paste)。
   AI はそれを SoT と突き合わせて「合っている / ここが違う」だけを返す。screenshot より
   テキスト貼付の方が照合が速く、確認画面 (入力確認) は全行が 1 頁に出るので最適。
3. **アップロードする file は AI が Finder で選択状態にして前面に出す** (`open -R <file>` +
   Finder activate)。chat のリンクは file 選択ダイアログに使えない。種目が変わるたびに言われる
   前に次の file を出す。
4. **提出確認用 PDF はダウンロードフォルダから AI が拾って verifier にかける** (ZIP なら展開)。
   「研究費の応募・受入等の状況」は確認用 PDF に無いので、2 の貼付テキストで照合したことを
   記録に残す (印刷 PDF は取らなくて済む)。
5. 送信ごとに **snapshot (`submitted/<日付>-sai/`) + status.md §提出記録 + 次の種目の file を Finder に**。
   4 種目を 1 晩で回した順は 基盤B → 萌芽 → 公募 2 件 (期限順、 かつ鏡像の親から)。

罠 (同日実測): 「事項」72 バイト上限 [#keihi-meisai-field-limits](#keihi-meisai-field-limits) /
相違点欄の prefix 照合は画面の現行文を SoT に写してからでないと偽 ✗ になる (SoT に推測 prefix を書かない)。
🔴 **この 4 種目 1 晩の運用で「公募研究の確認用 PDF に明細行が無い」と結論したが、それは誤りだった**
(= 実際は取込漏れ。[#confirmation-pdf-detail-rows](#confirmation-pdf-detail-rows))。
**送信可の判定を「✗ が 0」だけに置かない** — 期待する artifact (種目 × {確認用 PDF, 応募状況の印刷})
が**全部揃っているか**も同時に見る。2026-09-08 は 8 個中 4 個 (応募状況は 0 本) しか集めていないのに
verifier が「✓ 全項目一致 — 送信してよい」を出せる状態で、応募状況側の指摘 5 件は一度も機械照合されなかった
([convention-design-principles.md#fail-loud-not-fail-empty](../docs/convention-design-principles.md#fail-loud-not-fail-empty) の入力欠落版)。

**次の段階 = AI が打つ** (同日夜に sandbox で実証済): ログインだけ人間、以降の画面は Browser pane + JS で AI が
入力し ([#ai-write-route](#ai-write-route))、参照画面を自分で読んで SoT と突合する ([#ai-read-route](#ai-read-route))。
人間の役割は「ログイン → 添付 upload → (分担者追加) → 送信ボタン」に縮む。claude-in-chrome の `form_input` は
frameset で ref が取れず、本体ドメインも拒否されるので使わない ([web-tools.md#browser-pane-frameset-popups](web-tools.md#browser-pane-frameset-popups))。

## <a id="koubo-kenkyu-mechanics"></a>公募研究 (学術変革領域研究) の実務

- **重複制限**: 公募研究の新規応募は **2 件まで、ただし別領域に限る** (同一領域内は 1 件のみ)。
  基盤・挑戦的の代表応募との重複可否は当年の別表 1 で個別確認 (種目×年齢帯で異なる)。
- **Web 入力の入口 = 領域選択画面**: 全領域×研究項目番号×単年度上限額の**行単位**で [登録] を
  押して進む。同一項目に上限額の異なる複数行 (tier) を持つ領域があり、**tier ごとの採択目安件数**が
  公募要領の別表に載っている — 単独理論なら件数の多い低額 tier が通りやすいことが多く、tier 選択も
  応募戦略の一部。領域・項目の公募文言の現物 (別表 2 の当該頁) に調書を literal 正対させる。
- 応募情報は 研究課題情報 / 研究経費とその必要性 / 研究費の応募・受入等の状況 の 3 画面 +
  添付 (S-74)。**応募・受入等の状況は PDF に変換されない** (画面注記) — 提出確認用 PDF の検版で
  「本欄が無い」のは正常。
- 経費明細が少数行 (目安 10 行以下) なら CSV 取込より手入力が速い (CSV は行数が多い種目向け)。
- **学内〆切超過の救済**: 電子申請システム自体は学内〆後も送信を受け付ける (機関承認が後段に
  あるため)。支援課に受付可否を確認の上、送信 → 一報の順で。事後になった説明は事実ベースで
  簡潔に (過剰な謝罪の重ね置きは不要)。

## <a id="title-collision-check"></a>研究課題名の衝突検査 — 語が「よそのホットトピック」と衝突しないか

**課題名を確定する前に、タイトルの各キーワードについて 2 つを検査する**:

1. **正対**: 公募文言・審査区分の語彙に literal に対応する語が入っているか (審査員が公募内容と
   照合したとき課題名だけで対応が見えるか)。
2. **衝突**: その語が**単独では同名の他分野・他文脈のホットトピックとして誤読されないか**。
   タイトルは審査割当と第一印象を決める — 本文中の hedge や定義ではタイトル単独の誤読は解けない。
   衝突が見つかったら、語を機構名や対象に**縛る** (「X」→「X型 Y 崩壊」) か、新規性の否定形
   (「〜に依らない」) を冒頭に置いて generic 読みを遮断する。

実例 (2026-08、学術変革公募): 「超放射」単独 → 回転ブラックホールの superradiance (アクシオン
生成、当該領域でホット) や Dicke 原子系と誤読される → 「超放射インフラトン崩壊」と機構に縛って
遮断。「宇宙再加熱」単独 → 総称すぎて「よくある再加熱研究」に沈む → 「共鳴に依らない」を冒頭に
置いて標準機構 (パラメタ共鳴) との差分を宣言。
