# 口コミ (宿・店のレビュー) の起草と投稿先の選び方

**Load this when**: 本人が体験した宿・店・サービスの評価を、 agent が文章に整えて本人が投稿するとき。
投稿そのもの (送信ボタン) は本人が押す。 agent は文面・投稿先の適格性・書式・写真の説明文までを持つ。
本人のメモは**入力であって事実の保証ではない** = 検証できる主張 (料金・部屋名・設備の注記) は、 本人が「要確認」 と印を付けていなくても書く前に検証する。

一般則 = [`machine-route-first.md`](machine-route-first.md) (経路の段)、 内蔵 Browser pane の癖 = [`web-tools.md#browser-pane-input-quirks`](web-tools.md#browser-pane-input-quirks)。
本 file は口コミという対象に固有の手順と壊れ方だけを持つ。

## <a id="eligibility"></a>書く前に、 その媒体に書けるかを確かめる

文面を整えてから 「書けない」 と分かるのが典型の無駄 (実測)。 先に投稿先ごとの条件を当てる。

| 媒体 | 書ける条件 | 入口 |
|---|---|---|
| Google マップ | 予約経路を問わない | 施設ページ → 「クチコミを書く」。 投稿後も編集できる |
| Tripadvisor | 予約経路を問わない (アカウントは要る) | 施設ページ → 「口コミを書く」。 投稿後に審査 (数日) |
| booking.com | **booking.com 経由の宿泊で、 かつ提携会社経由 (「パートナー・オファー」) でないこと**。 利用規約に「当社プラットフォーム上での評価やクチコミはできません」 と明記 | チェックアウト後の招待メール、 または「予約」 → 過去の予約の「クチコミを投稿」。 予約確認画面には欄が無い |
| じゃらん / 楽天トラベル / Yahoo! トラベル 等の国内予約サイト | その予約サイト経由の宿泊 | 予約履歴から |

- **パートナー・オファーの見分け方** (実測): 予約確認の URL が `tpi_confirmation` (third-party inventory)、 画面に「パートナー・オファー」「予約は〜と交わされ、 弊社の提携会社経由で成立します」「領収書は提携プロバイダーが発行」 の表示。 この予約では招待メールも来ないし「クチコミを投稿」 も出ない。 本人が「ボタンが無い」 と言ったら、 まずこれを疑う。
- 書けない媒体が分かったら、 予約経路を問わない媒体 (Google マップ / Tripadvisor) に切り替える。 同じ本文を流用してよい (媒体ごとに書式だけ合わせる = 下)。

## <a id="price-claim"></a>相場の主張は料金表を読んでから書く

「安い時期は一人 N 円らしい」 「M 倍取っている」 は口コミの中で最も反論されやすい主張なので、 本人の記憶で書かない。

1. 予約サイトの**料金一覧ページ**を読む。 WebFetch は予約サイトを読めない (じゃらんは文字化け、 booking.com は空、 価格比較サイトは名前解決で落ちる = 実測) ので、 **内蔵 Browser pane で開いて `get_page_text`**。 じゃらんの料金一覧は URL が `…/yad<番号>/plan/` で、 プランごと・部屋ごとの「大人 1 名 (税込)」 が全部出る。
2. 同じ条件 (食事なし / 人数) の下限〜上限を取り、 払った額との倍率を**通常帯**に対して出す (最安比は反論の隙)。 **人数が違う予約 (N 名 1 室 vs 2 名 1 室) は 1 名単価が単純比較にならない**ので、 倍率は切り下げて「以上」 の形で書く (本人の体感の「5 倍」 が料金表では 3 倍台なら「3 倍以上」)。
3. 本文には「予約サイトでは通常 X〜Y 円程度」 の形で、 出典が予約サイトであることを書く。 本人の記憶の数字 (★ 要確認) は、 確認できなければその文ごと消す。

同じ料金表から、 **予約サイトが公開している設備情報** (風呂・トイレの有無、 部屋の名前) も取れる。 これは次節の「暴露にならない」 判定に使う。

## <a id="claim-discipline"></a>事実の書き方 (反論の隙を作らない)

- **1 回の観察を一般法則の形で書かない**。 「雨の続いた後は部屋が黴臭くなります」 は 1 泊しか見ていない人が書ける文ではない。 観察した条件をつけて「雨が続いた時期の宿泊時、 部屋は黴臭かった」 と書く。
- **予約サイトが公開している情報を「暴露」 として書かない**。 風呂・トイレ共用が予約画面に明記されているなら、 それを不満の根拠にすると「書いてある」 で終わる。 使うなら「明記されているとおり共用で、 実態は〜」 と事実の並置にとどめ、 根拠は**公開されていない事実** (部屋の状態、 対応、 説明の有無) に置く。
- **広告文句と実態の差は、 実態を言葉で書く**。 「マウンテンビュー」 に対して写真だけ添えても、 茂みか崖か・隣が何かは写真では分からない。 「目の前は木が密生した崖、 右手すぐに建物の窓」 のように、 見えたものを名詞で書く。 何の建物かは断定しない (隣家か同じ宿の別棟かは客には分からない)。
- **行為の帰属**: 「係の方」 「スタッフ」 と書く前に、 相手が誰だったかを本人に確かめる。 一人で運営している宿なら「ご主人」。 推測で複数のスタッフがいるように書くと、 読んだ側に事実誤認が伝わる。 運営者の氏名は予約サイトに公開されていても本文に書かない (名指しは攻撃に読まれる)。
- **本人の原文が持つ情報を上書きしない**。 「廊下から部屋の玄関に入った時点で」 は旅館の部屋の踏込 (扉の内側の小さな玄関) を指し、 畳に上がる前から臭った、 という順序を含む。 「扉を開けた時点で」 に直すと情報が減る。 語が不自然に見えたら、 直す前に**その語が現場で正確な可能性**を本人に問う。
- **本人が言っていない評価・対比を足さない**。 「説明の中で唯一具体的だったのは〜」 のような対比は起草者の創作になりうる (実際は規則が全部具体的だった = 実測)。 メモに無い形容は入れず、 入れるなら本人に確認する。
- **敬語の向きを客の側から確かめる**。 「一人 N 円を頂く宿」 は、 受け取る側 (宿) を低める謙譲語を客が宿に代わって使う形で向きが逆。 「取る」 「請求する」。 逆に「捨ててくださいました」 「運んでいただく」 は宿の行為を客が立てる向きで正しい。
- **評価と事実を分ける**。 皮肉 (「どれだけ湿気っているのだ」) は本文の感想の段落にだけ置き、 写真の説明文や実用情報の欄には置かない (下)。
- **推測は本文に入れない**。 「女将がいないからもてなしが無いのでは」 のような因果の推測は、 書くなら「ご主人がお一人で運営されているようで、 そのご苦労は察します」 のように事実 + 配慮の形に変える。 責める調子を和らげつつ、 言い訳の材料にはさせない。

## <a id="structure"></a>構成 = 結論 → 主問題 → 対応 → 副次 → まとめ

読む人 (次の客) は最初の 2 文で読み続けるか決める。

1. **結論** (1 段落): 何に対して何が見合わなかったか。 「建物が古いこと自体は構わないが、 分かっている問題を客に説明もなく引き渡し、 対処も客にさせる姿勢」 のように、 責める対象を 1 つに絞る。
2. **主問題** (見出し 1 つ): 時系列で事実。 宿側が問題を把握していた証拠 (置いてあった機器など) はここに。
3. **その後の対応**: 宿がしたこと・しなかったこと・客にさせたこと。
4. **副次**: 価格 (上の #price-claim)、 広告と実態、 接客。 副次は 1 見出し 2〜3 文まで。
5. **まとめ**: 「責めるつもりのないこと」 を先に列挙してから、 問題を 1 文に圧縮する。 「改善を期待して」 で閉じる。 高評価の媒体で低評価を書くなら「高評価と聞いて期待していただけに落差が大きかった」 の 1 文が、 読む側に「八つ当たりでない」 と伝える。

## <a id="platform-format"></a>媒体ごとの書式

| 媒体 | 本文の書式 | 付随の欄 |
|---|---|---|
| Google マップ | **書式なし** (Markdown の `**` はアスタリスクのまま出る)。 改行は保持されるので、 見出しは「■ 」 + 段落分け、 強調は 「」 で | 星 (総合 + 客室 / サービス / 場所)、 旅行の種類、 同行者、 任意の詳細欄 (客室 / 重要事項 / 安全性 …)。 **詳細欄は本文の繰り返しにしない**: 「重要事項」 は門限・支払い・アクセスの欄、 部屋の状態は「客室」 欄で、 宿の対応の話は入れない (欄の趣旨は部屋そのもの)。 埋めないのも正解 |
| Tripadvisor | タイトル + 本文 (下限の字数あり)。 書式なし、 改行は保持 | 星 5 段階、 訪問時期、 同行者、 写真 (説明文 = 下)、 投稿後に任意のアンケート (項目別の星 / 140 字のアドバイス / 設備の有無)。 投稿後に審査があり公開まで数日 |
| booking.com | 「良かった点」 「悪かった点」 の箇条 + タイトル + 10 点満点の総合と項目別 | 良かった点は空欄不可のことがある = 中立の事実 (駅からの距離など) を 1 行 |

- 「良かった点」 に皮肉を書かない (「除湿機の水を一度捨てに来てくれた」 は事実だが、 読んだ側には皮肉に取れる。 使うなら悪かった点の中で事実として)。
- 本文の「(写真参照)」 は、 その媒体に写真を添えたときだけ残す。

## <a id="machine-translation"></a>機械翻訳で読まれる前提で書く

Tripadvisor と booking.com は他言語の読者に機械翻訳を自動で表示する (Google マップも同様)。 日本語で書いてよいが、 翻訳で壊れる書き方を避ける:

- 主語を省かない (「言われた」 → 「ご主人から言われた」)。
- 反語・皮肉の疑問文 (「これは客の仕事でしょうか」) は肯定文に翻訳されうる。 本文に 1 つまで、 実用情報の欄には置かない。
- 「〜でしょうか」 「いかがなものか」 の婉曲は翻訳で消える。 事実の文は言い切る。
- 箇条書きの「・」 は保持される。 「■」 見出しも保持される。

## <a id="photo-captions"></a>写真の説明文は事実だけ

- 説明文の欄は短文 1 つで、 タイトル・箇条書き・書式は使えない (Tripadvisor 実測)。
- **評価語・皮肉を入れない**。 評価は本文の仕事。 「窓からの眺め。 目の前は木が密生した崖で、 右手すぐに建物の窓」 のように、 写っているものを名詞で。
- **写真だけでは分からないことを言葉で補う**。 崖は写真では茂みに見える。 機器が「置いてあった」 のか「稼働していた」 のか「客が動かした」 のかは写真に写らないので、 本人に確かめて書き分ける (「空気清浄機は止まっていたので自分で動かした」 = 実測でここを取り違えた)。
- 本文の「(写真参照)」 と説明文が矛盾しないか、 投稿前に 1 回突き合わせる。 写真に写っている物 (機器の種類・窓の外の物) と本文の語を揃える。

## <a id="workflow"></a>手順 (agent がやること / 本人がやること)

1. 本人の列記を受け取る → **投稿先の適格性** (#eligibility) を先に確認 (予約確認メール・画面の文言)。
2. 相場・設備の主張は料金表を読んで根拠を取る (#price-claim)。 本人の記憶の数字は ★ で置き、 確認できたら差し替え・できなければ消す。
3. 構成 (#structure) で起草 → 事実の書き方 (#claim-discipline) で自己点検 → 本人に全文を出す。 修正は 1 箇所ごとに本人が判断する (敬語の向き・帰属・写真で分かるかは本人にしか分からないことが多い)。
4. 媒体ごとに書式を合わせて (#platform-format) 全文を**最終メッセージに**出す。 本人が貼って投稿する。 投稿後、 本人が形式的な質問 (任意の欄・写真の説明文) を貼ってきたら、 欄ごとに答えを出す。
5. 投稿後に事実の訂正が出たら、 未投稿の媒体は文面を直し、 投稿済みの媒体は「編集」 で同じ箇所を直す (Google マップは編集可)。 どの媒体にどの版を出したかを本人側の記録に残す。
