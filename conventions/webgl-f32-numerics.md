# WebGL の f32 数値計算と f64 参照の組み方

物理量を shader で計算する viewer では、 **f64 の参照実装 (Python 等) を正本**にし、 shader はその式の f32 版とする。 以下はその組み方で、 どれも実測に基づく。 式そのものの正本は各 project の参照実装の docstring に置き、 shader の注釈はそこを指す。

## <a id="table-domain-extension"></a>事前計算 table の端は物理の境界ではない

lookup table (texture) で写像を持つとき、 table の最大引数は texture の都合で決まった端にすぎない。 利用者が端の外へ出られるようにするには、 **table を大きくして上限を先送りするのではなく、 外側を厳密に継ぐ**:

1. 写像を「強い領域 (table が担う)」 と「弱い領域 (解析的に扱える)」 に**厳密に分解**する。 例: 光線の曲がり角 = (table の端の半径までの寄与、 table の最終行から読む) + (端から観測者までの脚の積分)。 脚は被積分関数が穏やかなので shader 内の低次の求積 (Gauss–Legendre 12 点程度) で足りる。 同じ脚は、 同じ table を別の半径で読む他の層 (例: 軌道 table を使う物体の描画) の延長にもそのまま使える。
2. **近似の差分引き継ぎを使わない**: 「table 端での値と平坦極限の差を定数として持ち越す」 形は、 脚の寄与の一部を落とす (被積分関数の違いの積分がそのまま誤差になる)。 実測で目に見える大きさになった。 採るかどうかは、 f64 の厳密解と比べた数値で決める (推測で固定しない)。
3. **継ぎ目を分岐点に置かない**: 分解の境目 (どの入力を table 側に回すか) を、 写像が平方根の分岐点を持つ所 (例: table の端をかすめる光線) に置くと、 table 側と積分側に逆向きの √ε_f32 (≈ 3e-4) 程度の丸めが残る。 境目は分岐点から離れた所に取る。
4. 端でちょうど table と一致すること、 端の前後で連続なこと、 遠方で平坦極限に近づくこと、 厳密解との一致、 分岐の継ぎ目で連続・単調なことを参照実装の selftest に持つ。

## <a id="f32-conditioning"></a>f32 の条件付け

| 危険 | 起きること | 回避 |
|---|---|---|
| 90° 付近の `sin` | `|θ − 90°| < 3.5e-4 rad` で f32 の `sin θ = 1` になり、 sin から作った量 (衝突径数など) がずれの情報を失う | 小さなずれは `cos θ` (またはベクトルの成分) から作る。 解析的な恒等式で差を直接表す (例: 転回点までの距離 `w_p − w_R` を `cot²θ` の式で作る) |
| `acos(c)` の `c ≈ ±1` | √ε の誤差 (角度が小さいほど相対的に大きい) | `atan(|a × b|, a · b)`、 または横成分の長さを sin として使う |
| 小角での `sqrt(1 − c²)` | 遠くの小さな物体 (視角 ≪ 1) で c ≈ 1 の差が桁落ちする | 横成分の長さ (上と同じ) を使う |
| 積分端点の平方根特異性 (転回点) | 固定の求積点が特異性に吸われる。 端点が根そのものでなく根の近くで止まる区間でも同じで、 倍精度でも起きる (実測: 適応求積の f64 参照を固定の Gauss–Legendre に移したら、 端点が転回点のそばの脚で積分がずれ、 その積分の根を探す処理が根を見失った) | 根 `w_p` で因数分解し `w = w_p − t²` に置換 (被積分関数が滑らかになる)。 根を持つ枝の区間は、 端点が根でなくても全部この置換で積む (根から遠い区間でも滑らかなまま)。 区間幅は `(w2 − w1)/(t1 + t2)` で作り、 `t1 − t2` (桁落ち) を作らない |
| 区間の中で何桁も変わる被積分関数 | 例 = `1/w²` を小さい `w` まで積む。 固定の求積点が大きい側に足りず、 倍精度でも誤差が大きい (実測) | 対数変数 `y = ln w` (`dw = w dy`) に置換し、 一定の比で区間を刻む。 端点の近くで別の振る舞いをする所 (例 = `w → 1` の対数) は、 そこで区間を割って別の置換にする |
| 冪の溢れ | `p³` などが大きな引数で f32 を溢れる | 逆数変数 (`w = 1/p`) で解く。 固定点反復なら単調性と縮小率で収束を保証し、 反復回数を固定する |
| 定数の精度 | shader 側で求積点を計算すると f32 で丸まる | Gauss–Legendre の点・重みは f64 で出して literal で埋める |

- <a id="stationary-invariant"></a>**向きから作る不変量が停留する所では、 その不変量から次の量を作らない** — 画素の向きから衝突径数のような不変量を作り、 そこから転回点などを解く形は、 不変量が向きについて停留する所 (例 = 横向き 90°) で f32 の値が向きの情報を失い、 隣の画素と同じ値になる。 次の量は向きの精度を持つ成分 (cot など) から直接作り、 不変量は初期値にだけ使う (実測)。
- <a id="branch-from-precise-variable"></a>**分岐 (どちらの式・表を使うか) は精度のある変数で決め、 求積と表の行は同じ 1 つの量から作る** — 臨界の値の近くで、 分岐を f32 の不変量で決め、 求積と表の行を別々の量から作ると、 2 つが別の光線を指し、 当たるはずの画素が抜け、 当たらない画素が描かれる。 分岐の判定と、 求積・行の位置の入力を、 同じ精度のある量 1 つにそろえる (実測)。

## <a id="f32-emulation-gate"></a>f32 emulation を export の関門にする

参照実装の関数に dtype 引数を持たせ、 **同じ算術を `np.float32` でも回す** (NumPy 2 の NEP 50 で Python の float は弱い型 = float32 のまま進む。 定数は明示的に `dt(…)` で包む)。 shader と同じ table の読み方 (最終行・線形補間) も f32 で写す。 これで厳密解との差を測り、 texture を書き出す script の出力と metadata に「f32 誤差」 として残す (= 公開前の関門)。 厳密解側の許容誤差 (例: `scipy.integrate.quad` の既定 1.5e-8) を閾値の下限として扱い、 それより細かい一致を要求しない。

- <a id="error-in-screen-units"></a>**表の補間の誤差は、 写す量の誤差を写像の勾配で割り、 画面上のずれ (画素) で測る** — 写す量そのもの (角の rad) の閾値は、 写像の勾配が半径や深さで変わる所で意味を失う (勾配が縮む領域では、 行を 10 倍粗くしても rad の閾値は通り、 画素で測ると数十画素ずれていた。 実測)。 |Δψ| / |dψ/dχ| を 1 画素の角で割り、 行の間隔・角の格子はその値で決める。 同じ引き方を f64 でも回し、 f32 の丸めと格子の補間を分ける。
- <a id="reference-shares-builder"></a>**表を作った関数を照合の参照にもすると、 その関数自身の誤差は照合に出ない** — 表の行を足す・定義域を延ばす前に、 参照の関数を、 その関数を使わない独立な経路 (保存量の閉じた形と求積など) と、 延ばす先の範囲で照合する (実測: 表も probe の照合も同じ追跡器で、 その追跡器が延ばす先で黙って誤っていた)。
- <a id="self-consistent-ray-trap"></a>**f32 の誤差を shader 自身の光線の上で測ると、 自己整合して隠れる帯がある** — f32 で丸めた入力から作った光線の上で表と求積を照合すると、 入力の丸めで光線そのものがずれていても誤差 0 と出る。 上の停留する所や分岐の境界のような危ない帯は、 **画素の光線 (f64) か、 実装の関数を使わない独立の積分を基準に**門にする。 新しい門は、 直す前の実装で赤くなることを同じ検査の中で固定する (実測)。

## <a id="classified-table-interpolation"></a>離散分類を持つ表は、分類と連続量の補間を分ける

周囲の格子点の分類が異なるとき、分類と連続量をまとめて最寄り点へ切り替える処理は、入力が連続に動いても格子の中点で有限の跳びを作る。分類を入力から直接判定できる場合は、その判定を格子点の選択と切り離し、連続量は同じ分類のサンプルで補間する。分類間で色を混ぜた結果には、分類境界の位置と各領域内の補間値の誤差が混ざる。分類の判定と連続量を別々に probe して照合する。

行ごとに分類の領域が連続であることを使って端を探索する方式では、領域に穴がないことと、必要な値が有限であることを export 時に検査する。片方の行に必要な領域が存在しない場合の重みと、サンプルの端の扱いを f64 の参照に明記する。境界の連続性と、境界に近い連続量そのものの精度は別々に測る。

## <a id="intended-and-uploaded-input"></a>指定した入力と、GPU に送った f32 の入力を分けて照合する

極小の領域を拡大すると、入力を f32 に丸めただけで境界が画素を横切ることがある。独立な f64 の参照は、指定した入力と、実際に送った f32 の値を f64 に戻した入力の両方で評価する。前者との差は利用者が指定した条件に対する全体の誤差、後者との差は同じ入力に対する shader の誤差として分けて記録する。後者だけの一致で、入力の丸めを含む精度を保証したことにしない。

## <a id="probe-channel"></a>色でなく計算値を画素に書く probe channel

shader の実出力を f64 と照合するには、 検証用の uniform で**色の代わりに計算値を書き出す**:

- 値を 24 bit の固定小数に直して RGB に分けて書く (`floor(v · 2²⁴)` を 65536 / 256 / 1 に分解、 `v ∈ [0,1)` になるよう offset と scale)。 欠損 (影など) は 0 を sentinel にする。 精度は scale / 2²⁴。
- 読み戻しは `preserveDrawingBuffer: true` + `readPixels(RGBA, UNSIGNED_BYTE)`。 dithering を切る (`gl.disable(gl.DITHER)`)。
- 画素の方向は返さず、 **camera 基底・画角・canvas 寸法を返して、 f64 側で画素中心の方向を shader と同じ式で組み直す** (戻り値を小さく保つ)。 f64 側で観測者の boost 等も独立に再計算し、 参照実装の写像と比べる。
- 検証用の描画は**時間を進めない** (1 回描く hook は dynamics の積分を呼ばない) = 照合中に状態がずれない。 描画 loop が止まっていても (pane が隠れている等) 同期的に描いて読める。
- 大きな戻り値を file に落とすときは書き写さない → [`preview.md#tool-result-to-file`](preview.md#tool-result-to-file) (大きいと分かっている値は localhost の受け口へ POST、 返してしまった値は transcript から取り出す)。
- **色や画面上の目印で照合しない**: 目印の色を画面で探す照合は、 無関係な描画の変更 (天球の座標の付け替えなど) で目印が別の場所に移ると、 失敗せずに別のものを測りはじめる (実測: 目印の重力レンズ像を測るはずの照合が、 座標の付け替え後は影の縁の 1 画素を返し続けていた)。 照合は計算値を書いた probe で行う (例: 中央行の計算値が π を横切る位置を画素の間で補間すれば、 目印なしでリングの位置が取れる)。
- <a id="reference-from-captured-input"></a>**色の変換 (tone map・色の shift など) を照合するときは、 変換の入力の絵と、 変換が使う計算値 (画素ごとの倍率など) を probe で撮り、 f64 の参照は撮った 8 bit の入力から作る。 差は 2 つの集合に分けて読む** — 撮った入力は shader が変換に渡す丸める前の値と最大 0.5 段違う。 そのため (a) 入力の値で式を選ぶ変換 (例 = 2 つの channel の大小で枝を選ぶ) は境の近くで shader と参照が別の枝を取り、 (b) 傾きの大きい変換 (例 = 暗い画素に大きな倍率を掛ける) は 0.5 段の違いを傾きの倍に広げる。 境の近くの画素を数えて別にし、 合否はそれ以外の画素の最大差と、 全体の平均・99.9% 点で決める。 大きな差の画素は、 参照の入力を ±0.5 段動かした出力の幅に shader の値が入るかで確かめる (入れば参照の丸めで、 shader の誤りではない)。 撮る前に、 別の経路で上から塗る物 (重ねて描く sprite・既定で出ている他の物体の像など) を消す = 変換を受けない画素が混ざると、 最大差がその画素で決まる (実測)。

## <a id="seam-pixel-diff"></a>継ぎ目の連続性を実画面で測る

分岐の継ぎ目 (table 端など) の前後で、 観測者を微小に動かした 2 枚の画素差を取るだけでは判定できない (grid 線などの縁の画素が入れ替わる基準の差がある)。 **継ぎ目をまたぐ差を、 またがない同じ幅の差と比べる**。 特定の物体だけを見たいときは「その物体を描いた画像 − 描かない画像」 が 0 でない画素で mask してから比べる。

## <a id="frame-time-budget"></a>実時間 simulation の 1 frame の時間予算

描画が止まった後に一気に進んで「ワープ」 しないよう、 経過時間は捨てずに借り (time debt) として繰り越し、 1 frame に返す量に上限を置く。 このとき上限を**定数にすると、 時間の倍率を上げても simulation が上限で頭打ちになり**、 借りも際限なく溜まる。 上限は「倍率 × min(その frame の実時間, 上限時間) × 1.5 程度」 にする (通常の frame rate では追いつき、 停止直後の 1 frame だけ上限時間で抑えられる)。

<a id="time-rate-real-time-multiplier"></a>**時間の倍率は「実時間の何倍か」 で 1 つだけ持ち、 既定は 1 にする** (実測):

- 物理の時間の単位が質量などの parameter で決まる simulation では、 倍率を「その parameter の実時間の何倍か」 で持ち、 表示にもそう書く (例 = 「×1 (この質量の実時間、 1 単位 = 42 s)」 / 「×100 (… の 100 倍速)」)。 単位あたりの固定の速さ (例 = 「2 単位 / 秒」) を既定にすると、 その速さが実時間の何十倍かが画面から読めず、 user は「一瞬で終わる」 を物理だと受け取る (実測: 既定が実時間の 85 倍速で、 物理の過程が 0.3 秒で終わって見えた)。
- 倍率を状況で自動に変えない (例 = ある境界を越えたら実時間に、 戻ったら元の倍率に)。 変えるのは user の操作だけにする (実測: 自動の切替は何が起きているか分かりにくく、 元に戻した)。
- 経過時間はフレームごとに今の倍率で積む。 開始時刻からの差に倍率を掛ける形は、 途中で倍率が変わると位置が飛ぶ。
- <a id="input-control-overwritten"></a>**入力の control を表示にも使うなら、 どの状態でも入力を受ける**: 積分器が毎フレーム値を書き戻す slider を「その状態では表示だけ」 にすると、 触っても戻されて壊れているように見える (実測)。 入力を受けた瞬間にその状態の側の操作に読み替える (例 = 動いている最中ならその位置で状態を作り直す)。

## <a id="generated-asset-noise"></a>再生成した binary 資産の公開

f64 の table を再生成すると、 数値計算の非決定性で f32 の最下位桁だけ揺れることがある。 **公開用の copy の前に、 公開済みの版と数値で比べる**: 差が最下位桁だけなら公開済みの版を据え置き、 公開 repo に中身の同じ MB 単位の差分を積まない。 比べずに copy → commit しない。

## <a id="payload-cache-pairing"></a>table の大きさを書いた metadata と table 本体を別々に cache させない

table (texture の binary) と、 その大きさ・格子を書いた metadata (JSON) を別の file で配ると、 browser や CDN が片方だけ新しくした組を作る (静的 hosting は数分の cache を許す)。 古い table を新しい大きさで texture に送ると転送が黙って失敗し (WebGL は警告を console に出すだけ)、 その table を引く領域が全部欠損の値になる (実測: 内部視界が全部影になった)。

- metadata は毎回再検証して取る (`fetch(..., {cache: "no-cache"})`)。
- export の道具が table 本体の内容 hash を metadata に書き、 page は table を `<name>.bin?v=<hash>` で取る (中身が変わらない限り cache が効き、 変われば必ず取り直す)。
- 受け取った大きさを metadata の格子と照合し、 合わなければ「再読み込みしてください」 と出して止まる (黙って描かない)。

## <a id="reload-after-tables"></a>頁を開き直す検査は、 前の読み込みが table を取り終えてから開き直す

headless の検査が同じ頁を状態ごとに開き直すとき、 load の event の直後に開き直すと、 前の読み込みがまだ取っている table (数 MB の binary) の取得が打ち切られる。 頁の起動処理の catch がそれを error として console に書き (`TypeError: Failed to fetch`)、 console の error を数える検査は、 測った値が正しいのに落ちる (実測)。 手元の server では load の前に読み終わるので出ず、 公開 URL では毎回出る = release の後に初めて見える。

- 開き直す前に、 頁が table を受け取った印 (起動処理の最後で立てる global など) を待つ。 metadata を読むためだけの最初の読み込みも同じ。
- 待つ形にすると、 本当の取得の失敗 (印が立たない) はその読み込みの時間切れとして止まり、 打ち切りと分かれる。
- 打ち切りかどうかの確かめ = 回線を絞って開き直す (CDP の network の条件) と同じ error が出て、 印を待ってから開き直すと 0 件になる。 再現の側も、 落ちた検査と同じ口 (page error と console の両方) で error を拾う ([`debugging-discipline.md#reproduce-through-same-channel`](debugging-discipline.md#reproduce-through-same-channel))。

## <a id="derivatives-in-divergent-flow"></a>画面微分 (dFdx / mip) は分岐した return の後で取らない

写真の背景 (正距円筒図法の全天画像など) を光線の行き先で引くとき、 縮小で砂嵐にならないよう mip level を選ぶ。 ここで:

- **画面微分は一様な制御の中で取る**: GLSL ES 3.00 では、 分岐した `return` (影・円盤に当たった画素の早期 return) の後の `dFdx` / 暗黙微分の texture 参照は未定義。 全画素で背景の方向を計算してから、 最後に影・物体・背景を選ぶ形に組む (物体の色は変数に入れて `break`)。 欠損の画素では方向に既定値を入れる (隣の画素の footprint が大きくなるだけ)。
- **mip level は方向ベクトルの微分から明示する**: 経度の uv は 180° の継ぎ目で跳ぶので、 その微分を使うと継ぎ目に線が出る。 単位方向ベクトル `s` の画面微分は連続なので、 `foot = max(|dFdx(s)|, |dFdy(s)|)`、 `lod = log2(foot · W / 2π)` (W = 画像の横の画素数) を `textureLod` に渡す。 光子リングのように 1 画素が空の広い範囲を掃く所では lod が上がり、 平均の色に寄る (= 正しい平均化)。 極付近の横方向の過小な平均化は残る。
- 組み替えの前後で、 背景以外の画面が変わっていないことを画素で比べる (浮動小数の丸めで縁の画素が数個入れ替わる程度のはず)。

## <a id="engine-handoff"></a>2 つの lookup engine の切替は frame と精度で決める

同じ写像を 2 つの table (例: 外側の静止 frame の table と、 地平面をまたぐ落下 frame の table) で持つとき:

- **各 engine が前提にする観測者の frame を切替の条件に入れる**: 片方が特定の frame (自由落下) しか持たないなら、 別の frame (静止) の観測者をそちらに回さない。 半径だけで切り替えると、 その frame を持たない engine が別の観測者の視界を描く (実測: 静止カメラが切替半径の内側で落下の視界になり、 半径をまたぐと画面全体が影と空で入れ替わった)。
- <a id="slider-keeps-observer"></a>**位置を動かす control (半径のスライダなど) は観測者を替えない**: その観測者が存在しない所 (例 = 静止観測者は地平面の内側に居られない) まで control が動かすと、 境界で別の観測者に黙って替わり、 両者の相対速度の分の収差で画面が跳ぶ (実測: 地平面で相対速度が光速に届き、 画面の大半が入れ替わった)。 観測者を明示の状態にし、 control はその観測者のまま動かし、 存在しない所の手前で止めて「切り替える」 操作を出す。 確かめ = control の値を書いて入力の event を発火する headless の sweep で、 隣り合う歩の画素の差を周りの歩の中央値と比べる ([#seam-pixel-diff](#seam-pixel-diff))。
- **切替の位置は、 両 engine を参照実装と比べた精度で決める**: 定義域が重なる範囲で両方を f64 と比べ、 精度の高い方を使える所まで使う (実測: 外側の table は下端の近くまで 2 桁以上正確だった)。 その値を選んだ理由を記録する (理由の無い閾値は、 後から動かせるかを誰も判断できない)。
- 切替の前後で probe を取り、 視野の向きごとに (正面・横・後ろ) f64 との差を並べる。 一方の向きだけでは段差を見落とす。
- <a id="frame-convention-rotation"></a>**基準の観測者を切替で取り替えるなら、 camera の軸を回して継ぐ**: 外側では静止観測者、 内側では自由落下観測者を基準にする、 のように engine ごとに基準の観測者が違うとき、 同じ 4 元速度の camera でも「基準の triad を camera の速度で純粋に boost した軸」 は 2 つの基準で一致しない (2 つの boost の合成は回転を含む = Wigner 回転)。 切替の瞬間に、 保存している camera の軸を回転行列 R_ji = η(e'_j, e_i) で一度だけ回す。 回さないとその角度だけ画面が跳ぶ (実測: 横向きの速度を持つ camera で約 8°)。 速度が径方向だけなら回転は単位行列。 回転は両方の基準が存在する側 (例 = 静止観測者がまだ在る外側) で計算する。
- 回した軸は、 その後の kick が読むようにする: コマの頭で受け取った軸を step の loop に持ち回すと、 切替の step の後半と同じコマの残りの kick が、 回す前の軸で推す (実測)。 kick のたびに軸を読む。
- 基準を取り替えるときは、 camera の保存量 (エネルギー・角運動量) を引き継ぐ。 切替で既定の観測者 (例 = 無限遠から静かに落ちる観測者) に乗り換えると、 速度の段差が画面の跳びとして見える (実測)。 新しい基準に対する速度は、 保存量から閉じた形で出るなら、 境界 (例 = 地平面) で正則な形に直してから使う。

## <a id="input-starts-from-shown-state"></a>操作で始める状態は、 画面に出ている観測者から作る

画面にどの観測者の視界を出すかを表示の設定 (例 = 「自由落下の視界」 の切替) で選べるのに、 操作 (推進のキー) で始める積分の状態を既定の観測者 (例 = 静止) から作ると、 押した瞬間の 1 コマで速度が置き換わり、 収差の分だけ画面が跳ぶ。 視野角は変わらないのに「視野角が切り替わった」 と見える (実測)。 上の節の「基準を取り替えるときは保存量を引き継ぐ」 と同じ形の、 操作を始める側。

- 状態は画面に出ている観測者の 4 元速度から作る。 どの観測者を出しているかは、 描画の関数が使う判定と同じ判定で決める (2 か所に別の判定を書くと片方だけ直る)。
- 「その場で止まる」 のように、 速度を置き換えること自体が命令の中身なら跳ぶのが仕様。 どちらの命令かを記録に書き分ける。
- 跳びの有無の確かめ = 操作の直前のコマと直後のコマを headless の browser で取り、 **基準の取り方に依らない量** (2 つの 4 元速度の相対速度・影の角・画素の差) で比べ、 キーを押さない 1 コマの差を並べて noise にする。 shader に渡す速度は engine ごとに基準の観測者が違うので、 engine の切替をまたいで差を取ると同じ観測者でも偽の跳びが出る (実測)。 落下の途中のように動いている状態はキーを押さない間も 1 コマで 4 元速度が変わるので、 閾値は noise の数倍にする。

## <a id="held-input-checks"></a>押したまま・離した後の操作を headless で確かめる

1 コマごとに積分を進める viewer では、 キーを押していた区間と状態を読んだ時刻が合っていないと、 推力の検査も「離したら変わらない」 の検査も偽に倒れる (実測)。

- **キーは 2 コマ以上押す**: コマとコマの間で押して離したキーは積分に届かない。 遅い runner (software の GL) は 1 コマが長いので、 時間で「100 ms 押す」 と 1 コマも挟まらないことがある = 押す間は rAF を 2 回待って決める。 browser の自動操作の key 入力 (押してすぐ離す) も届かないことがある = 押し続ける検査は page に `keydown` / `keyup` の event を送る (実測)。
- **event と読みを page の 1 回の呼び出しにまとめる**: 送る呼び出しと読む呼び出しを分けると、 間にコマが回って区間がずれる。 1 回の呼び出しの中で event を送って状態を返し、 積分器が進めた固有時間も状態に出す。 区間がその固有時間で決まるので、 f64 の ODE を同じ固有時間だけ積んで比べられる (壁時計とコマの予算から推すと、 予算の打ち切りで合わない)。
- **向きは、 検査の間に境界を越えない方に取る**: どこまで進むかはコマの予算で回ごとに変わる (実測: 同じ操作で、 地平面を越えて飛行が終わる回と越えない回が出た)。 外側だけの参照と比べる検査は、 境界から離れる向きに押す。
- **同じ状態かは成分の等号で見る**: 2 つの 4 元速度の内積から γ を作り β = √(1 − 1/γ²) とすると、 同じ状態どうしでも √(2ε) ≈ 2e-8 になる (丸めの下限)。 「操作で速度が変わらない」 はエネルギー・角運動量などの成分の等号で見る。 相対速度の閾値で見るなら 1e-6 以上にする。
- **離した後に保存量が変わらないことは等号で確かめられる作りにする**: 推力の無い step で保存量を速度から作り直さない (kick を飛ばす) と、 惰性の間の保存量は厳密に同じ値になる。 作り直すと丸めが積もり、 「変わらない」 を閾値で見るしかなくなる。

## <a id="thrust-in-pilot-frame"></a>推力を camera の軸で与えるなら、 操縦者の系の固有加速度として boost する

camera の軸が基準の観測者の triad を camera の速度で純粋に boost したもの (上の [#frame-convention-rotation](#frame-convention-rotation)) なら、 軸の上の推力の成分は操縦者の静止系の成分。 操縦者の系で一定の固有加速度 α は、 基準系の固有速度 u = γβ に du/dτ = α + (α·u) u/(γ+1) で足す (boost した 4 元加速度の空間部分。 時間部分 α·u は、 u から γ を作り直す更新が足す)。

- du/dτ = α をそのまま足すと、 進行方向に操縦者が感じる加速度は α/γ で、 γ が大きいほど効かない (β = 0.9 で 0.44)。 保存量の率もこの分ずれる (実測: エネルギーの率が教科書の式の 1/γ になっていた)。
- この率は速度に依るので、 Euler の kick は γ の大きい所で足りなくなる。 中点 (k/2 進めた u で率を評価) にする (実測: γ = 30 まで、 Euler の半 kick で 1.7 % 不足、 中点で 5e-5)。
- 減衰の無い推力では γ が cosh(ατ) で育ち、 shader の f32 の収差の誤差は γ² で増える。 表示の精度で決めた上限で「γ を上げる成分」 だけを切り (速度の向きの成分を落とす)、 さらに kick が |u| を上限より大きくしないように止める。 向きを変える推力と減速は残す。 前者だけだと、 上限を跨ぐ 1 回の kick が k γ α ほど行き過ぎる (実測)。
- 「離すと止まる」 のような操作感のための保持と減衰は、 物理の推力と分けて、 それを持つ観測者 (例 = 静止の観測者) にだけ付ける。 速度に依る保持を対称の半 kick で足すと、 step の大きさに比例する偏りで定常の流れが残る (実測: h² でなく h に比例)。 止まったとみなす閾値は、 実際の step の大きさで届くかを確かめて決める。

## <a id="paused-state-one-event"></a>止めた状態は 1 つの事象の写真にする (時計を全部止める)

実時間の viewer で観測者の位置を止めて見せるなら、 その状態が読む時計 (他の物体の時刻・光の遅れ・残り時間の表示) も全部止める。 位置だけを止めて時計を進めると、 画面の観測者はどの世界線にも乗らない = 位置は静止の観測者、 4 元速度と時計は動く観測者のもの、 という混ぜ物になる (実測: 落下の観測者を止めた状態で、 位置と残り時間の表示は止まり、 他の物体の時計だけが落下者の進み方で進んでいた)。

- 静的な時空では、 空や円盤のような定常の背景は位置と向きだけで決まる。 だから動く観測者を止めた絵は、 その位置を通る観測者が撮る 1 枚の写真として正しい。 嘘になるのは、 それを時間が進む状態として見せるところ (残り時間が減らない・他の物体だけが動く)。
- 確かめ = 時間の倍率を上げて止めた状態で数秒置き、 位置・残り時間・時計を読んで、 どれか 1 つだけが動いていないかを見る。 1 コマの壁時計を打ち切る loop では、 遅い runner (software の GL) で時計の進みが倍率より小さく出るので、 比べるのは「動くか動かないか」 にする。
- 位置を動かす操作 (slider) で観測者を置き直すとき、 時計を保つか (同じ種類の別の観測者に乗り換える)、 同じ世界線の上の別の事象に移すか (時計も動く) は、 定常の背景の絵には効かず、 時計を読む物 (他の物体) の動きにだけ効く。 どちらにしたかを記録に書く。
- **止める状態は観測者に依らない 1 つの変数にする**。 止める操作を特定の観測者 (例 = 落下) にだけ持たせると、 止まる観測者と止まらない観測者が分かれ、 止めたまま観測者を替えると時間がまた動く (実測)。 描画の loop は、 その変数が立っている間はどの観測者の積分も時計も進めない。
- **動かし直した最初のコマで、 止めていた時間を取り戻さない**: 各時計が持つ「前のコマの時刻」 を、 止めている間も毎コマ今に置き直す (積分の借りの持ち越しも 0 にする)。 置き直さないと、 動かした瞬間に止めていた壁時計の分を 1 コマで進め、 跳んで見える。 確かめ = 止めて 1 秒置き、 動かした最初のコマの固有時間の進みが 1 コマ分 (止めていた分の数 %) か。
- **閉じた形で進む運動 (例 = 放射の自由落下) は、 毎コマ今の状態から閉じた形で 1 コマ分進める**。 起点 (位置・時計・経過時間) を持ち回して「起点から閉じた形」 で位置を出すと、 位置を書き換える経路 (slider・検査用の API・観測者の切り替え) のたびに起点を置き直す必要があり、 置き忘れた経路で古い起点が位置を書き戻す。 今の状態から進める形なら、 どこで書き換えてもそこから同じ種類の観測者として続く。 閉じた形の合成なので、 増えるのは丸めだけ (実測: 1 秒の落下で起点からの閉じた形と相対 3e-16)。
- **積分が毎コマ slider に位置を書き戻す viewer では、 pointer で slider を掴んでいる間は時間を進めない** (動画の scrub と同じ)。 進めると、 指を止めている間に積分が thumb を動かし、 次の入力で指の位置に戻る。 pointer の up・cancel と window の blur で解く (window の外で離されると up が届かず、 時間が止まったままになる)。 keyboard の矢印は 1 回ずつの入力なので止めない。 検査で slider の値を書いて `input` を送るときは pointer が無いので、 時間を止めた状態で測るか、 先に `pointerdown` を送って掴んだ状態で測る。

## <a id="readout-observer-own"></a>計器の量は、 その観測者の世界線の量にする

計器 (HUD) に残り時間・速さのような量を出すなら、 画面に出ている観測者自身の量だけを出す。 「もし〜なら」 の仮定の量を出すときは、 その観測者が今の状態から仮定どおりに進んだときの値を計算し、 札の名で仮定を言う。 別の観測者の閉じた形をそのまま使わない (実測: 止まっている観測者に「落ちれば地平面まで」 として無限遠から落ちる観測者の時間を出していて、 地平面の近くで桁違いに短かった。 手を離した落下 = 静止からの放射の測地線の時間が正しい)。

- 仮定の量が定義できない観測者 (落ちない円軌道、 今の速度では折り返して届かない飛行、 離すと止まる操作の途中) には札を出さない。 出せるかを決める式 (例 = 惰性の測地線の動径の式の根が途中にあるか) を、 値と同じ関数に置く。
- 常に同じ値の札 (止まっている観測者の、 その観測者の系に対する速さ 0) は出さない。
- 確かめ = 計器の値を、 ページの式と別の道 (同じ初期値の ODE を f64 で積分) で求めた値と、 計器の表示の桁で比べる。 閉じた形を 2 回書いて比べても、 同じ誤りは見えない。

## <a id="gpu-time-from-readpixels"></a>描画 loop が止まっている pane で 1 frame の GPU 時間を測る

pane が隠れていると rAF が間引かれることがあり (止まらない場合もある = 先に rAF の回数を測る)、 そのとき HUD の fps は GPU の重さを表さない ([`preview.md#browser-pane-visibility`](preview.md#browser-pane-visibility))。 同期描画の hook を N 回呼び、 毎回 1 画素の `readPixels` で完了を待たせた時間を N で割る。 機能の有無 (背景画像あり / なし等) の差はこの値で比べる。
