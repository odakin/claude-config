# 研究メール規約

研究共同研究のメール通信を管理するリポで適用。CLAUDE.md から参照: `~/Claude/claude-config/conventions/research-email.md`

## <a id="mail-classification"></a>メール分類

受信メールを以下の基準で分類する:

| 分類 | 条件 | 処理先 |
|------|------|--------|
| 研究メール | 送信者が `research-collab/collaborators.yaml` に登録 **または** 件名が既知プロジェクトに関連 | `research-collab/threads/{project}.yaml` |
| 事務メール | 大学事務・委員会・人事・学生対応 | `email-office/TODO.yaml` |
| その他 | 上記以外 | 通常対応（必要に応じて分類） |

## <a id="thread-recording-rules"></a>スレッド記録ルール

### 記録するもの
- 共同研究者との往復メール
- 論文投稿・レフェリーレポート関連
- 学会招待・講演依頼（研究関連）
- 研究に関する議論・質問

### 記録しないもの
- 一方的な通知メール（ML配信、学会ニュース等）
- スパム・広告

### スレッド記録の書式

```yaml
- thread_id: "Gmail thread ID"    # gmail_read_thread で再取得可能
  subject: "件名"
  participants: [collaborator_id]  # collaborators.yaml の id
  account: lab | cis | personal   # どの Gmail アカウントか
  started: YYYY-MM-DD
  last_message: YYYY-MM-DD
  status: active | waiting | resolved
  summary: |
    スレッドの要約（数行）
  action_items:
    - description: "アクション内容"
      assignee: odakin | collaborator_id
      status: pending | done | waiting
      due: YYYY-MM-DD | null
      completed: YYYY-MM-DD | null
```

### status の使い分け
- **active**: やり取りが進行中
- **waiting**: 相手の返信待ち
- **resolved**: 議論終了、アクション完了

### <a id="recording-attribution"></a>記録時の帰属 (= 誰が言った・誰が決めたか)

`summary` / `action_items` に「誰が言った・誰が決めた」を書く瞬間は誤帰属の主現場。**carrier proxy (= 送信者・転送者・議事の書き手) を発言者・意思決定者と等値しない** — 送信者 ≠ 意思決定者 (= 秘書送信 / 代理送信 / 合議の結果を 1 人が送る)、転送・要約 mail 経由の発言は原発言者が曖昧なら「〜の記録によると (発言者未確認)」と hedge して記録する。帰属 5 規律の正本 = [`actor-attribution.md`](actor-attribution.md)。なお §アウトリーチ前の身元確認は「これから接触する相手は誰か」の裏取りで、こちらは「この記録は誰の行為・発言か」— 別 kernel。

## <a id="session-start-procedure"></a>セッション開始時の手順

プロジェクトリポで作業開始する際:
1. `research-collab/threads/{project}.yaml` を読む
2. status が active/waiting のスレッドを報告
3. 未完了の action_items を報告
4. Gmail MCP で新着メールをチェック（共同研究者からのもの）

## <a id="post-send-recording"></a>メール送信後の記録

Claude がメールを送信（またはドラフト作成）した場合、**同じセッション内で即時に**以下を実行:
1. 該当スレッドの `last_message` を更新
2. `summary` に送信内容の要約を追記
3. 関連する action_items の status を更新

「次のセッションでやる」は禁止。送信と記録は原子的操作。

## <a id="researcher-contact-lookup"></a>研究者連絡先 (email) の取得手順

新規研究者にコンタクトする際、メールアドレスが手元になければ以下の優先順位で探す:

1. **collaborators.yaml / 既存リポの `researchers.yaml` 等の手元 DB** — 過去に登録があれば最速
2. **論文 PDF の 1 ページ目 (arXiv 等)** ← **推奨**。著者所属の脚注として email が記載されている case が多く、確実に取得できる
   - `WebFetch` で `https://arxiv.org/pdf/<arxiv-id>` を取って著者 email を抽出
   - 学会誌掲載済の論文も最初の正式版 PDF に email がある
3. **所属機関の公式メンバーページ** — 例: 大学研究室の member 一覧。**ただし mask されていることが多い** (`****@univ.example` 等)
4. **OpenReview / Semantic Scholar / Google Scholar の著者プロフィール** — mask されていることが多く、確実に取得できないことが多い
5. **共著者・知人経由の問い合わせ** — 上記で見つからない場合の最後の手段

### 失敗例 (反パターン)

メンバーページの mask された表示を見て「公開で取得できない」と user に尋ねたが、論文 PDF を直接見ればすぐ取れた case があった。**arXiv 論文がある相手なら、まず PDF を見る**。

一般則 = [`docs/convention-design-principles.md#retrieval-key-choice`](../docs/convention-design-principles.md#retrieval-key-choice) (= retrieval の null は「対象が無い」でなく「key / source が悪い」を先に疑う)。 **過去の投稿・査読記録をメールから掘り起こす場合は、誌名や送信者でなく発行体の案件 ID (= 原稿番号 `XXNNNNN` / 投稿番号) を第一の検索 key にする** — 転送されると From は同僚に変わり、件名に誌名が一度も出ないことがあり、報告が本文のみで添付が無いこともあるが、ID は件名と本文の両方に literal で残る。

### 注意

- メールアドレスは PII。**取得経路 (= どこで見つけたか) を log に残す** (= researchers.yaml の notes に source を書く) と、後日「このアドレスは公開情報か?」を判定できる
- 公開ページに載っていない address を間接ルート (= 紹介・名刺) で取得した場合は、そのことも notes に記録 (= 受信者から「どこで知ったか」と聞かれた場合の説明責任)

## <a id="pre-outreach-identity-check"></a>アウトリーチ前の身元確認 (= 誰に書いているか裏取りする)

上の手順で email が取れても、**「その人が論文 X の著者本人か」は別問題**。相手を「論文 X の著者」「定理 Y を打ち立てた本人」と **事実として断定して外部メールを送る前に**、以下を守る。一般原則は [`docs/convention-design-principles.md#single-field-identity-corroboration`](../docs/convention-design-principles.md#single-field-identity-corroboration) (= 単一 field の一致で同定して action を取るな) の outreach 適用。

- **積極的な裏取りを要求する (corroboration)**: 名前一致以外の **積極的リンク**で人物↔業績を結ぶ — ① 引用論文 PDF / 本人ページに載る email、② 著者レコード (INSPIRE 等) に **当該論文が含まれる**、③ 本人 CV。「機関に同姓の人がいる」は **反証が無いだけ**で裏取りではない (= 見つけやすさ ≠ 同一人物)。**古い論文 (preprint 普及前) 等で本人を積極特定できなければ、身元は断定しない。**
- **身元の確定根拠を別欄に記録する (provenance)**: 「email をどこで得たか」とは **別に**「**身元をどう確定したか**」を書く。強い例 = `論文 PDF の corresponding author`、弱い例 = `同姓・近年の著者レコードは別人 = 未検証`。レビューで「未検証」が一目で分かるようにする。
- **曖昧さを検知したら解決するか送らない (override 禁止)**: 「同名別人がいる」等の同定ハザードに気づいたら、**積極的に解決するまで確信ある身元主張つきで送らない**。解決できなければ **送らない / 身元の主張を一切外した内容にする**。⚠️ 「裏取りできないが柔らかい言い方にして送る」は **不可** — 未検証の信念のまま送れば、文面を和らげても誤った相手への誤接触は残る (= 害は文法でなく誤接触)。

⚠️ いずれも意味判断で、機械では検出できない ([`docs/convention-design-principles.md#downstream-net-intake-leverage`](../docs/convention-design-principles.md#downstream-net-intake-leverage) = leverage は上流の judgment)。最後の砦は人間のレビューなので、確定根拠の可視化 (上記) で人が「本人か」軸で見られるようにすることが要。

**反パターン (実例から)**: 古い論文の引用元著者を、姓の一致だけで現役の同姓研究者と同定し「あなたが打ち立てた定理」と本文に断定して送信 → 別人で「人違いです」と返信。著者レコードで「近年の論文は同名別人」と気づいていたのに「では現役でない方が本人だろう」と消去法で当て推量したのが直接因。同じ送信群でも、正しい人物が現役で arXiv・所属メールを辿れた相手は同名別人問題を正しく解決できていた = 差は「正しい人物を積極的に裏取りできたか否か」。

## <a id="pre-send-cosigner-confirmation"></a>共著メール送信前の共著者 draft 確認

共同署名で外部 (= 学外 / 学内事務 / 上長 等、 信頼関係に影響しうる相手) に送るメールは、 **送信前に共著者の draft 確認を informal channel** (= chat / DM / informal mail) で取る。 各々の name が footer に並ぶ「同意の上 send された」 体裁になるため、 sender が単独で送ると共著者が「勝手に署名された」 不快感や、 立場の不一致を public surface に焼き付けるリスクがある。 §「アウトリーチ前の身元確認」 (= 受信側の身元裏取り) と sibling = sender-side responsibility (= 自分の署名)。

確認手順:

1. draft (= 送信予定の本文 + To/Cc/件名) を informal channel に提示
2. 共著者の "OK" or 修正指示を待つ
3. 修正があれば反映 → 再 OK
4. send 後、 informal channel で「送信完了 + messageId」 を共有 (= 後で「あの mail どうなった?」 と聞かれる reflex も防ぐ)

省略可なケース:

- 毎日対面で discuss していて互いの意思が共有されている同僚との low-stakes mail
- 共著者が事前に「一任する」 と明示 (= 委任の record が available なら)
- 共著者の input が完全に反映済 (= 共著者自身がほぼ書いた、 sender が typo 直しのみ)

省略不可なケース:

- 公式組織 (= 学部長 / 事務局 / 出版社 / referee) 宛
- 議題提案・抗議・苦情等 reaction risk のある内容
- 共著者の立場・専門領域への言及がある (= 共著者の name で誤った主張を出さない)

⚠️ DM 確認は記録に残る形 (= scrollback できる channel) で行う。 口頭・電話のみだと後で「合意していない」 と紛糾しうる。 また確認 turnaround が長い場合は send-side responsibility の judgment (= 「expected delay」 vs 「重要なので待つ」) を sender が引き受ける。

origin: 2026-06-29 学内事務向け詫び返信の作成 session。 共同署名 mail について、 (1) 初稿 → 共著者 DM 確認、 (2) 共著者新提案 (= 「次回会議の議題に取上げ依頼」 追加) を反映した修正稿 → 再 DM 確認、 (3) GO 受領 → send + 送信完了 DM 通知、 という 3 段の loop で運用した実例。 sender 単独 send だった場合、 共著者の追加提案が捨象されかつ署名のみ共同で出てしまう risk があった。

## <a id="version-arrives-off-thread"></a>相手の最新版は自分宛のスレッドに来るとは限らない

共同執筆で改訂版をやりとりしていると、 「最新版 = 自分と相手の 1 対 1 スレッドの末尾」 と
思い込みやすい。 実際には相手が**別のスレッド (会議の案内、 関係者一斉配信、 別件の返信)
に添付して**出すことがあり、 その版は 1 対 1 スレッドには現れない。

- 最新版を取りに行くときは **thread でなく `from:<相手>` で期間検索**する
- 版の台帳 (= どの版をいつ・どの経路で受け取ったか) を持ち、 取り込み済みの版を記録する
- 検出器・surface 機構を thread 単位で組んでいる場合、 この経路は**構造的に射程外**になる
  ことがある。 気付いた時点でその旨を記録に残す (= 次に同じ死角を踏まない)
- 返信の宛先は**内容で決める**。 会議スレッドに届いたからといって、 原稿の細かい指摘を
  その全員に返すのは筋が違う

### <a id="reply-thread-follows-counterpart"></a>返信を「どのスレッドに置くか」も相手の運用に合わせる

上の鏡像。 **相手が毎回新規スレッドで送ってくるなら、 こちらの返信も新規で立てる。**

- 1 対 1 の古いスレッドへ `In-Reply-To` で返すと、 相手の一覧では**そのスレッドの最初の件名**で
  表示される。 こちらが件名に足した要約は開くまで見えない。 相手がそのスレッドの**送信者**なら、
  なおさら「自分が出した古いメール」 に見えて素通りされる。
- 相手の運用は**過去の往復で判定できる**: 前回の返信がスレッド内か新規か。 3 回とも新規なら
  スレッド内返信は届かないものと考える。
- 「1 対 1 スレッドに返すのが筋」 は**こちらの整理都合**であって、 相手に届く保証ではない。
  内容が新しい論点なら、 新規 + 内容が分かる件名の方が強い。
- ⚠️ 「届いていない」 と言われたら、 まず**送信側の機械事実**を確認する (= 送信済ラベル /
  宛先が相手の送信元と一致するか / bounce の有無 / Message-Id 発番)。 それが揃っていれば
  配送は成立しており、 原因は**可視性**の側にある。 そこから先 (相手の受信箱・迷惑メール・
  組織のフィルタ) は自分から見えないので、 再送の形を変えるのが唯一の手。

## <a id="shrink-the-ask"></a>共著者への確認依頼は、解けるところまで解いてから縮めて送る

**ルール:** 多忙な共著者に判断を仰ぐ前に、公開情報 (= 当人たちの原稿の式・投稿記録・過去の査読 report) から自力で決着できる部分をすべて潰し、**相手にしか決められない最小の問い**に縮めてから送る。

- 開いた問い (「これで正しいですか、どう思いますか」) を投げない。自力検証の結論 + 具体的な手当てを提示し、相手の action を「diff の承認」 「yes/no」 まで落とす。
- **相手の action を変えない情報は本文にも添付にも載せない** (= 検証の詳細は自 repo に記録し、聞かれたら出す)。判断材料と検証記録を混ぜると読まれない。
- 依頼文に確認項目を残す前に「これは本当に相手にしか決められないか」を 1 回問う。公開された式の数学的性質は自力検証で足りる (= 相手の記憶や実装を確認するまでもない) ことが多い。

**Why:** 2026-08 の共著論文再投稿の実例。当初 draft は開いた確認 2 問 + 検証 note 添付だったが、user の連続指摘 (「こっちで極限まで深く考えられない？相手は忙しそうだし」「これ言う意味ある？」) で自力決着 → 依頼は「diff 2 箇所の承認 → 投稿」 のみに縮み、相手の負担が数十分から数分になった。

**検証依頼の変種 (= AI 併用の大規模改訂を共著者に確認してもらうとき、2026-08 追記):** 縮めるのは「問い」だけでなく**「検証をお願いする範囲」**も同じ。改訂一式 (数十 edit + 構成変更 + 対外文面) を 1 通で「確認してください」と投げると、相手は「AI の作業をどこまで信じてどこから検証するか」という別問題を背負い、判断不能で止まる (実例: 返信 = 「ここまで内容に影響していると判断が難しい。修正の正誤を確認するだけでも膨大」)。正しい形は層別:

1. **AI の作業を 1 行も信用せずに確かめられる、結論を決める最小の主張** (= 出版済み・共有済みの版の数字だけから電卓で出るもの) を先頭に置き、これ**だけ**の検証を頼む。
2. 残り (個別修正の正誤・構成案・文面) は「保留にしてください、今は見なくてよい」と明示する。黙って添付すると相手は全部が確認対象だと解釈する。
3. 検証と読み物を区別して宣言する (「(a) は検算をお願いします、(b)(c) は読んでいただければ十分です」)。

関連: 断言 framing・査読実績の照合は [`rebuttal-letter.md #defensive-revision`](rebuttal-letter.md#defensive-revision)、検証 note の最小構成は [`physics-notes.md #verification-note-minimal`](physics-notes.md#verification-note-minimal)。

## <a id="apology-cause-attribution"></a>不手際の詫びメールは真因を正確に書く — AI/ツール起因の失敗を曖昧化・転嫁・user 帰責しない

自分側の不手際 (見落とし・期限徒過・提出漏れ 等) を詫びるメールで原因を記述するとき、**実際の失敗機構をそのまま書く**。とりわけ失敗の原因が AI アシスタントやメール仕分け等の自動化機構にあるとき、draft は系統的に記述を真因から遠ざける drift を起こす (2026-08-31 実測: 1 通の詫び draft で 4 連続の user 訂正が必要だった):

1. **曖昧化**: 「確認が遅れ」 — 機構の失敗を人の怠慢に見せ、かえって印象が悪い
2. **user への帰責**: 「当方の (設定の) 不備により」 — 設定を作った主体は AI 側なのに、user が雑な設定をしたかのような文になる
3. **外部サービスへの転嫁**: 「メールサービスの自動振り分けによって」 — 最終的に握り潰したのは自前の仕分け層なのに、プラットフォームのせいにする
4. 過剰な内部開示も不要: 対外的には「メール管理のフィルタが誤って通知対象外に分類していた」で十分 (AI と明示する必要はないが、帰責は正しく自動化機構に置く)

**How to apply**: 原因段 = 「メール管理のフィルタが◯◯を誤って通知対象外に分類していたため、気づくことができないまま〜」 + 再発防止 1 文 (「フィルタの誤分類は修正しました」)。結果への責任 (ご迷惑をおかけした) は本人として引き受けつつ、機構の記述は事実どおりに保つ。この 2 つは独立に成立する — 責任を引き受けることと原因をぼかすことを混同しない。

**Why**: 詫び文面はインシデントの対外的な一次記録になる。真因を曖昧化すると (a) 相手が誤った再発防止を期待する (b) 自分側の記録も汚染される (c) 「怠慢」 と読まれて信頼コストが上がる。draft を書く AI 自身の機構が原因である場合、記述が自分から遠ざかる方向に歪む圧が働くことを前提に、送信前に「この原因記述は機構の事実と一致しているか」を 1 問通す。

## <a id="gratitude-without-reproach"></a>指摘を断る返信の 3 則 — 感謝に相手の落ち度を埋め込まない / 第三者への escalation を予告しない / 結論の後にもう一度礼を置く

相手 (事務職員・共同運営者・共著者) の指摘や依頼に対して「結論は変えない」 と返すメール・チャットは、 内容が正しくても tone で関係を損ねやすい。 draft は次の 3 方向に系統的に滑る (2026-09-05 実測: 1 通の返信 draft で user 訂正 3 回):

1. **感謝に落ち度を埋め込む**: 「日程が決まった後にもかかわらずご確認いただき」 — 「にもかかわらず」 が相手の遅さを foreground し、 感謝の形をした嫌味になる。 感謝は**相手の行為そのもの** (「ご確認いただき」 「気にかけていただき」) に向け、 タイミング・経緯の修飾語を付けない。
2. **第三者への escalation を予告する**: 「念のため◯◯さんにも共有いたします」 — 相手の頭越しに上位部署へ持ち込む宣言に読める。 共有が必要なら黙って別便で行い、 相手への返信には書かない。
3. **礼が冒頭 1 回で終わる**: 結論 (「変更せず進めます」) で文が終わると、 断りが最後の印象になる。 **結論の後に短い礼を 1 文**置く (「お手間をおかけしますが、 引き続きよろしくお願いいたします。 いつもありがとうございます」)。 = 謝罪最小限 (層3 の apology-minimalism) とは逆向きで、 **礼は 2 箇所 (冒頭 + 末尾) が既定**。

**How to apply**: 結論を変えない返信を書いたら送信前に (a) 感謝文の修飾語を全部外して意味が変わらないか (b) 第三者の名前が「共有 / 確認 / 相談」 の動詞と一緒に出ていないか (c) 末尾の 1 文が礼か、 の 3 点を見る。 相手が事務職員・下位者でも同じ (= むしろ tone の非対称が効く)。

## <a id="publisher-solicitation-triage"></a>出版社発の就任・寄稿勧誘 (Guest Editor / Special Issue / mass 査読 invite) の triage 軸

有名出版社の実名 domain から届く勧誘は、 **送信元の正当性と依頼の学術的実体が独立** — 「本物の大手からだ」 は受諾理由にも精査省略の理由にもならない。 件名と送信者名だけで「mass だろう」 と捨てるのも逆向きの同じ誤り (= 判定は本文 1 読の上で)。 判定軸 4 つ:

1. **送信部門**: 署名の所属が editorial board / 学術編集者か、 commissioning・publishing-performance・growth 系部門か。 後者は出版数 KPI の営業であって学術的招聘ではない。
2. **分野一致**: 勧誘対象の誌・collection の scope が受信者の研究分野と一致するか。 分野違いへの Guest Editor 依頼 = 業績を読まない名簿ベースの spray 送信の確定 signal。
3. **誌の tier**: 大手出版社は高 tier 誌と大量創刊の低 tier OA series を同じ brand 下に併存させる — series 名で tier を判定し、 出版社名で判定しない。
4. **依頼の労働実体**: 「テーマ提案 + 著者集め + 宣伝 + 投稿管理」 を依頼側が丸ごと求める形は、 collection 増産のための無償労働の外注。 editorial 実績としての価値は tier に従う。

処置: 軸 2-4 が揃って negative なら**失効するものは無い** (応答期限・義務なし) — 無視でよいが、 判断理由つきの declared-skip を記録に残す (= 将来の同種勧誘の前例になる + 監査系 sweep への再出現を止める)。 既定 decline にしたい発信 platform は [`convention-design-principles.md §8.21`](../docs/convention-design-principles.md#noise-obligation-signal-sharing) の記録付き opt-out へ。 ⚠️ 逆に、 editorial office 発の**査読依頼**は義務 class (放置 = 事故) — 勧誘と依頼を送信 domain で混同しない (同 §8.21 の bucket 混在)。

origin: 2026-09-01、 大手出版社の commissioning 部門から分野違いの低 tier OA collection への Guest Editor 勧誘 (依頼 + 週次リマインド 3 通) を suppressed-mail 棚卸しで発掘した triage。 初回報告が件名のみの判定で user 押し返し後に本文精読した経緯ごと記録 (= 「本文 1 読」 規律の実例)。
