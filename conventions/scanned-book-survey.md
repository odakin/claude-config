# Scanned book survey — 書籍スキャンの棚卸し

## <a id="scope"></a>場面

他人から共有された書籍スキャン PDF の束 (参考書・関連書の自炊 PDF) を、 比較検討や資料整理のために
**書誌・刷り色・関連する箇所**で棚卸しするとき。 撮影写真の転記は別の doc
([photographed-document-transcription.md](photographed-document-transcription.md))、 表や多段組の文字抽出は
[office-automation.md#pdf-table-layout-aware-reading](office-automation.md#pdf-table-layout-aware-reading)。
共有 folder の監視と取り込みは [google-api-direct-access.md#shared-folder-watch](google-api-direct-access.md#shared-folder-watch)。
棚卸しした本を図書館の購入候補にするときの書誌・所蔵・価格の下調べは [book-purchase-lookup.md](book-purchase-lookup.md)。

## <a id="workflow"></a>手順

1. **題名で仮に区分する** (直接関係 / 隣接 / 無関係)。「仮」と明記して一覧表を正本ノートに作り、 commit する。
   無関係な本は取り込まない。 監視台帳の除外に**書名の一部**を足す (足さないと session 開始時の新着通知が残る)。
   除外の語は他の本の名前に部分一致しないか、 一覧を出し直して件数で確かめる。
2. **取り込む**。 1 冊数十 MB でも、 読み取りの待ち時間が短いと同じ file だけ続けて切れることがある (実測)。
   同じ file の失敗が続いたら道具の timeout を疑う。
3. **下見**: `scripts/scan-book-survey.py digest BOOK.pdf --kw 名前=正規表現` で、 ページ数・刷り色の見立て・奥付と目次の候補ページ・
   語の出現ページを 1 画面に出す。 本ごとに見る語は、 比較したい論点 (導入の仕方・扱う道具など) から決める。
4. **奥付は画像で読む**: `colophon BOOK.pdf <奥付のページ> --thumbs <色を見たいページ>` で奥付の書誌ブロックと縮小ページを 1 枚にする。
5. **要所を読む**: 目次とまえがきは `text --compact --max-chars N` で文字層を読み、 引用や主張の根拠にする箇所は `render` で画像にして読む。
6. **正本ノートに記録する** (下の [#record](#record))。 数冊ごとに commit・push する (長い棚卸しは文脈が圧縮されても成果が残るように)。
7. **隣接の本は短く**。 未決の論点に効く本だけ取り込んで目次を見る。 題名だけで除外した本は「題名で判断」 と書き、 判断を変える条件も書く。

## <a id="print-color"></a>刷り色の判定 — colorspace は刷り色ではない

- **全ページ DeviceGray のスキャン**は、 原本が単色刷りなのか、 スキャナの設定で色が落ちたのか区別できない。 「判定不能」 と書く。
  表紙だけがカラーで本文がグレーでも、 表紙を別に取り込んだ可能性があるので同じく判定不能。
- **自動カラー判別のスキャナ**はページごとに RGB / Gray / 1-bit を選ぶ。 RGB で取り込まれたページだけ、 縮小描画して**彩度の高い画素の割合**と**色相の分布**を測る。
- **色相は名前でなく円弧の幅で見る**: 1 色のインク (例: 青緑) は、 色の名前の境目で「青緑」 と「緑」 に割れて 2 色に見える。
  彩色画素の 9 割を含む最小の色相の円弧が狭ければ (目安 60 度以下) **二色刷りの候補**、 広ければ多色の候補。
- **1 色に絞ったフルカラー本は二色刷りと区別できない**。 彩色が 1 色相に集中していても、 別のページにまれに別の色が出ることがある。 最後は縮小画像で目視し、 出版社の表記があればそれを正とする。
- 判定を記録するときは「フルカラー / 二色刷り (黒 + ○系) と見える / 判定不能」 と、 見立ての根拠 (彩色ページ数・見たページ) を添える。

## <a id="ocr-text-layer"></a>文字層 (OCR) は案内板

- 語の出現ページを探す、 目次の構成をつかむ、 には十分使える。
- **崩れるもの**: 奥付の日付と刷数、 ISBN の数字、 人名 (異体字・旧字は別字になる)、 章番号 (「第2章」 が別の字になる)、 数式、 ルビ。 これらは画像で読む。
- **検索 0 件は不在の証明にならない**。 記録には「文字層で 0 件」 と書き、「扱っていない」 とは書かない。 確かめたいなら目次と該当章を画像で見る。
- plain な文字抽出は表・多段組の視覚順を保証しない ([office-automation.md#pdf-table-layout-aware-reading](office-automation.md#pdf-table-layout-aware-reading))。
- 日本語の正規表現で前後の文脈を切り出すとき、 Bash tool の grep (ugrep) は `.{0,N}` のような繰り返しで `exceeds complexity limits` になる。 python の `re` を使う。

## <a id="page-offset"></a>本のページと PDF のページ

- 記録と引用は**本のノンブル**で書く (他の人が紙の本や別のスキャンで引ける)。 前付けがあるので PDF の番号とずれる。
- `offset BOOK.pdf 40-50` はページ上下端の数字だけのブロックから `PDF − ノンブル` を推定する。 章の扉・図版ページ・柱と一体の数字では外れるので、 本文の続くページ範囲で測る。
- 本ごとの差を正本ノートに書いておく (「本のページ = PDF − N」)。 次に読む session が同じ測定をしなくて済む。

## <a id="colophon"></a>奥付

- **初版の日付と、 スキャンした本の刷**を分けて書く (「新版第1刷 YYYY-MM-DD、 スキャンは第N刷」)。 版と刷は別物。
- 書誌はファイル名から推測しない。 ファイル名は略称・誤字・別の本 (同じ題の図解本など) のことがある。
- 著者名・監修者名・訳者名は画像で確かめる。 奥付に発行日の行が無いスキャンもある (そう書く)。

## <a id="output-volume"></a>出力の量

- 前付け 30 ページの文字層を全部出すと数万 token になる (実測)。 点線リーダと数字だけの行を落とし (`--compact`)、 ページあたりの文字数を切る (`--max-chars`)。
- 長い出力は file に書いて必要な範囲だけ読む。 1 冊ずつ下見を file に出しておくと、 本を行き来しても再計算が要らない。

## <a id="record"></a>記録の書き方

- 1 冊 1 節: **書誌 (奥付)・刷り色・ページ対応・見た範囲・所見・比較材料**。
- **見た範囲**を必ず書く (「目次と奥付のみ」「第 N 章全体 p.a–b」「画像で読んだのは p.c の定義枠」)。 見ていない範囲について結論を書かない。
- 状態の区別を表の列にする: 「目次のみ」「下見」「照合」「本文確認」。 題名だけで判断した本は「題名で判断」。
- **所見と判断を分ける**: 所見は「本がどう書いているか」、 比較材料は「自分の仕事のどの未決に効くか」。 どちらも決定ではないと明記する。
- 既存のノートに「現物未照合」 と書かれた他書の再構成を照合したら、 旧記述は消さずに日付つきの訂正を添える。
- 取り込めなかった本・画像で確かめられなかった値は、 そのまま「未取得」「文字層のみ」 と書く。

## <a id="third-party-works"></a>第三者の著作物

- PDF の写しは `.gitignore` 済みの dir に置く。 ページ画像や切り出しは repo の外 (一時 dir) に出す。
- 引用は照合に要る数行までにし、 所見は自分の言葉でページ番号を指して書く。
- 書名や所見を公開の場所 (公開 repo・公開 doc) に書かない。 公開してよいのはこの doc のような手順だけ。
- 共有してくれた人への質問が要るときは、 記録の「聞くこと」 節に書いて、 連絡するかは依頼者が決める。

## <a id="parallel-sessions"></a>並列 session と同じノート

棚卸しの最中に、 同じ project の別 session が同じノートや SESSION を直すことがある。 編集の前に pull し、 commit は path を指定する
([multi-session-coordination.md#staging-window-race](multi-session-coordination.md#staging-window-race))。 他の session が作業の前提 (方針の決定・役割) を変えたら、 それまでの所見の「比較材料」 をその前提に合わせて書き直す。
